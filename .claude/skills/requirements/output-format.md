# 出力フォーマット（Issue コメント）

確定版は以下の形式で GitHub Issueへコメントする。Issue本文は書き換えない。

```md
## 確定版 受入れ条件・品質条件（P2 要求整理）

### 受入れ条件
- AC-1 🔵 [integration] {条件または操作} のとき、{期待結果} になる（出典: Issue本文 受入れ条件 1）
- AC-2 🔵 [E2E] {条件} のとき、{期待結果} になる（出典: 2026-06-12 PdM 回答。本文にない新規）

### 品質条件
- QC-1 🔵 [CI] {測定可能な基準}（例: 検索 API の p95 応答時間が現状から悪化しない）
- QC-2 🔵 [手動] {基準と確認方法}
- 他は対象外（性能・セキュリティ: 影響なしを確認済み）

### 備考
- {対象外にした項目とその理由、適用した Intent Delta}
```

## 観測を伴う AC（実環境の状態を見て合否を決めるもの）

「デプロイ後に〜が不変であること」「適用前に〜を確認する」のように、**実環境を観測して判定する AC** は「{条件} のとき {期待結果} になる」では書けない。次の欄を明示する。欄が無いと、書き手は「観測すること」だけを書いて「観測した値をどう判定するか」を落とす。

```md
- AC-n 🔵 [手動] {何を観測するか}
  - 基準値: {いつ・何を取るか}
  - 合格条件: {どの値がどうなっていれば合格か}
  - 参考値: {取るが合否には使わない値と、その理由}
  - 不合格時: {中止するのか、どのフェーズへ戻すのか、何を起動するのか}
```

- **「不変」は前後 2 点の比較でしか判定できない。** 基準値を取る AC と判定する AC は必ず対で書く
- **合格条件と「期待する変更」を分ける。** この変更で意図的に変えるもの（削除する索引など）を合格条件に混ぜると、**正常時に不合格になる述語**ができる
- **環境ごとに 1 組ずつ書く。** 検証環境で書いた観測は本番の判定にならない（識別子・命名が環境依存のため）
- **不合格時の行き先を必ず書く。** 「確認する」で終わる AC は、失敗したときに誰も止められない
- **破壊的な回復手順には起動条件を書く。** 起動条件の無い切り戻しは、正常時に実行されて実データを壊す

### 運用手順は AC に埋めない

適用手順・切り戻し・失敗時の対応が (a)(b)(c)… と枝分かれし始めたら、それは AC ではなく **runbook** である。`{records_root}` 配下の別文書へ切り出し、AC 側は「手順書が存在し、各観測に基準値・合格条件・不合格時の分岐が対応づいている」ことを条件にする。

AC に埋めると確定版が人間の読み切れる長さを超え、承認が「全文提示 + OK」に退化する（`common.md`「長期コンテキスト文書の承認」）。

ルール:

- ID は欠番を作らない。後から追加する場合は末尾に追記し、変更は新しいコメント（Delta）で表す
- マーカーは確定時点で全項目 🔵 であること（🟡・🔴 が残る場合は確定しない）
- 出典は人間が検証できる粒度で書く（「Issue本文 受入れ条件 {番号}」「{日付} の {誰} の回答」「既存仕様 {リンク}」）
- **Issue 本文の受入れ条件との対応を追跡可能にする**: 本文由来の AC は本文条件の番号を出典に含め、本文にない AC（具体化・分割・エッジケース追加）は「本文にない新規」とその根拠を明記する。本文の全条件がいずれかの AC にマップされていること（対象外にした条件は備考で申告する）
- テストレベル `[unit|integration|E2E]` は AC に、検証手段タグ `[CI|テスト|手動]` は QC に付ける
