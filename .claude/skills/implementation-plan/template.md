# 実装方針テンプレート

置き場: スタックにしない計画は draft PR 説明文、スタック構成に合意した計画は Issue コメント（`workflow.md` §3・§4）。

```md
## 実装方針（P5 実装計画）

参照: {Issue 番号}、設計書 {リンク or なし}、ADR {リンク or なし}

### ステップ

| # | 内容 | 区分 | 対応 AC | PR | 備考 |
|---|---|---|---|---|---|
| 1 | {再現テストを書く} | TDD | AC-1 | step1（base: {既定ブランチ}） | |
| 2 | {設定値を追加する} | DIRECT | QC-2 | step2（base: step1） | 実施手順: {…} / 検証手順: {…} |

### 触らない範囲
- {範囲}: {理由}

### リスクと検証方針
- {リスク}: {検知・回避方法}

### 人間確認ポイント
- ステップ {n} 完了時: {確認内容}
```

ルール:

- DIRECT のステップは実施手順と検証手順を必ず書く（テストが無い分、検証を明文化する）
- 「PR」列はスタック構成に合意したときだけ埋める。スタックにしない計画では列ごと省く（下の例は 2 ステップをスタックにした場合）
- bugfix の簡易計画はこの表を 1 段落に圧縮してよい（再現テスト → 修正 → 回帰確認）。**簡易計画は 1 PR で出す**（段落内の 3 つの作業をスタックに分けない）
- 計画からの逸脱（スコープ変更・想定外・新しい技術判断）が生じたら停止して人間へ確認する
- 「対応 AC」列は **計画時点の暫定**。実装で可否・粒度が変わりうる。P6 実装 exit で実際のテストと突き合わせて更新する（`tdd-cycle` の「実装後の突き合わせ」を参照）。未検証の AC は `手動(P7 検証・レビュー)` / `別Issue(#n)` / `対象外` を明示し、裏付けの無い「assert 済み」を残さない
