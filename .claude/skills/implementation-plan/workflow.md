# Implementation Plan Workflow

## 1. 入力の読み込み

- P2 要求整理の確定版 AC/QC（Issue コメント）
- 合意した設計・ADR（あれば）。bugfix / chore など P3・P4 を実施しないルートでは P2 要求整理の出力から直接計画する
- 合意した設計がある場合（視点 0 件の Issue を除く）、計画は実装順序・スタック構成・検証方針の確認と、机上のなぞり（下の節。feature / refactoring）に絞る。合意した設計（責務分割・構造・命名）を計画で再掲・再検討しない（変えたくなったら P4 へ戻り、合意し直す）
- P2.5 プロトタイピングを実施した場合は `IMPLEMENTATION_PROMPT.md`（プロトタイプ合意の制約）

## 2. 計画の作成

`template.md` に従い、以下を含める。

- 実装順序とその理由（なぜこの順か）
- 各ステップの TDD / DIRECT 区分
  - TDD: テストで駆動できる作業。`tdd-cycle` で実装する
  - DIRECT: テストで駆動できない作業（環境構築・設定変更・スキーマ適用など）。実施手順と検証手順を必須にする
- 各ステップが満たす AC-ID・設計要素
- 変更対象と、触らない範囲（それぞれ理由つき）。**触らない範囲には Issue のやらないことを全件含める**（`N1`… の番号と理由のみ）。やらないことに踏み込むステップを計画に入れない。踏み込まないと作るものが成り立たないと分かったら、計画を止めて人間へ確認する（スコープ変更。`dev/escalation.md`）
- リスクと検証方針
- 人間確認ポイントの配置

## 3. 刻み方の検討

1 ステップは PR レビュー可能な粒度（1〜数コミット）に保つ。議論の中心は刻み方と確認ポイントの配置。計画が大きくなりすぎる場合はIssue分割を提案する。

### スタック構成の確定（スタックにするかの判定）

ステップが 2 つ以上あり、**各ステップが独立にレビュー・マージできる単位**である計画は、**ステップ = 1 PR** として積み上げ式 PR（stacked PR）で進める。刻み方の合意はそのまま PR の切り方の合意になるため、次を対話で確定する。

- 各 PR の内容（どのステップがどの PR になるか）
- 積む順序と base 関係（step{k} の base は step{k-1}。step1 の base は既定ブランチ）
- 人間チェックを挟む位置

次のいずれかに当たる計画はスタックにしない（従来どおり 1 PR）: ステップが 1 つ、各ステップが独立にマージできない、P5 実装計画を通らないルート（chore / hotfix / spike）、bugfix の簡易計画（`dev/routes.md`）。手順は `stacked-pr` skill を参照する（この skill は構成の合意までを担う）。

スタックの機構は GitHub ネイティブ機能（`gh stack`）が持つ。環境要件は `stacked-pr/SKILL.md` を正とし、**ここで確認できるものを確認する**。

- **事前に確認できる**: gh 2.90.0 以降・`github/gh-stack` 拡張と skill・git 2.20 以降・同一 repo 内で完結すること
- **事前には確認できない**: 対象 repo で stacked PR が有効かどうか（`gh stack submit` が exit 9 で失敗して初めて分かる）。**最初に submit するのは §4 の step1 PR 作成（P5）なので、判明するのもここ**。失敗したら作業を止め、有効化の可否を人間に確認する（有効化できなければスタックにしない）

事前確認で満たさないことが分かった場合:

- **その計画にスタックの有用性があるなら、人間に確認する**（前提を満たす / 従来の 1 PR で進める）。**AI が単独で 1 PR へ落とさない**。前提は更新やインストールで解消できることが多く、黙って落とすとスタックの利点を失う判断を人間が知らないまま行うことになる
- 満たせないことが確定したら、スタックにしない

## 机上のなぞり（承認の前。feature / refactoring）

- **語**: 机上のなぞり = P5 の承認を求める前に、AI が計画のステップを 1 つずつ、コードを書かずにたどり、ステップごとに 4 つ（触るファイル、最初に書くテスト、決めること、未確認の前提）を書き出すこと。決めること = そのステップで、選べる案が 2 つ以上あるもの。計画外の停止 = P6 で、計画のステップにも人間確認ポイントにも置いていないのに、AI が作業を止めて人間に判断を求めた出来事（1 つの出来事は 1 件。前のフェーズ（P2〜P5）へ戻り、戻った先で人間の承認・採用判断を経たものと、スタックで下位の PR への指摘が設計の判断を要して中断したものは数える。P5 で置いた人間確認ポイントと、人間の側から出た追加の依頼は数えない）
- **書き方**: 結果は計画（`template.md` の欄。スタックのときは Issue コメント）に残す。ステップが 1 つの計画でも省かず、短く書く（項目ごとに 1〜2 行）。DIRECT のステップと、新しいテストを書かないステップでは、「最初に書くテスト」の代わりに、検証手順か、守りに使う既存のテストを書く。「触るファイル」は名前だけを挙げる（合意した設計の再掲はしない）。結果は計画の時点の見込みで、P6 でそこから外れること自体は停止にしない。bugfix の簡易計画では行わない
- **決めることの行き先**: 1 件ごとに付ける。(a) ADR の目安（`adr/SKILL.md`）に当たれば P3 へ戻す。(b) 設計に関われば P4 へ戻す。(c) 要求の検討漏れなら P2 へ戻す（(a)〜(c) は Intent Delta を残す）。(d) やらないことへの踏み込みなら、計画を止めて、範囲の変更として人間に確認する。(e) あとから変えても、ほかのステップや設計に響かない選択は、承認のときに選択式の問いとして人間が答え、答えを計画に残す（響くものは (a) か (b)）。答えの無いものを残して P6 に入らない。計画の全体で 1 件も無いときは「なし」と理由を書く
- **未確認の前提**: コードを読んで確かめ、結果を書く。外れていたら計画を直す（合意した設計の前提なら P4 へ戻る）。確かめられないものは「リスクと検証方針」に書き、承認のときに人間に示す。試さないと分からないものは、AI が「リスクとして進める」か「spike の Issue を先に行う」かの推奨を付け、人間が選ぶ。1 件も無いときは「なし」と確かめた範囲を書く
- **なぞり直し**: 前のフェーズへ戻ったあとや、計画を直したあとは、変わったステップだけをなぞり直す

## 4. 承認と記録

- 承認を求める前に、`critical-gate` の軽量版（設計 + 仕様適合の視点）を通すことを推奨する（feature / refactoring。他タイプは任意 — `critical-gate/workflow.md` §0.5）
- AI の見解（推奨する刻み方・棄却した代替案とその理由・残る懸念）を先に提示する（`common.md` の出力契約）。`context-snapshot` を更新して添える（同じ URL）
- 承認は計画全文の一括提示 + OK 待ちにせず、判断のある項目（刻み方・変更対象と触らない範囲・DIRECT の手順・人間確認ポイントの配置）を対話的に確定する（Issue 作成と同じ密度。判断の余地がない項目まで問いに分解しない）
- feature / refactoring では、承認で問うものに、机上のなぞりの (e) の「決めること」と、試さないと分からない前提の扱いを加える。ほかの確かめられなかった前提は、示すだけにする
- ブランチにコミットが無いと GitHub 上で PR を作成できない。その場合は空コミット（`chore: Issue #{n} 着手`）を作ってから draft PR を作成する

**スタック構成に合意しなかったとき（従来の 1 PR）**

- draft PR を作成し、説明文に計画を書く（branch 名は `feature/issue-{Issue番号}-short-desc`、PR タイトルは `{Issue 番号}: 要約`）

**スタック構成に合意したとき（§3）**

- **計画全体（スタック構成を含む）は Issue コメントに記録する**。計画全体はどの PR にも属さず、下位 PR が先にマージされて閉じても参照が切れないようにするため
- P1 で作ったブランチは、まだ PR が無ければ step1 名へ改名してよい（`feature/issue-{n}-step1-{要約}`）。**既に PR がある場合は改名せず、そのブランチと PR を step1 として引き継ぐ**（`stacked-pr` §7）
- 最下段（step1）の draft PR のみをこの時点で作成する。説明文には**自ステップ分**の計画を書き、計画全体の Issue コメントへリンクする。step2 以降の PR は P6 実装で各ステップ完了時に作成する（`stacked-pr` §1）

## 注意事項

- 実装方針は使い捨ての短期コンテキスト。長期価値のある判断理由は P7 検証・レビューの短期コンテキストの昇格で ADR・設計ドキュメントへ移す
- **次の Issue に影響する判断・引き継ぎ（意図的な重複、先送りした検討、前提の制約）は PR 説明でなく Issue コメントに残す**。PR 説明は使い捨てであり、次の Issue の Product Intent 整理時に参照されるのは Issue 側だからである
- 計画時点で新しい技術判断が見つかったら P3 技術判断へ戻る（Intent Delta を Issue へ追記してから）
- bugfix は「再現テストを書く」が最初のステップになる（簡易計画は PR 説明 1 段落でよい）
