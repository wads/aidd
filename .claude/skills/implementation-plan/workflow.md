# Implementation Plan Workflow

## 1. 入力の読み込み

- P2 要求整理の確定版 AC/QC（Issue コメント）
- 設計書・ADR（あれば）。bugfix / chore など P3・P4 を実施しないルートでは P2 要求整理の出力から直接計画する
- P2.5 プロトタイピングを実施した場合は `IMPLEMENTATION_PROMPT.md`（プロトタイプ合意の制約）

## 2. 計画の作成

`template.md` に従い、以下を含める。

- 実装順序とその理由（なぜこの順か）
- 各ステップの TDD / DIRECT 区分
  - TDD: テストで駆動できる作業。`tdd-cycle` で実装する
  - DIRECT: テストで駆動できない作業（環境構築・設定変更・スキーマ適用など）。実施手順と検証手順を必須にする
- 各ステップが満たす AC-ID・設計要素
- 変更対象と、触らない範囲（それぞれ理由つき）
- リスクと検証方針
- 人間確認ポイントの配置

## 3. 刻み方の検討

1 ステップは PR レビュー可能な粒度（1〜数コミット）に保つ。議論の中心は刻み方と確認ポイントの配置。計画が大きくなりすぎる場合はIssue分割を提案する。

### スタック構成の確定（スタックにするかの判定）

ステップが 2 つ以上あり、**各ステップが独立にレビュー・マージできる単位**である計画は、**ステップ = 1 PR** として積み上げ式 PR（stacked PR）で進める。刻み方の合意はそのまま PR の切り方の合意になるため、次を対話で確定する。

- 各 PR の内容（どのステップがどの PR になるか）
- 積む順序と base 関係（step{k} の base は step{k-1}。step1 の base は既定ブランチ）
- 人間チェックを挟む位置

次のいずれかに当たる計画はスタックにしない（従来どおり 1 PR）: ステップが 1 つ、各ステップが独立にマージできない、P5 実装計画を通らないルート（chore / hotfix / spike）、bugfix の簡易計画（`dev/routes.md`）。手順は `stacked-pr` skill を参照する（この skill は構成の合意までを担い、PR の作成・積み替え・マージ追随の手順は持たない）。

## 4. 承認と記録

- 承認を求める前に、`critical-gate` の軽量版（設計 + 仕様適合の視点）を通すことを推奨する（feature / refactoring。他タイプは任意 — `critical-gate/workflow.md` §0.5）
- AI の見解（推奨する刻み方・棄却した代替案とその理由・残る懸念）を先に提示する（`common.md` の出力契約）
- 承認は計画全文の一括提示 + OK 待ちにせず、判断のある項目（刻み方・変更対象と触らない範囲・DIRECT の手順・人間確認ポイントの配置）を対話的に確定する（Issue 作成と同じ密度。判断の余地がない項目まで問いに分解しない）
- ブランチにコミットが無いと GitHub 上で PR を作成できない。その場合は空コミット（`chore: Issue #{n} 着手`）を作ってから draft PR を作成する

**スタック構成に合意しなかったとき（従来の 1 PR）**

- draft PR を作成し、説明文に計画を書く（branch 名は `feature/issue-{Issue番号}-short-desc`、PR タイトルは `{Issue 番号}: 要約`）

**スタック構成に合意したとき（§3）**

- **計画全体（スタック構成を含む）は Issue コメントに記録する**。計画全体はどの PR にも属さず、下位 PR が先にマージされて閉じても参照が切れないようにするため
- P1 で作ったブランチを step1 名へ改名する（`feature/issue-{n}-step1-{要約}`。手順は `stacked-pr` §1）
- 最下段（step1）の draft PR のみをこの時点で作成する。説明文には**自ステップ分**の計画を書き、計画全体の Issue コメントへリンクする。step2 以降の PR は P6 実装で各ステップ完了時に作成する（`stacked-pr` §1）

## 注意事項

- 実装方針は使い捨ての短期コンテキスト。長期価値のある判断理由は P7 検証・レビューの短期コンテキストの昇格で ADR・設計書へ移す
- **次の Issue に影響する判断・引き継ぎ（意図的な重複、先送りした検討、前提の制約）は PR 説明でなく Issue コメントに残す**。PR 説明は使い捨てであり、次の Issue の Product Intent 整理時に参照されるのは Issue 側だからである
- 計画時点で新しい技術判断が見つかったら P3 技術判断へ戻る（Intent Delta を Issue へ追記してから）
- bugfix は「再現テストを書く」が最初のステップになる（簡易計画は PR 説明 1 段落でよい）
