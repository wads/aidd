# TDD Workflow

TDD はテスト技法ではなく、振る舞いを先に確定させる設計と検証の規律である。このプロセスでは、ゲート 1（P6 実装 exit、テスト green）の信頼性が「テストが実装と独立に書かれたこと」に依存するため、test-first は省略できない。

## 0. TODO リスト

実装する AC と、検証手段タグが CI / テストの **QC 全件**を、検証すべき振る舞いの TODO リストに分解する。

- 1 行 1 振る舞い。各行に対応する AC-ID / QC-ID を付ける
- **QC を AC の付随扱いにしない**。QC の各項（例: 「衝突して上書きした件数が 0」）はそれぞれ TODO 行になる。QC が TODO に現れていない場合、その QC はゲートで初めて検証されることになり、往復を生む（実例: remosys-context#77 で QC-4(c) が TODO に無く P7 で 2 往復）
- 設計書の「守るべき振る舞い」も行に含める
- リストから 1 つだけ選んでサイクルに入る。残りには手を付けない
- サイクル中に気づいた振る舞いはその場で実装せず、リストに追記する
- **リストは生きた仮説として扱う**: サイクルごとに現状（完了 ✅・追加・分割・削除）を更新して提示する。最初のリストが最後まで無変更なのは「計画が完璧だった」か「発見を拾っていない」かのどちらかであり、後者を疑う

## 1. Red: 失敗するテストを書く

- TODO リストから選んだ 1 つの振る舞いについて、テストを 1 つ書く
- テストの根拠は AC・設計書・Issueであり、実装コードではない
- **実行して、失敗を観察する。** 「落ちるはず」と仮定して進まない
- **正しい理由で落ちたことを出力で確認する**（コンパイルエラーや別件のエラーで落ちているなら、それは Red ではない）
- **Red の観察は出力の転記で残す**（失敗行 1 行でよい）。チャットに出しただけの観察は記録に残らず、後から検証できない（`common.md` 証拠つき報告の適用対象）。転記先は PR 説明の「Red の記録」セクション
- **予期せぬ Green は停止事象**: 新しいテストが一度も赤にならず通ったら即停止し、人間へ報告する。振る舞いが既に存在する / テストが何も検証していない / 仕様を誤解している、のいずれかである

## 2. Green: テストを通す

最小の変更でテストを通す。戦略は確信度で選ぶ。

- **明白な実装**（デフォルト）: 既知のパターンで確信があるなら、素直に実装する
- **仮実装 → 三角測量**（不確かなとき）: 根拠の薄い領域（未知のライブラリ、🟡 で確定した仕様、複雑なロジック）では、まずベタ書きで通し、2 つ目の例を追加して一般化を強制する。三角測量は AI の誤ったパターンマッチを暴く道具でもある
- 通すのに必要な分だけ書く。先回りの一般化・機能追加をしない

## 3. Refactor: 重複を除去する

- 主目的は重複の除去と意図の明確化。「なんとなく改善」はしない
- 振る舞いを変えない。テストが green のまま維持されることを実行して確認する
- リファクタ中に新しい振る舞いが必要だと気づいたら、TODO リストに戻す
- **この一拍を暗黙に飛ばさない**: 毎サイクル「Refactor: 実施した内容」または「Refactor: 不要（理由）」を明示する。Red→Green→commit の 2 拍で流れ続けるのは第三拍の欠落であり、重複の意図的な残置（後続 Issue で解消予定など）は理由と引き継ぎ先を記録する
- **選択肢のある判断をしていないか確認する**: 実装中に「採らなかった案を名指しできる」判断（方針・データの扱い・方式）を自分で決めていたら、黙って進めず P3 技術判断へ戻って記録する（判定の目安は `adr/SKILL.md`）。**実装中の暗黙の決定は ADR 欠落の最大の経路**であり、記録が無いことは後から grep で検知できない。戻るときは自動進行を中断し、人間の採用判断を経てから実装を再開する（`common.md`「長期コンテキスト文書の承認」）

## 4. 繰り返しと commit / push

- TODO リストの次の 1 行を選んで繰り返す
- **draft PR の担保**: P6 実装の開始時に対象 Issue の draft PR が無ければ、最初のサイクルに入る前に作成する（feature / refactoring は P5 実装計画で既に存在。P5 実装計画を実施しない chore はここで初めて作られる）。spike は対象外 — コードはマージしない前提であり、成果は Issue への報告で残す
- **commit**: サイクル内で刻む。Green 到達時に 1 commit、Refactor で構造を変えたらもう 1 commit（人間が commit タイミングを判断する場合はそれに従う）
- **push**: 1 サイクル完了時（Refactor 後・green 状態）に draft PR へ push する。Red→Green の途中（重複を含む仮実装や三角測量の途上）では push しない — 観察窓のノイズと CI 実行コストを増やさないため

## 鉄の規律

1. 失敗するテストなしに本番コードを書かない
2. 失敗させるのに必要以上のテストを一度に書かない（テストの大量先行生成は後付けと同じ仕様ドリフトを生む）
3. 実装に合わせてテストを書かない（写経テストの禁止）。テストの出所は常に AC・設計書・Issue
4. テストを実行せずに結果を仮定しない

## ガイドライン

- 1 サイクルの変更は小さく保つ。根拠が薄い領域ほど歩幅を狭くする
- テストは振る舞いを検証する。内部実装の詳細に結合させない
- 外部依存のみモックする
- テストレベル（unit / integration / E2E）は P2 要求整理の割り当てに従う
- DIRECT 区分のステップ（環境構築・設定変更など）は TDD の対象外。実装計画の実施手順・検証手順に従う

## 受入れ条件との対応（出力契約）

- AC⇄テストの追跡は **PR 説明の対応表に一本化する**。表は「AC-ID → 検証する振る舞い（テスト名）」でマップする
- **TODO リストの最終状態（✅・追加・分割・削除）と Red の記録（各サイクルの失敗行の転記）を PR 説明の固定セクションに置く**。3 拍がチャットにしか無いと、P8 の独立チェックはそれが実施されたかを判定できない
- **テスト名・コメントに AC-ID を埋め込まない**。`AC-5` 等はそのテスト単体では Issue 文脈を欠き無意味で、Issue 番号を書けば陳腐化する。テスト名は振る舞いの記述のみにする（追跡は上記の対応表が担う）
- 設計書の「守るべき振る舞い」も AC と同様にテスト化する

### 実装後の突き合わせ（reconciliation・P6 exit の必須手順）

計画（P5 実装計画）の AC⇄テスト表は「意図」であり、TDD では実装中にテストの可否・粒度が変わるのが正常。**実装完了時に、対応表を実際に存在するテストと突き合わせて更新する**。

- 各 AC について次のいずれかを明示する:
  - (a) 検証する **実在の** テスト名
  - (b) テストが無い場合 → `手動(P7 検証・レビュー)` / `別Issueに切り出し(#n)` / `対象外` のいずれかのラベル
- 計画時の「〜を assert する」等の**未来形の記述は、実装後に実績へ置き換える**。裏付けの無い「assert 済み」を残さない
- 対応表は PR 内で **1 つ**に保つ（計画表と完了表を分裂させない）

理由: この対応表は「各 AC が実際に検証されている」ことを人間が信じる根拠（ゲート 1 の信頼性の土台）である。裏付けの無い 1 行が表全体の信頼を崩す。計画は意図・実装は実績であり、ゲートの根拠となる表はマージ時点で実績と一致していなければならない。

## 停止条件

- 予期せぬ Green（上記）
- 計画からの逸脱（スコープ変更、想定外の問題、新しい技術判断）
- テストに過剰適合した不自然な実装しか思いつかないとき（仕様の誤解を疑い、人間へ確認する）

いずれも作り込まずに停止して人間へ確認する（エスカレーション）。実装中に要求・設計の検討漏れや矛盾に気づいた場合は、Intent Delta を Issue へ追記してから該当フェーズへ戻る（正常な反復。書式・区分は `common.md`）。
