# Context Snapshot Workflow

## 1. 情報の収集

Issue 番号を起点に以下を読む（GitHub Issue が索引。Issue のリンクとIssue 番号の grep で辿る）。

- GitHub Issue本文（Product Intent）と Intent Delta コメント（P2 要求整理の確定条件、差し戻し記録、UI 合意）
- 関連 ADR・設計書（Binding の records_root 配下の `adr/`・`design/` を Issue 番号で grep）
- PR の実装方針・AC⇄テスト対応表・検証記録・必須申告セクション

## 2. 意図の復元

Product Intent に Intent Delta を古い順に適用し、「最新の意図」を復元する。原文の転載ではなく、適用後の姿を簡潔に書く。

## 3. HTML の生成

1 ファイルの HTML として生成する。**「人間がこれから何を判断するか」を軸に構成し、AI の作業記録は付録へ置く**。セクション構成:

1. **Goal**: この開発単位で達成すること（1〜2 行）
2. **今回の判断**: この snapshot で人間に求める判断（承認・受入れ・選択）と、判断に効く論点・差分。判断ポイントごとの生成では、ここが本文の入口になる
3. **最新の意図**: Delta 適用後の受入れ条件・対象範囲（AC-ID つき。Issue 本文の受入れ条件番号との対応も示す）
4. **設計と構造**: 人間の理解に寄与する形で書く
   - 設計方針: なぜこの分割か・守るべき振る舞い（設計書へのリンク）
   - 関係コンポーネントの構造図・データの流れ（**関係部分のみ**。ER・シーケンスは理解に必要なときだけ）
   - ソースコード参照（`file:line`。読み手が現物へ跳べるように）
   - 設計トピック: 適用したパターン・ドメインモデル・ベースにした技術との対応、意図的に受け入れた技術的負債。**実際に選択・逸脱があった箇所だけ書く**（毎回の定型欄にしない。該当がなければ節ごと省く）
5. **技術判断**: ADR の要約（採用・捨てた選択肢・トレードオフ）とリンク
6. **検証状態**: 要件⇄設計⇄テストの対応。各テスト（unit / integration / E2E）がどの AC-ID・設計要素を検証するか、E2E が要件と合っているかを示す（未検証は明示）
7. **注意が必要な点**: 信頼性マーカーの残存サマリー（未解決の 🟡・🔴）、未検証項目、未確定事項
8. **昇格された記録**: 短期コンテキストから ADR・設計書へ移した内容（あれば）
9. **付録: 作業記録**: P6 実装を自動進行した場合の実行結果（TODO リストの最終状態・Red/Green の記録・テスト/lint の結果）、ゲート通過記録

図にも信頼性マーカーを適用する（コードから機械的に導出 🔵 / AI の解釈を含む 🟡。`SKILL.md` の原則）。判断ポイント途中の生成では、まだ存在しない成果物の節は「未着手」と明示して省く。

ヘッダに生成日時と「これは生成ビューであり、最新の正は記録側にある」旨を明記する。

## 4. 保存と提示

- ワークスペースの使い捨てディレクトリ（例: `.snapshots/`。バージョン管理外）に保存する（ファイル名: `snapshot-{Issue 番号}-{YYYYMMDD}.html`）。HTML は再生成可能な生成ビューであり、リポジトリや records_root にはコミットしない
- 人間がすぐ開ける形で提示する（ブラウザ表示・パス提示など環境に応じて）。GitHub Issue には HTML の要点（検証状態・注意点）を短くコメントする
- 判断ポイントで使う場合は、人間に求める判断と注意点（セクション 2・7）を先頭に要約して提示する

## 注意事項

- 記録に無い内容を推測で補わない。情報が見つからない項目は「記録なし」と書く
- 将来拡張: 入力範囲をプロジェクト全体（コード + 全 ADR・設計書）に広げたプロジェクトレベルのスナップショット。その場合の信頼性マーカーは、生成されるビュー自身の各記述に付与する（どの記述が記録に根拠を持ち、どれがコードからの推定か）
