# Context Snapshot

## いつ使うか

- 判断ポイント（P3 採用判断・P4 設計承認・P5 計画承認・P7 受入れ判断）で、人間へ判断材料を提示するとき。**その時点までの内容でよい**（まだ存在しない成果物の節は「未着手」と明示して省く）
- Issue の現在状態（意図・判断・検証）を素早く把握したいとき

## 入力

- GitHub Issue（Product Intent 本文 + Intent Delta コメント）
- 関連 ADR・設計書（Issue からのリンク）
- PR（実装方針、AC⇄テスト対応表、検証記録）
- 実コード（コンポーネント構造・データの流れ・ソース参照の導出元）

## 出力

- HTML スナップショット 1 ファイル（生成日付き）。Artifact（クロード上の公開ページ。同じファイルを再公開すると同じ URL の内容が更新され、版履歴が残る）として公開し、同じ開発単位では**同じ URL を判断ポイントごとに更新**する。URL は Issue / PR に貼る。ローカルには `.snapshots/` に連番で途中版も残す（`workflow.md` §4）。Artifact が使えない環境（Codex 等）ではローカルの控えを正本とし、パス提示 + Issue コメントで代替する（`workflow.md` §4）

## 扱う Intent

- 全 Intent の生成ビュー（新しい Intent は作らない）

## 原則

- **読者は人間、軸は判断**: 「AI が何をしたか」ではなく「人間がこれから何を判断するか」で構成する。作業履歴・ゲート通過記録は付録に置く
- **日本語で、簡潔に、情報量は多く**: 文章を削る代わりに図で密度を上げる。P4 以降は関係する範囲の構造図（レイヤー / コンポーネント）を必ず載せ、データの流れ・シーケンス・クラス図は設計要素があるときに描く（mermaid）。文字だけの snapshot は要約として失敗している
- **判断ポイントごとに作り直す**: 数値や一部の節だけを書き換えて使い回さない。前の版は `.snapshots/` に残るので、差分は版の比較で分かる
- **図・記述にも信頼性マーカーを付ける**: コードから機械的に導出できるもの（import 関係・コンポーネント構造）は 🔵、AI の解釈を含むもの（シーケンス・データフロー）は 🟡 とし、承認の対話で人間が確認したら 🔵 化する。誤った図は、図が無いより認知負債として悪い
- 関係部分だけを描く。全体図を毎回描かない。読む量が人間の閾値を超えたら要約として失敗している（`common.md` の軽さの定義）
- スナップショットはビューであり、真実の源ではない。不変記録（ADR・設計書・テスト）と食い違った場合は記録側を正とする
- 手で保守しない。古くなったら再生成する（前の版はファイルとして残す。捨てるのは内容の手直しであって版ではない）
- スナップショットを直接編集して情報を足さない。足すべき情報は元の記録（GitHub Issue・ADR・設計書・PR）に書いてから再生成する
