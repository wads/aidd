# Context Snapshot

## いつ使うか

- 判断ポイント（P3 採用判断・P4 の視点の合意・P5 計画承認・P7 受入れ判断）で、人間へ判断材料を提示するとき。P4 では、視点を 1 つ合意するたびに更新する。**その時点までの内容でよい**（まだ存在しない成果物の節は「未着手」と明示して省く）
- Issue の現在状態（意図・判断・検証）を素早く把握したいとき

## 入力

- GitHub Issue（Product Intent 本文 + Intent Delta コメント）
- 関連 ADR、関係する設計ドキュメント・既存の設計書
- PR（実装方針、AC⇄テスト対応表、検証記録）
- 実コード（コンポーネント構造・データの流れ・ソース参照の導出元）

## 出力

- HTML スナップショット 1 ファイル（生成日付き）。Artifact（クロード上の公開ページ。同じファイルを再公開すると同じ URL の内容が更新され、版履歴が残る）として公開し、同じ開発単位では**同じ URL を判断ポイントごとに更新**する。URL は Issue / PR に貼る。ローカルには `.snapshots/` に連番で途中版も残し、片付けで全部消す（`workflow.md` §4）。Artifact が使えない環境（Codex 等）ではローカルの控えを正本とし、パス提示 + Issue コメントで代替する（`workflow.md` §4）

## 扱う Intent

- 合意した設計は、Issue の途中の Design Intent の置き場。それ以外の節は全 Intent の生成ビュー（新しい Intent は作らない）

## 原則

- **判断は背景・問題・現状から書く**: 「今回の判断」は、なぜ今決めるのか（背景）・決めないと何が困るのか（問題）・今どうなっているのか（現状の事実）を先に置き、選択肢と推奨はその後に書く。推奨から始まる判断文は、前提を共有していない読み手には選べない（AAR 2026-09-23）
- **読者は人間、軸は判断**: 「AI が何をしたか」ではなく「人間がこれから何を判断するか」で構成する。**AI の作業記録（TODO・Red/Green・ゲート台帳・テスト実行ログ）は本文にも付録にも置かず、worklog（別ファイル）へ分離する**（同居させると人間の判断材料が埋もれる — AAR 2026-09-11）
- **書き下ろす**: 会話ログ・作業メモの文体を転写しない。完結した日本語で書き下ろし、過度に省略しない。用語は records_root の用語集（`glossary.md`。あれば）の正式名に従い、その場の言い換えを発明しない
- **日本語で、簡潔に、情報量は多く**: 文章を削る代わりに図で密度を上げる。合意した設計に「構造・依存」がある Issue では構造図（レイヤー / コンポーネント）を必ず載せ、データの流れ・シーケンス・クラス図は合意した設計にあるときに描く（mermaid）。それ以外で理解のために載せる図は「参考の図（合意していない）」として分ける。文字だけの snapshot は要約として失敗している
- **記録から作る節は、判断ポイントごとに作り直す**: 数値や一部の節だけを書き換えて使い回さない。合意した設計は同じ 1 枚に引き継ぎ、人間の再合意なしに変えない。前の版は `.snapshots/` に残るので、差分は版の比較で分かる
- **図・記述にも信頼性マーカーを付ける**: コードから機械的に導出できるもの（import 関係・コンポーネント構造）は 🔵、AI の解釈を含むもの（シーケンス・データフロー）は 🟡 とし、承認の対話で人間が確認したら 🔵 化する。誤った図は、図が無いより認知負債として悪い
- 関係部分だけを描く。全体図を毎回描かない。読む量が人間の閾値を超えたら要約として失敗している（`common.md` の軽さの定義）
- 合意した設計は、Issue の途中の設計の元である。それ以外の節（要求、技術判断、検証）はビューであり、記録（Issue・ADR・テスト）と食い違った場合は記録側を正とする
- 記録から作る節は、直接編集して情報を足さない。足すべき情報は元の記録（GitHub Issue・ADR・PR）に書いてから作り直す。合意した設計と実装のポイントは、snapshot に直接足す
