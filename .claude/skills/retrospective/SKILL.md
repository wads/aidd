# Retrospective

## いつ使うか

- Issue の開発フローが終わったとき（P8 振り返り）
- フェーズ区切りで、意図と結果のズレを点検したいとき
- プロセス自体（playbook・ルール）を直す材料を集めたいとき

## 入力

- `topic`（対象の Issue・フェーズ）
- 対象フローの経過（Issue・PR・コメント・実行結果）

## 出力

- 合意した「次に変えること」→ playbook への PR、プロジェクトのルール・メモリ
- 発見のトリアージ結果（Issue 化 / その場修正 / 候補保持 / 破棄）
- **AI 自身の逸脱の申告**（省略不可。「逸脱なし」には根拠を必須とする）
- **参照されなかった記述の申告**（形骸化の検出。AI にしか観測できない）

## 扱う Intent

- Learning Intent（作成）

## 形式（AAR）

KPT（Keep / Problem / Try）ではなく AAR（After Action Review）を基本形とする。理由:

- この playbook は Intent 駆動であり、AAR の中心問い「**意図と結果の差分**」が構造にそのまま一致する（P8 の第一関心「どの Intent がどこで途切れたか」は AAR そのもの）
- KPT はスプリント単位のチーム活動用で、1 Issue 単位・人間 1 人 + AI の単発イベントには形が合わない
- KPT には「なぜそうなったか」を掘る導線がなく、症状の分類で止まりやすい
- **Keep 列を置かない**。埋めるために書かれた誤った Keep は害になる。うまくいったことは差分分析で「意図どおり動いた箇所」として自然に出る

## 当事者性への対処

この振り返りは AI が当事者であるプロセスを AI と行う。進行役と被評価者が同一のため、自己評価は甘くなる。次で担保する（詳細は `workflow.md` の 4-1〜4-3）。

- 人間の期待違反を入口に置き、AI の観察を先出ししない（AI が生成できない唯一の情報を先に取る）
- AI 自身の逸脱を出力契約として要求する
- 作業文脈を渡さない独立チェックを併用する（毎回の契約チェックは軽量モデル、判断を要する独立レビューは条件付きで強いモデル。両者を混同して報告しない）
