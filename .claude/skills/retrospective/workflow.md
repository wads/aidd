# Retrospective Workflow

KPT は AI が完成品を提示して読んでもらう成果物ではなく、人間との対話で作る。一方的に整理して記録するのは振り返りの形骸化である。

1. 対象フェーズやタスクを確認する
2. **AI の観察を先に短く提示する**（Keep / Problem の候補。長文の完成 KPT にしない）
3. **人間の Keep / Problem を聞く**。AI の観察と食い違う場合は、AI 側の認識を修正するか、根拠を添えて異を唱える（同調しない）
4. 突き合わせの結果から Try を合意する。特に以下を重点的に抽出する（Learning Intent）
   - 意図が後工程へ伝わらなかった点（どの Intent がどこで途切れたか）
   - 認知負債になりかけた点（記録すべきだったのにされなかった判断）
   - 短期コンテキストの昇格漏れがなかったか
   - プロセスが重かった点（形骸化した記載、不要だった承認）・対話が薄かった点（読むだけで流れた承認）
5. フロー中に捕捉した発見（アイデア・フォロー候補・スコープ外化した要求）をまとめてトリアージする。各件を次のいずれかに割り当てる:
   - 着手を決める → product-intent → Issue 化
   - その場で修正（数分で直せる負債）
   - `roadmap` 等に候補として保持
   - 破棄
   フロー中に個別 Issue を量産せず、ここで昇格・整理する（未検証のアイデアを一級 Issue として滞留させない）
6. **記録先は「合意した Try」だけでよい**: playbook への PR / Issue、またはプロジェクトのメモリ・ルールへ反映する。KPT の生ログを GitHub Issue へコメントするのは既定では行わない（Issue に長期価値のない記録を残さない）。プロジェクトとして残したい場合のみ人間の指示でコメントする
