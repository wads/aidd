# Retrospective Workflow

振り返りは AI が完成品を提示して読んでもらう成果物ではなく、人間との対話で作る。一方的に整理して記録するのは振り返りの形骸化である。

## 1. 期待違反（入口・人間が先に答える）

**「想定と違ったのはどこか」** を人間へ先に問う。AI は自分の観察を先出ししない（先に出すと人間の回答がそれに引きずられる）。

- 期待と現実のズレは、AI 協働で最も情報量の多い信号（「AI がこう動くと思っていた」とのズレ）
- 「特に無い」と返ってきた場合のみ、AI 側の気づき（下記 2 で拾ったズレ）を 1〜2 点提示して呼び水にする

## 2. 意図と結果（AI が下書きを出す）

AI は経過（Issue・PR・コメント・実行ログ）から、フェーズごとに次を短く並べる。長文の完成レポートにしない。

| フェーズ | 意図したこと | 実際に起きたこと |
|---|---|---|

- 意図どおりだった箇所も 1 行で書く（「うまくいったこと」はここに現れる。専用の枠は作らない）
- 事実だけを書く。この段階で評価・原因を混ぜない

## 3. 差の原因（掘る）

ズレのあった行について「なぜズレたか」を突き合わせる。重要なのは**プロセスの構造に原因があるか、この回だけの個別事情か**の切り分け。

- 構造が原因 → playbook・ルールの修正候補
- 個別事情 → 記録するだけで修正しない（過剰な一般化を避ける）
- 人間の見立てと AI の見立てが食い違う場合は、AI 側の認識を修正するか、根拠を添えて異を唱える（同調しない）

## 4. 沈黙の点検（KPT では見えない領域）

起きなかったこと・書かれなかったものを能動的に探す。ここは質問しないと永久に出てこない。

- 選択肢のある判断をしたのに ADR に記録しなかったものはないか（→ P3 技術判断）
- 従うべき既存 ADR を引けなかった・気づかなかったことはないか（→ topic 語彙表の見直し。ADR-0003 決定 7）
- 短期コンテキスト（PR・Issue コメント）に残したまま昇格しなかった知見はないか
- 形式的に通しただけのゲート、読むだけで流れた承認はなかったか
- 逆算での確認: 「半年後にこの Issue が原因で問題が起きたとしたら、原因は何か」

### 4-1. AI 自身の逸脱（出力契約・省略不可）

この振り返りは **AI が当事者であるプロセスの振り返り**であり、進行役と被評価者が同一である。自己評価は甘くなる（実例: 対話が薄いフローに対して AI が「ゲートは形骸化しなかった」と誤って肯定した）。したがって次を出力契約として要求する。

- AI は **自分が playbook の契約から外れた箇所を必ず挙げる**（例: 毎サイクル明示すべき Refactor の一拍を飛ばした、TODO リストを一度も更新しなかった、出力契約のフィールドを省略した）
- 「逸脱なし」と述べる場合は、**なぜ無いと言えるかの根拠を必須**にする（`common.md` の「懸念なし」と同じ扱い）
- 人間から先に指摘される前に出す。指摘されてから認めるのは、この契約を満たしたことにならない

### 4-2. 参照されなかった記述の申告

AI は「どの skill・契約を実際に読み、適用したか」を知っている。**一度も参照しなかった記述**を申告する。形骸化した記載を検出する唯一の実行可能な手段であり、人間には観測できない。

- 参照しなかった skill ファイル・チェック項目・テンプレート欄を挙げる
- **「参照しなかった＝不要」ではない**。今回のタイプ・規模で該当しなかっただけの可能性が高い。削除の根拠にするのは、複数回の振り返りで繰り返し参照されなかったことを確認してから

### 4-3. 独立チェック（当事者の自己申告に頼らないための担保）

自己申告（4-1）だけでは、AI が気づいていない逸脱は出てこない。作業文脈を渡さない独立チェックを併用する。**性質の違う 2 種類を分け、混同して報告しない**。

| 種別 | 内容 | 実行 | モデル |
|---|---|---|---|
| 契約チェック | 明示ルールとの照合（PR 必須セクションの有無、AC⇄テスト表に裏付けのない行、🟡🔴 の残存、ルート判断・ゲート記録のコメント有無） | 毎回 | 軽量モデルで足りる（判断を要さない照合のため） |
| 独立レビュー | 判断を要するズレの検出（対話が実質的だったか形式承認か、飛ばされた拍、ズレが構造由来か個別事情か） | 条件付き（契約チェックが違反を出した / 人間が構造的なズレを感じた / 数 Issue に 1 回の定期） | 強いモデル |

- 独立レビューには `critical-gate` の独立性ルール（作業文脈を渡さない・否定する前提で読む・指摘ゼロなら根拠を示す）を適用する
- **契約チェックの結果を「独立レビューを通過した」と報告しない**。機械的照合が通ったことは、判断を要する逸脱が無いことを意味しない。軽量モデルの「特に問題ありません」を通過の根拠に使うと、ゲートが無い状態より悪い（偽の安心を生む）

## 5. 発見のトリアージ

フロー中に捕捉した発見（アイデア・フォロー候補・スコープ外化した要求）をまとめて割り当てる。

- 着手を決める → `product-intent` → Issue 化
- その場で修正（数分で直せる負債）
- `roadmap` 等に候補として保持
- 破棄

フロー中に個別 Issue を量産せず、ここで昇格・整理する（未検証のアイデアを一級 Issue として滞留させない）。

## 6. 次に変えること（合意したものだけ）

- 人間が採否を判断する。AI が「改善案」を並べて終わりにしない
- 記録先は **合意した変更のみ**: playbook への PR / Issue、プロジェクトのルール・メモリ。振り返りの生ログを GitHub Issue へコメントするのは既定では行わない（Issue に長期価値のない記録を残さない）。プロジェクトとして残したい場合のみ人間の指示でコメントする

## 注意事項

- ステップ 1 を飛ばして 2 から始めない（AI の観察が先に出ると、人間の視点が失われる）
- 「うまくいった点」を無理に列挙しない。埋めるために書かれた誤った肯定は、次の判断を誤らせる
- 重い・答えにくいと感じたら、その事実自体を Problem として扱ってよい（この形式も改善対象）
