# 批判的視点（レンズ）

フル版（P7 検証・レビュー）で起動する 4 視点。各視点は独立 agent として実行し、他視点の結果を見せない。

## 1. 仕様適合（acceptance）

- 各 AC は本当にテスト・検証で裏付けられているか（対応表の記載と実在テストの中身を突き合わせる）
- AC にない振る舞いを勝手に追加していないか（スコープ逸脱）
- Issue 本文の受入れ条件と AC の対応が追跡できるか
- エッジケース（空・エラー・境界値・権限）が AC/テストから漏れていないか

## 2. 設計（design）

- 既存アーキテクチャ・パターン・命名との一貫性
- **ドメインの語の名前が用語集と食い違っていないか**: 画面の表示・文書・保存するフィールド・外部に公開する名前に現れるドメインの語が、用語集の識別子から導いた名前になっているか。用語集に無い概念に名前を付けていれば、用語集への追加 PR が出ているか。保存済みの値や変更しない外部提供物に由来する名前は既存のままでよい（`common.md`「用語集」）
- 責務の混在（表示層のビジネスロジック等）、不適切な重複、過剰な抽象化
- ADR・設計書との不整合（設計と違う実装になっていないか）
- 将来の変更（既知の次 Issue）に対して壊れやすい構造にしていないか
- **既存 ADR と矛盾していないか**: 同 topic の有効 ADR（ADR ディレクトリの `INDEX.md`）の決定と、この変更の判断・実装が衝突していないか。衝突しているのに新 ADR が `supersedes` / `amends` でなく `considered`（無関係）と宣言していれば戻り先は P3 技術判断。スクリプトは宣言の網羅しか見ないので、宣言の中身の正しさはここで見る。語彙表に topic を足した ADR は、既存 topic に入らない理由が語彙表の意味欄から読めるか、既存 topic の有効 ADR と実質的に衝突していないかも見る（新 topic だけを名乗る ADR は網羅検査を通る）
- **設計書が無い変更で、構造の判断が diff に埋まっていないか**: 責務分割・依存方向・エラーモデル・命名など「将来の変更者が知らないと壊す」判断が、設計書なしに実装へ入っていないか。`design-docs/workflow.md` §1 の構造基準（テスト以外のコードの新設、責務分割・依存方向の変更）に当たる変更に設計書が無ければ、内容にかかわらず戻り先は P4 設計（chore など P4 を実施しないルートで出てきた場合も同じ。タイプの見直しを提案する）。構造基準に当たらない変更で「設計書なし」が人間に提示・確定されていれば、確定時点で見えていた判断は対象外。確定後の実装中に生じた構造の判断は対象（`common.md` の P6 中の P3/P4 再入）
- **技術的負債を増やしていないか**: 意図しない重複・密結合・テスト困難な構造・層をまたぐ直接参照が増えていないか。意図的に受け入れた負債は設計書「技術的負債の方針」に記録され、返済条件があるか。記録の無い負債は戻り先 P4（設計書に記録するか、実装を直すか）
- **記録されていない判断が diff に埋まっていないか**: 実装中に決められた「採らなかった案を名指しできる」判断（方針・データの扱い・方式）が ADR に無いまま入っていないか。該当すれば戻り先は P3 技術判断。記録の欠落は grep で検知できないため、diff から逆に探す

## 3. テスト独立性（test-integrity）

- テストが実装の写経になっていないか（テストの根拠が AC・仕様に辿れるか）
- 期待値を実装と同じロジックで算出していないか
- テストが内部実装の詳細に結合していないか（リファクタリング耐性）
- 何も検証しないテスト・常に通るテストがないか
- **内部協調者をモックしたテストだけで、部品をまたぐ性質（値が届く・使われる・守られる）の AC を裏づけていないか**。経路の終点（照会・キーの組み立て）で観測しているか、外部境界だけをモックした integration テストがあるかを見る（`requirements/workflow.md` §3）。検出力は変異注入ハーネス（`{aidd_root}/shared/scripts/mutate.py`。呼び出し例は `tdd-cycle/workflow.md` §1）で確かめる
- **変異の置き場は、差分からではなく守る性質の経路（発生源 → 中継 → 終点）から選ぶ**。差分と本体だけでなく、配線・中継・時間方向（値が変わった後の再描画で追随するか）に 1 つ以上置く。生存した変異は、その継ぎ目にテストが無いことを示す指摘として記録する（実装者が自分のテストに合わせて置いた変異では、テストの無い継ぎ目は見つからない。AAR 2026-09-29）

## 4. 回帰・影響範囲（regression）

- 変更が宣言した「触らない範囲」に本当に影響していないか（diff・依存関係で裏取り）
- 削除・変更されたコードの参照が残っていないか
- 既存挙動の互換性（URL・API・データ・操作）が壊れていないか
- ドキュメント（CLAUDE.md・README 等）が変更後の実態と食い違わないか

## 出力形式（各 agent）

```md
- [Critical|Warning|Suggestion] {指摘内容}
  - 根拠: {ファイル・行・記録への具体的参照}
  - 想定戻り先: {P2 要求整理|P3/P4|P6 実装|表現のみ}
```

指摘ゼロの場合は「なぜ欠陥が見つからないと言えるか」を検査した箇所を列挙して示す。
