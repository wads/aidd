# Critical Gate Workflow

## 0. モードの決定

| モード | 対象フェーズ | 構成 |
|---|---|---|
| フル | P7 検証・レビュー（PR レビュー前・必須） | 独立 agent 4 視点（`lenses.md`）+ 取りまとめ |
| 軽量 | P2 要求整理の確定前・P5 承認前（推奨） | 独立 agent 1〜2 視点（対象に応じて選択） |

軽量版の視点選択: P2 要求整理は「仕様適合（要求の曖昧・矛盾・漏れ）」、P5 実装計画は「設計 + 仕様適合（計画が AC を漏れなくカバーするか、刻み方の欠陥）」。

## 0.5 タイプ別の深さ（過剰なゲートを避ける）

ゲートの深さは Issue タイプで決める（タイプ別ルートの原則）。人間から見た軽さを保ちつつ、chore / hotfix の入口コストを上げない。

| タイプ | P7 のゲート | P2/P5 軽量版 |
|---|---|---|
| feature / refactoring | フル版（4視点） | 推奨 |
| bugfix | 軽量版（仕様適合＝再現条件の裏付け + 回帰の2視点） | 任意 |
| chore | 契約チェックのみ（PR 必須セクション・対応表など明示ルールとの機械的照合。軽量モデルで可。独立レビュー agent は起動しない） | 実施しない |
| hotfix | 事後実行を許容（先に直すことを優先。事後必須の P8 振り返り・記録とセットで、マージ後にフル版を実行） | 実施しない |
| spike | 対象外（コードはマージしない。報告のレビューは人間が行う） | 任意（P2 の問いの定義に対して） |

契約チェックの通過を「独立レビュー通過」と報告しない（`retrospective/workflow.md` の独立チェックと同じ区別）。

## 1. 独立 agent の起動

- 各視点の agent には**作業文脈を渡さない**。対象成果物と上流記録（Issue・AC/QC・ADR・設計書）だけを入力にする
- プロンプトに「この成果物には欠陥があるという前提で、それを見つけよ。欠陥が見つからない場合は、なぜ見つからないと言えるかを具体的根拠で示せ」を含める（同調・追認の禁止）
- 各 agent は指摘を {重大度, 内容, 根拠, 想定される戻り先} で返す

## 2. 取りまとめと戻り先判定

- 重複指摘を統合し、取りまとめ役が各指摘の妥当性を**裏取りしてから**採用する（agent の指摘を鵜呑みにしない）
- 採用した指摘ごとに戻り先を確定する:
  - 要求の曖昧・矛盾・検討漏れ → **P2 要求整理**（Intent Delta を Issue へ追記して再入）
  - 技術判断・設計の欠陥 → **P3/P4**
  - 実装・テストの欠陥 → **P6 実装**
  - 表現・記載のみの問題 → その場修正（戻りなし）

## 3. ゲート判定と差し戻しループ

- **Critical が 1 件でも残る場合は不通過**。戻り先フェーズへ差し戻し、修正後に**再度本ゲートを実行**する（修正が新たな欠陥を生んでいないか）
- 差し戻しは `common.md` の「フェーズ間の戻りと Intent Delta」に従う（正常な反復。ただしプロダクト判断・スコープ変更に踏み込む指摘はエスカレーションとして人間へ）
- Warning / Suggestion は通過を妨げない。対応するか持ち越すかを記録して人間レビューへ渡す

## 4. 記録と人間への引き継ぎ

- 指摘一覧・ゲート判定・差し戻し履歴を PR コメント（P2/P5 の場合は Issue コメント）に記録する
- 通過時は「人間レビューで見るべき残論点」（未対応の Warning、判断が割れた点、agent が確信を持てなかった点）を 3〜5 行で要約する。「指摘なし」の場合はなぜ無いと言えるかを添える

## 5. 通過後の追加変更

ゲート通過は**その時点の差分**に対する判定である。人間レビュー・受入れ確認中に追加されたコミットは通過範囲外であり、マージ前に追加差分で本ゲートを再実行する（実装の実質があればフル版、記録・文言のみなら契約チェックで可）。受け皿の手順は `review/acceptance.md` §6〜7。

## 注意事項

- ゲート実行者（取りまとめ役）は作業者と同一セッションでもよいが、視点 agent は必ず独立させる
- 同一指摘への差し戻しが 2 回を超えて解消しない場合は、作り込まず人間へエスカレーションする
- 視点や重大度基準はプロダクト特性に応じて preset で上書きできる
