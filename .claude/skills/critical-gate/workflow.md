# Critical Gate Workflow

## 0. モードの決定

| モード | 対象フェーズ | 構成 |
|---|---|---|
| フル | P7 検証・レビュー（PR レビュー前・必須） | 独立 agent 4 視点（`lenses.md`）+ 取りまとめ |
| 軽量 | P2 要求整理の確定前・P5 承認前（推奨） | 独立 agent 1〜2 視点（対象に応じて選択） |

軽量版の視点選択: P2 要求整理は「仕様適合（要求の曖昧・矛盾・漏れ）」、P5 実装計画は「設計 + 仕様適合（計画が AC を漏れなくカバーするか、刻み方の欠陥、構造基準に当たるのに設計書が無い・「設計書なし / ADR なし」の人間確定が無い）」。

## 0.5 タイプ別の深さ（過剰なゲートを避ける）

ゲートの深さは Issue タイプで決める（タイプ別ルートの原則）。人間から見た軽さを保ちつつ、chore / hotfix の入口コストを上げない。

| タイプ | P7 のゲート | P2/P5 軽量版 |
|---|---|---|
| feature / refactoring | フル版（4視点） | 推奨 |
| bugfix | 軽量版（仕様適合＝再現条件の裏付け + 回帰の2視点） | 任意 |
| chore | 契約チェックのみ（PR 必須セクション・対応表など明示ルールとの機械的照合。軽量モデルで可。独立レビュー agent は起動しない） | 実施しない |
| hotfix | 事後実行を許容（先に直すことを優先。事後必須の P8 振り返り・記録とセットで、マージ後にフル版を実行） | 実施しない |
| spike | 対象外（コードはマージしない。報告のレビューは人間が行う） | 任意（P2 の問いの定義に対して） |

契約チェックの通過を「独立レビュー通過」と報告しない（`retrospective/workflow.md` の独立チェックと同じ区別）。

**P2 へ戻って受入れ条件を立て直した場合は、確定前に軽量版（仕様適合）を必須にする**（chore は契約チェックのみ、hotfix は事後実行のまま。上の表に従う）。立て直した要件の欠陥を P7 で初めて見つけると、フィードバックが最も高くつく（AAR 2026-09-29）。

## 1. 独立 agent の起動

- 各視点の agent には**作業文脈を渡さない**。対象成果物と上流記録（Issue・AC/QC・ADR・設計書）だけを入力にする
- 前回までのゲートの記録と Critical の型の一覧も、視点 agent には渡さない。渡すと、その型を探しに行く偏りが生まれる。同型判定（§2）は取りまとめ役だけが行う
- プロンプトに「この成果物には欠陥があるという前提で、それを見つけよ。欠陥が見つからない場合は、なぜ見つからないと言えるかを具体的根拠で示せ」を含める（同調・追認の禁止）
- 各 agent は指摘を {重大度, 内容, 根拠, 想定される戻り先} で返す

## 2. 取りまとめと戻り先判定

- 重複指摘を統合し、取りまとめ役が各指摘の妥当性を**裏取りしてから**採用する（agent の指摘を鵜呑みにしない）
- 採用した指摘ごとに戻り先を確定する:
  - 要求の曖昧・矛盾・検討漏れ → **P2 要求整理**（Intent Delta を Issue へ追記して再入）
  - 技術判断・設計の欠陥 → **P3/P4**
  - 実装・テストの欠陥 → **P6 実装**
  - 表現・記載のみの問題 → その場修正（戻りなし）
- **同型判定（取りまとめ役が行う）**: 採用した Critical ごとに、欠陥の**型**を 1 文で命名し（例: 「本体は守られているが、本体を呼ぶ配線が空いている」）、前回までのゲートの記録と照らして同じ型かを記録に書く。同じ型なら、修正者は修正の前にその型が成り立ちうる箇所（経路・兄弟・対になる箇所）を全部列挙してから直す。2 回目の扱いは §3 の停止規則
- **取りまとめ役は agent の戻り先を格下げしない**: 判定を変える場合は「agent の判定 / 採用した判定 / 変更の理由」を併記し、P2〜P4 から P6 以下・「表現のみ」への格下げは人間の判断を経る。取りまとめ役が実装者本人のとき、自分が飛ばしたフェーズを軽く見積もる動機を持つ（AAR 2026-09-29）

## 3. ゲート判定と差し戻しループ

- **Critical が 1 件でも残る場合は不通過**。戻り先フェーズへ差し戻し、修正後に**再度本ゲートを実行**する（修正が新たな欠陥を生んでいないか）
- **停止規則（人間へ）**: 同じ型の Critical が**通算 2 回目**に出た場合、または同じ Issue（stacked のときは PR）でゲートが 3 回連続で不通過になった場合は、修正にも次のゲートにも進まず人間へエスカレーションする。推奨の選択肢は「P2 へ戻り、守る性質を 1 文で書き直す」。包括的な承認（「通過するまで繰り返す」等）では免除できず、毎回新しい判断を要する（AAR 2026-09-06 / 2026-09-29）
- 差し戻しは `common.md` の「フェーズ間の戻りと Intent Delta」に従う（正常な反復。ただしプロダクト判断・スコープ変更に踏み込む指摘はエスカレーションとして人間へ）
- Warning / Suggestion は通過を妨げない。**処置台帳**（項目ごとに 対応 / 持ち越しと理由 / 次回に再確認）を記録に置き、取りまとめ役は次回のゲートで持ち越した項目を再確認する。「到達不能」「等価」を理由に格下げするときは、呼び出し元の列挙を根拠として付ける（AAR 2026-09-29）

## 4. 記録と人間への引き継ぎ

- 指摘一覧・ゲート判定・差し戻し履歴を PR コメント（P2/P5 の場合は Issue コメント）に記録する。**記録の無いゲートは実施と認めない**。指摘 ID（例: Critical-1）を他の文書から引用する場合は、参照先の台帳（指摘一覧のコメント）が実在しなければならない（参照先の無い ID は読み手に解決できない）
- 通過時は「人間レビューで見るべき残論点」（未対応の Warning、判断が割れた点、agent が確信を持てなかった点）を 3〜5 行で要約する。「指摘なし」の場合はなぜ無いと言えるかを添える
- **記録は指摘への対応に入る前に投稿する**。見出しは `## N 回目のゲート（{フル版|縮約版|軽量版}）— {通過|不通過}` とする（回数の照合は `review/acceptance.md` §7）。取りまとめ役は前回ゲートの記録を読んでから次のゲートを起動する
- **人間への引き継ぎでは、判断が要る項目と「規約 X に従い Y とした」という報告を分ける**。規約で答えが決まる項目（ADR の採番方法、記録の置き場、既存コメントの扱い等）は問いにしない（`common.md` Principles「判断の数で測る」）

## 5. 通過後の追加変更

ゲート通過は**その時点の差分**に対する判定である。人間レビュー・受入れ確認中に追加されたコミットは通過範囲外であり、マージ前に追加差分で本ゲートを再実行する。深さは 3 段:

- **フル版**: 追加分に実装の実質があり、差分が大きい・独立した機能を含む場合
- **縮約版**: 小差分の連続往復（レビュー対応・ゲート指摘対応）では、独立レビュア 1 体が 4 観点をまとめて検証する縮約を認める。縮約した旨と対象コミットを記録に明記する
- **契約チェックのみ**: 記録・文言のみの変更。ただし**テストの追加・変更を含むコミットは「記録・文言のみ」に該当しない**（検出力の無いテストが green を水増しするリスクがあるため、縮約版以上で再検証する）

受け皿の手順は `review/acceptance.md` §6〜7。

## 6. 適用単位（stacked PR のとき）

ステップが複数で stacked PR を使う場合、本ゲートは **PR の差分ごと**に実行する（Issue 全体でまとめて 1 回ではない）。「ゲート通過後に人間チェック」の順序は PR 単位でも変わらない。

- 対象は当該 PR の差分（その PR の base との差分）であり、下位ステップの差分は含めない
- 深さ（フル / 軽量 / 契約チェック）は §0.5 のタイプ別基準をそのまま PR 単位に適用する
- **積み替え後の再ゲート**: **積み替え、または base の付け替え（下位のマージに伴う自動再ターゲットを含む）**が起きた PR は、差分が変わったかによらず**常に**ゲート通過と人間チェック済みの状態が失効する（ADR-0006）。免除の判定は置かない。**再ゲートの実行は、次にその PR を人間チェックへ出す直前**でよい（失効中の PR はチェックにもマージにも出さない）。あわせてそのステップの検証を再実行する（`stacked-pr` §5）

## 注意事項

- ゲート実行者（取りまとめ役）は作業者と同一セッションでもよいが、視点 agent は必ず独立させる
- 視点や重大度基準はプロダクト特性に応じて preset で上書きできる
