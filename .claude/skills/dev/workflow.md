# Dev Workflow（P1 着手）

## 開始手順

1. Issue の `type-*` ラベルを確認する。ラベルがなければ着手せず、`product-intent` での整備へ差し戻す
2. `workspace-hygiene` の手順で作業ツリーを確認し、未コミット差分を解消する。あわせて、**直前にマージした PR が既定ブランチへ着地しているか**を確認する（`review/acceptance.md` §8。着地していなければ本手順を止め、回復を先に行う。マージ後の確認は人間からの伝達に依存するため、ここが伝達漏れに対する受け皿になる）
3. 差分ゼロを確認したら topic branch を作成する（`feature/issue-{Issue番号}-short-desc`）
4. Issue を読解し、自分の言葉で要求を言い直して人間に確認する
5. `routes.md` からルートを特定して提示する。feature の場合は UI に見える変更を含むかを判断し、P2.5 プロトタイピング（`ui-prototyping`）の実施要否を提案する。**スキップ判断は「見た目に調整の余地があるか」で行う**。初期案に正解（原典・既存踏襲・画面イメージ）があることはスキップ理由にならない — 正解が固定するのは構図だけで、色・凡例・文言などの好みは実表示を見た調整に残る。スキップした場合、その調整は受入れ確認の往復として現れる（`review/acceptance.md` §6 が受け皿）。`critical-gate` の行も省かずに提示する
6. 人間がルートと P2.5 プロトタイピング 実施要否を承認したら、ルートと判断理由を 1〜2 行で Issue コメントへ残し、最初のフェーズ skill へ進む

## 別 Issue の取り込み（受入れ確認中・実装中に「X も今の Issue の中で」と指示されたとき）

人間がスコープ変更を決めた**後**の手順。決定は人間の言葉から始まるが、それはフェーズ省略の許可ではない。コードに触る前に次の 3 つを行う。

1. 両方の Issue に Intent Delta（範囲の変更）を投稿する（`common.md`。「戻る前」だけでなく「取り込む前」も発火条件）
2. 取り込む Issue の `type-*` に従って P1 のルート表（`critical-gate` の行を含む）を提示し、少なくとも P2 の AC を確定する。タイプが元の Issue と違えば分割を提案する（`routes.md`）。取り込む中身が構造基準（テスト以外のコードの新設・スキーマや認可の変更）に当たれば、ラベルが bugfix でも設計書と P3 を要する
3. 入れ物を問う。選択肢は「同じ PR / stacked PR で上に積む / 別 PR」で、マージの順序（出荷前に塞ぐか）とは切り離して問う。分離のコストは `git log` の出力で裏づけて書く

`review/acceptance.md` §6 の調整往復（表示調整・小さな仕様追加）には当たらない。別 Issue・別タイプ・構造基準・スキーマや認可の変更のどれかに当たれば、§6 ではなくここへ来る。「直して」の一言を「実装せよ」と受け取り、P1〜P5 を経ずに 7 分で実装した結果、ゲートが 5 回連続で不通過になった実例がある（AAR 2026-09-29）。

## ルール

- 差分が残っている状態で実装フローを開始しない
- topic branch 作成前にコード変更を始めない
- タイプの特定・差分の扱いに迷ったら人間に確認する
- 着手後にタイプが誤りと判明したらラベルを修正し、本手順からルートを引き直す
- 必須指定のフェーズ・ゲートについて、AI から省略を提案しない。人間が省略を選ぶのは自由だが、それは人間の言葉から始まる
