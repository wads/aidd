# 受入れ検証と昇格判定（P7 検証・レビュー）

ブランチレビューに加え、マージ前の P7 検証・レビューでは以下を実施する。

## 0. 批判的レビューゲート（必須）

人間のレビューへ入る前に `critical-gate` を実行し、通過させる。深さは Issue タイプで決まる（feature / refactoring はフル版、bugfix は軽量版、chore は契約チェックのみ、hotfix は事後実行を許容 — `critical-gate/workflow.md` §0.5）。Critical 指摘は戻り先フェーズへ差し戻して解消してから以降のステップへ進む。ゲートの指摘一覧と判定は PR コメントに記録する。

## 1. 受入れ検証

- P2 要求整理の確定版 AC を 1 件ずつ検証し、AC-ID つきで手順と結果を PR コメントに記録する
- 検証手段タグが CI・テストの項目はゲート 1（テスト green）の結果を確認する
- 手動タグの項目（見た目・操作感・実機確認）はここで検証する
- 未検証項目が残る場合は「未検証項目」として理由つきで明示する

## 2. 整合確認

- diff が ADR・設計書と整合しているか確認する（設計と違う実装になっていないか）
- records_root 配下の `adr/`・`design/` に追加されたファイルの命名（`{連番}-short-title.md`、連番 4 桁 0 埋め）と連番重複を確認する

## 3. 短期コンテキストの昇格判定

短期層（PR 説明・コメント、Issue コメント）を走査し、以下に該当する内容を長期層へ昇格提案する。判定結果は「あり / なし」を必ず申告する。

- 将来の変更時に壊しやすい「守るべき振る舞い」が短期層にしかない → 設計書へ（`design-docs`）
- 選択肢を比較して捨てた判断が短期層にしかない → ADR へ（`adr`）

昇格は人間の承認を得てからマージ前に行う。

あわせて、フロー中に捕捉した発見（アイデア・フォロー候補・スコープ外化した要求）をトリアージする（着手を決めたもののみ Issue 化 / その場修正 / 候補保持 / 破棄）。P8 振り返りを実施しないルート（chore、P8 振り返りを省略した bugfix 等）では、ここが唯一のトリアージ点になる。

## 4. PR 説明の最終化

PR 説明に以下の必須セクションをそろえる。該当がない場合も「なし」と明記する。

- 受入れ条件⇄テスト対応表（AC-ID で参照）
- 技術判断: あり（ADR へのリンク + 設計意図・トレードオフ・影響範囲の要約）/ なし
  - **参照する ADR に `status: proposed` が残っていないことを確認する**。残っている場合は、この場で採用判断を取って `accepted` へ更新するか、保留のままにする理由を明記する。着手前に起票された ADR は、確認されないまま `proposed` で滞留し、判断が済んだのか誰も分からない状態になる
- 短期コンテキストの昇格判定: あり（内容）/ なし
- 未検証項目: あり（内容と理由）/ なし

## 5. コンテキストスナップショット

`context-snapshot` skill でスナップショットを生成して Issue へ添付し、受入れ判断で人間が見るべき点（人間に求める判断・マーカー残存・未検証項目）を要約して提示する。あわせて AI の見解（受入れ可否の推奨と残る懸念。「懸念なし」には理由を付ける）を明示する（`common.md` の出力契約）。

## フェーズ間の戻り

受入れ条件・品質条件を満たせない、または検証中に前段の検討漏れに気づいた場合は、その場で作り込まず、Intent Delta を Issue へ追記してから原因に応じたフェーズ（P2〜P5）へ戻る。戻った先は変わった項目に関係する下流成果物だけを差分更新する（部分再入）。書式・戻りとエスカレーションの区別は `common.md` を参照。
