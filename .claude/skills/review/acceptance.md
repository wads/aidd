# 受入れ検証と昇格判定（P7 検証・レビュー）

ブランチレビューに加え、マージ前の P7 検証・レビューでは以下を実施する。

## スタック時の適用単位（stacked PR の場合の読み替え）

ステップが複数で stacked PR を使う場合、この文書は Issue 単位でなく **PR 単位**で回る。各節の分担は次のとおり（責務配置は `docs/design/0002-stacked-pr-responsibilities.md`）。

| 節 | 各 PR で実施（その PR のマージ前） | 最終 PR で追加実施 |
|---|---|---|
| §0 批判的レビューゲート | ✓ その PR の差分を対象に実施 | ✓（自ステップ分） |
| §1 受入れ検証 | ✓ **自ステップ分の AC のみ**（手動タグはここで検証）。最終 PR も自ステップ分をここで初回検証する | 全 AC の横断確認（他 PR で検証済みの分は再照合） |
| §2 整合確認 | ✓ その PR の差分範囲 | ✓（自ステップ分） |
| §3 昇格判定 | − | ✓ Issue 全体で 1 回 |
| §4 PR 説明 | ✓ 対応表は自ステップ分。集約する節は「最終 PR で実施」と参照記載する | ✓ 全 PR 分の対応表を集約 |
| §5 スナップショット | − | ✓ Issue 全体で 1 回 |
| §6 追加変更の受け皿 | ✓ 該当 PR で | ✓ |
| §7 マージ前契約チェック | ✓ マージのたびに | ✓ |

- **マージ順序**: マージできるのは最下段（base が既定ブランチ）の PR のみ。チェック依頼・ready 化・マージ後の着地確認の手順は `stacked-pr` §6〜§7 に従う
- **Issue 全体の受入れ（AC-10 相当）**: 未マージの PR が最後の 1 本になった時点で、そのマージ前に全 PR の AC⇄テスト対応表を集約し、Issue の全 AC が検証されたことを横断確認する
- **前方修正**: 下位 PR は都度マージされるため、横断確認で漏れが見つかっても巻き戻せない。マージ済み分の誤りは**追加の修正 PR**（前方修正）で直す。漏れの内容と対応 PR を Issue コメントに残す
- **再ゲート・失効**: 積み替えで差分内容が変わった PR は §0 のゲート通過と人間チェック済みの状態が失効する（判定と手順は `stacked-pr` §4〜§5）

## 0. 批判的レビューゲート（必須）

人間のレビューへ入る前に `critical-gate` を実行し、通過させる。深さは Issue タイプで決まる（feature / refactoring はフル版、bugfix は軽量版、chore は契約チェックのみ、hotfix は事後実行を許容 — `critical-gate/workflow.md` §0.5）。Critical 指摘は戻り先フェーズへ差し戻して解消してから以降のステップへ進む。ゲートの指摘一覧と判定は PR コメントに記録する。

## 1. 受入れ検証

- P2 要求整理の確定版 AC を 1 件ずつ検証し、AC-ID つきで手順と結果を PR コメントに記録する
- 検証手段タグが CI・テストの項目はゲート 1（テスト green）の結果を確認する
- 手動タグの項目（見た目・操作感・実機確認）はここで検証する
- 未検証項目が残る場合は「未検証項目」として理由つきで明示する

## 2. 整合確認

- diff が ADR・設計書と整合しているか確認する（設計と違う実装になっていないか）
- records_root 配下の `adr/`・`design/` に追加されたファイルの命名（`{連番}-short-title.md`、連番 4 桁 0 埋め）と連番重複を確認する

## 3. 短期コンテキストの昇格判定

短期層（PR 説明・コメント、Issue コメント）を走査し、以下に該当する内容を長期層へ昇格提案する。判定結果は「あり / なし」を必ず申告する。

- 将来の変更時に壊しやすい「守るべき振る舞い」が短期層にしかない → 設計書へ（`design-docs`）
- 選択肢を比較して捨てた判断が短期層にしかない → ADR へ（`adr`）

昇格は人間の承認を得てからマージ前に行う。

あわせて、フロー中に捕捉した発見（アイデア・フォロー候補・スコープ外化した要求）をトリアージする（着手を決めたもののみ Issue 化 / その場修正 / 候補保持 / 破棄）。P8 振り返りを実施しないルート（chore、P8 振り返りを省略した bugfix 等）では、ここが唯一のトリアージ点になる。

## 4. PR 説明の最終化

PR 説明に以下の必須セクションをそろえる。該当がない場合も「なし」と明記する。

- 受入れ条件⇄テスト対応表（AC-ID で参照）
- 技術判断: あり（ADR へのリンク + 設計意図・トレードオフ・影響範囲の要約）/ なし
  - **参照する ADR に `status: proposed` が残っていないことを確認する**。残っている場合は、この場で採用判断を取って `accepted` へ更新するか、保留のままにする理由を明記する。着手前に起票された ADR は、確認されないまま `proposed` で滞留し、判断が済んだのか誰も分からない状態になる
- 短期コンテキストの昇格判定: あり（内容）/ なし
- 未検証項目: あり（内容と理由）/ なし

## 5. コンテキストスナップショット

`context-snapshot` skill でスナップショットを生成して Issue へ添付し、受入れ判断で人間が見るべき点（人間に求める判断・マーカー残存・未検証項目）を要約して提示する。あわせて AI の見解（受入れ可否の推奨と残る懸念。「懸念なし」には理由を付ける）を明示する（`common.md` の出力契約）。

## 6. 受入れ確認中の追加変更（調整往復の受け皿）

人間の受入れ確認中に追加の変更依頼（表示調整・小さな仕様追加）が出るのは、UI を含む feature では**正常な工程**である。実表示・実データを見て初めて確定できる判断があるためで、往復を減らすことを目標にしない。ただし追加変更は critical-gate の通過範囲外になるため、次を守る:

- 各変更は通常どおり TDD + 検証で進め、確定した判断（PdM 指示・色・命名等）を PR コメントに記録する
- **往復の終了時（マージ前）に必ず**: (1) ゲート通過後の追加差分に対して `critical-gate` を再実行する（追加分に実装の実質があればフル版、記録・文言のみなら契約チェックで可）(2) 確定版 AC・Intent Delta を最終実装と突き合わせ、乖離は Delta として Issue へ追記する
- 「受入れ OK」の言葉だけで再ゲートを省略しない。受入れ判断の対象はゲートを通った成果物である

## 7. マージ前契約チェック（全タイプ必須）

マージ直前に、以下を機械的に照合する（軽量モデル・self-check で可。`critical-gate` の契約チェックと同じ位置づけであり、独立レビューの代替ではない）:

- critical-gate 通過後の追加コミットが再ゲート済みか（§6）
- 確定版 AC・Intent Delta が最終実装と一致しているか
- 「別 Issue でやる」「後で記録する」と宣言した項目が、宣言先（Issue・ADR 等）に実在するか
- PR・Issue に書いた「確認済み・実施済み・green」等の事実主張に、対応する実行記録があるか（`common.md` の証拠つき報告）
- PR 必須セクションがそろっているか（§4。スタック時の下位 PR では、集約する節が「最終 PR で実施」と参照記載されていれば足りる）
- （スタック時）マージ対象が最下段か、直前のマージが既定ブランチへ着地したか（`stacked-pr` §7-1）

## フェーズ間の戻り

受入れ条件・品質条件を満たせない、または検証中に前段の検討漏れに気づいた場合は、その場で作り込まず、Intent Delta を Issue へ追記してから原因に応じたフェーズ（P2〜P5）へ戻る。戻った先は変わった項目に関係する下流成果物だけを差分更新する（部分再入）。書式・戻りとエスカレーションの区別は `common.md` を参照。
