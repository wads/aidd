# Design Docs

## いつ使うか

- **必須（構造基準）**: feature / refactoring で、構造基準（`workflow.md` §1）に当たるとき。実装前に、「構造・依存」と「技術的負債の方針」を含む視点を人間と合意する（ADR-0012）
- **判断駆動**: 上記に当たらないときは、「将来の変更者がこれを知らないと壊すか」を目安に、AI が見せる視点を提案するか、0 件にするかを決める
- P7 検証・レビューの昇格で、設計ドキュメントを更新するとき（`review/acceptance.md` §3）

視点を 0 件にする判断も正当だが、**その場合は理由を人間に提示して確定する**（AI が黙って飛ばさない）。設計の合意があれば P5 実装計画は順序・スタック構成・検証方針の確認に絞る。構造基準に当たる変更では、P3 で「選択肢のある技術判断は無い」と判断した場合もその旨と理由を人間に提示して確定する（P4 の入口で視点を提案する問いにまとめてよい）。

## 入力

- 確定版の受入れ条件・品質条件（P2 要求整理の Issue コメント、AC/QC ID）
- 関連する ADR（あれば）
- 関係する設計ドキュメント・既存の設計書・コード構造（同じ対象に両方あるときは設計ドキュメントを正とする）

## 出力

- P4: 合意した視点 → snapshot の「設計と構造」の節。合意の 1 行 → 対象の GitHub Issue へコメント（`workflow.md` §5）
- P7: 設計ドキュメント → `{records_root}/design/{レイヤー・コンポーネントの名前}.md`（連番なし。service/system 分割は Binding に従う。`template.md` 参照）

## 扱う Intent

- Design Intent（作成）/ Product Intent・Decision Intent（入力）

## 定義（ゲートと後続の手順はここを参照する）

- **設計の合意がある**: Issue に合意の 1 行がある。構造基準に当たる Issue では、その 1 行に「構造・依存」と「技術的負債の方針」の名前がある。ADR-0012 のマージの時点で P4 を終えていた Issue では、設計書か「設計書なし」の確定がある（構造基準に当たる変更では設計書があること。無ければ P4 へ戻り、新方式で合意する）
- **合意した設計**: snapshot の「設計と構造」の節のうち、合意した視点の部分（P5・P7 で足す実装のポイントは含まない）。ADR-0012 のマージの時点で P4 を終えていた Issue では、その設計書
- P4 を通らない Issue（bugfix・chore・hotfix）には、設計の合意を求めない

## exit 条件（ゲート）

- 設計の合意がある（構造基準に当たる Issue で負債が無ければ、「なし」で合意する）
- 各視点に関係する AC-ID が添えてあり、どの視点にも現れない AC は理由が 1 行ある
- 🟡・🔴 マーカーが残っていない
- ADR と内容が重複していない（判断理由は ADR へ寄せ、参照する）
- 視点ごとに人間が合意している（合意の取り方は `common.md`「長期コンテキスト文書の承認」。全文の一括提示 + OK 待ちを合意とみなさない）
