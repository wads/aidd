# Design Docs

## いつ使うか

- 構造基準に当たるとき（必須）と、判断駆動の条件に当たるとき。どちらの条件も `workflow.md` §1
- P7 検証・レビューの短期コンテキストの昇格で、設計判断を記録化するとき

書かない判断も正当だが、AI が黙って飛ばさない。要否は見せる視点と同じ入口の問いで人間が確定する（「設計書なし」= 視点 0 件 + 理由）。設計書が必要かは「将来の変更者がこれを知らないと壊すか」で決める。設計が決まれば P5 実装計画は順序・スタック構成・検証方針の確認に絞る。

## 入力

- 確定版の受入れ条件・品質条件（P2 要求整理の Issue コメント、AC/QC ID）
- 関連する ADR（あれば）
- 既存の設計書・コード構造

## 出力

- 設計書 → `{records_root}/design/{連番}-short-title.md`（service/system 分割は Binding に従う。`template.md` 参照）
- 対象の GitHub Issue へ設計書のリンクをコメント

## 扱う Intent

- Design Intent（作成）/ Product Intent・Decision Intent（入力）

## exit 条件（ゲート）

- 受入れ条件の各 AC-ID について「設計のどこで満たされるか」を対応付けられる
- 関係する範囲の構造図（mermaid）があり、意図的に受け入れる技術的負債とその返済条件が書かれている（無ければ「なし」と明記）
- 🟡・🔴 マーカーが残っていない
- ADR と内容が重複していない（判断理由は ADR へ寄せ、参照する）
- 入口の問いで人間が見せる視点を確定し、各視点を図と AI の見解つきで合意して設計書へ書き込んでいる（`workflow.md` §1・§2）
- 視点の合意から書き足した部分を人間が確認している（全文の一括提示 + OK 待ちを承認とみなさない）

## 読むべき補助ファイル

- `workflow.md`
- `template.md`
