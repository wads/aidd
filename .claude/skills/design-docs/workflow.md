# Design Docs Workflow

## 1. 入口の問い（設計書の要否と見せる視点）

次を読んでから問いを立てる:

- P2 要求整理の確定版 AC/QC（Issue コメント）
- 関連 ADR（技術判断の理由はここに寄せる。設計書に重複させない）
- 既存設計書・既存コードの構造（責務分割・依存方向の現状）

次のいずれかに該当すれば設計書は**必須**（構造基準。feature / refactoring。規模軸ではなく「設計判断が生じたとみなす条件」。ADR-0009）:

- テスト以外のコード（モジュール・スクリプト・コンポーネント。playbook の md やテンプレートは含まない）を新設する
- 既存の責務分割・依存方向を変える

適用後の最初の 2 件（feature / refactoring）では、設計書にかかった往復と分量を P8 振り返りの観察項目に入れ、構造基準を維持するか下限を設けるかを人間が判断する（ADR-0009 トレードオフ）。

該当しない場合は判断駆動で、次のいずれかに当たれば作成する:

- 責務の置き場所に選択の余地があり、間違えると後で壊れる
- 例外ケース・状態遷移が自明でない
- 「守るべき振る舞い」が生まれ、テストだけでは意図が伝わらない

要否と、人間に見せる視点を**同じ 1 問**で聞く（選択式。P5 の承認に混ぜない）。視点は `template.md` の構造図・責務分割・データと状態・主要フロー・例外ケースを既定とし、AI はこの Issue で見せる視点を、入れる・外す理由つきで提案する。人間は視点を足し引きする。

- 視点を選ぶ場合、構造図は外せない（`template.md` の必須節）。小さな変更なら構造図 1 つで足りる
- 「設計書なし」は「視点 0 件 + 理由」として提示する。構造基準に当たる Issue では 0 件を選べない
- 構造基準に当たる変更で P3 に ADR が無い場合は、「ADR なし」の確定もこの問いに含める

0 件で確定したら P5 実装計画へ進む。AI が黙って飛ばした場合は critical-gate の設計レンズ（設計書が無い変更で構造の判断が diff に埋まっていないか）で P4 へ戻される。

## 2. 視点ごとの合意と書き込み

確定した視点を、図（mermaid）つきで 1 つずつ人間と合意する（`common.md`「長期コンテキスト文書の承認」）。順は 構造・依存（構造図・責務分割）→ データ（データと状態）→ 流れ（主要フロー）→ 判断が要る点（例外ケースのほか、技術選定との対応・命名とパターン・守るべき振る舞い・受け入れる負債のうち判断が残るもの）。合意に入る前に `context-snapshot` を生成・更新し（同じ URL）、提案する図を「今回の判断」に載せる。

- 各視点で `common.md` の「AI の見解」（推奨 / 棄却した代替案 / 懸念）を省かない。最後の確認は書き足し部分だけになるので、棄却した案を人間が把握する場はここしかない
- 往復を減らすため、代替案が無く既存構造の写しで済む視点は、隣の視点とまとめて 1 問で見せてよい（まとめても視点ごとの AI の見解は省かない）
- 合意した図と決定は、その場で `template.md` の該当節へ書き込み、🔵 にする
- How と Intent を混ぜない。「どう作るか」より「何を守るか・なぜこの分割か」を中心にする

## 3. 書き足し部分の確認

視点の合意から書き足した部分（目的 / 非目的・AC 対応・技術的負債の方針・未確定事項など、視点として問わなかった節）を仕上げ、その部分だけを人間に確認する。

- 各記述に信頼性マーカー（🔵/🟡/🔴）を付ける。🟡・🔴 を解消（🔵 化または対象外）してから確認を求める
- 各 AC-ID がどの設計要素で満たされるかを対応表にする。やらないこと（N）は「どの設計要素にも含めない」ことを確認し、設計がやらないことを前提にしてしまう箇所（やらないことの実装が無いと成り立たない構造）があれば人間へ提示する
- 長文化しない。書くべき判断がない節は削る
- 確認の前に `context-snapshot` を再生成する（図は設計書から引用される）

## 4. 記録

- `{records_root}/design/{連番}-short-title.md` として保存（連番は 4 桁 0 埋め、design ディレクトリ内で独立）。Binding に `service` がある場合はサービス固有設計を `{records_root}/services/{service}/design/`、横断を `{records_root}/system/design/` に置く
- frontmatter（`type` / `scope` / `status` / `updated`）を必ず付与する
- 既存設計書を置き換える場合は、新しい設計書に「Replaces: {旧文書}」を明記する（旧文書は書き換えない）
- 対象の GitHub Issue へリンクをコメントする

## 注意事項

- 技術選定の理由・捨てた選択肢は ADR の責務。設計書からは参照のみ
- 設計中に新しい技術判断が生まれたら P3 技術判断（`adr`）へ戻ってよい（P3 技術判断 ⇄ P4 設計は反復可能）
- 設計が要求の矛盾・検討漏れを露呈させた場合は P2 要求整理へ戻る（正常な反復。Intent Delta を Issue へ追記してから。書式は `common.md`）
