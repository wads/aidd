# Design Docs Workflow

## 1. 視点の提案（P4 の入口）

次のいずれかに該当すれば**必須**（構造基準。feature / refactoring。規模軸ではなく「設計判断が生じたとみなす条件」）:

- テスト以外のコード（モジュール・スクリプト・コンポーネント。playbook の md やテンプレートは含まない）を新設する
- 既存の責務分割・依存方向を変える

該当すれば、「構造・依存」（構造図つき）と「技術的負債の方針」を含む設計の合意が必須で、視点 0 件は選べない。小さな変更なら、構造図 1 枚と負債「なし」の合意で足りる。

ADR-0012 の適用後の最初の 2 件（feature / refactoring）では、視点の合意にかかった往復と分量を P8 振り返りの観察項目に入れ、必須の視点と順を人間が見直す（ADR-0012 トレードオフ）。

AI は、見せる視点（候補は 構造・依存、データ、流れ（例外を含む）、判断が要る点）を理由つきで提案し、人間が足し引きする。構造基準に該当しない Issue で視点を 0 件にするときは、理由を**人間に提示して確定**し（選択式の問い。P5 の承認に混ぜない）、P5 実装計画へ進む。構造基準に当たる変更で P3 に ADR が無い場合は、「ADR なし」の確定をこの問いに含める。AI が黙って飛ばした場合は critical-gate の設計レンズ（設計の合意が無い変更で構造の判断が diff に埋まっていないか）で P4 へ戻される。

## 2. 入力の読み込み

- P2 要求整理の確定版 AC/QC（Issue コメント）
- 関連 ADR
- 関係する設計ドキュメント・既存の設計書・既存コードの構造（責務分割・依存方向の現状）

## 3. 視点の準備

決まった視点を 1 つずつ書く。守るべき原則:

- How と Intent を混ぜない。「どう作るか」より「何を守るか・なぜこの分割か」を中心にする
- 各記述に信頼性マーカー（🔵/🟡/🔴）を付け、推定で書いた箇所を明示する
- 各視点に関係する AC-ID を添え、どの視点にも現れない AC は理由を 1 行書く。やらないこと（N）は「どの設計要素にも含めない」ことを確認し、設計がやらないことを前提にしてしまう箇所（やらないことの実装が無いと成り立たない構造）があれば、合意の前に人間へ提示する

## 4. 視点ごとの合意

視点を 1 つずつ `context-snapshot` に足して見せ（同じ URL）、AI の見解（推奨・棄却した代替案とその理由・残る懸念）を付けて、合意してから次へ進む（`common.md` の出力契約）。順は、構造・依存 → データ → 流れ → 判断が要る点。図で表せる視点には図（mermaid）を付ける。最終決定は人間が行う。

「判断が要る点」では、**技術的負債の方針（意図的に受け入れる負債と返済条件、増やさないための制約。構造基準に当たる Issue では必須）**を扱う。技術選定との対応（ADR の決定がどの構造に現れるか）は関連 ADR があるとき、命名とパターンは新しい名前を付けるとき、守るべき振る舞いは新しく生まれるときに扱う。全文の一括提示 + OK 待ちは合意とみなさない（`common.md`「長期コンテキスト文書の承認」）。

## 5. 記録

- P4 では文書を保存しない。合意が済んだら、対象の GitHub Issue に 1 行（日付、合意した視点の名前、snapshot の URL。0 件のときは理由）をコメントする。図ややり取りは書かない。公開ページが使えない環境では、URL の代わりに「`.snapshots/` のこの Issue の控え」と書く
- 完了後に残す内容は、設計ドキュメントに書く。`{records_root}/design/` に、連番を付けず、レイヤー・コンポーネントの名前で置き、書き換えて保守する。Binding に `service` がある場合はサービス固有設計を `{records_root}/services/{service}/design/`、横断を `{records_root}/system/design/` に置く
- 設計ドキュメントを最初に作るときは、AI が切り方（レイヤー・コンポーネント）の案を出し、人間が決めてから作る。関係する部分の設計ドキュメントが無ければ、Issue のタイプによらず、その部分だけを作る
- 更新の時点と承認の取り方は `review/acceptance.md` §3 に従う

## 注意事項

- ADR にした判断は、合意した設計でも設計ドキュメントでも繰り返さず、ADR を参照する。ADR にしなかった意図は設計ドキュメントに書く
- 設計中に新しい技術判断が生まれたら P3 技術判断（`adr`）へ戻ってよい（P3 技術判断 ⇄ P4 設計は反復可能）
- 視点の合意で出た代替案が ADR の目安（`adr/SKILL.md`）に当たれば、その場で P3 へ戻る。当たらない棄却案は snapshot に残り、受入れの昇格判定で候補になる（`review/acceptance.md` §3）
- 合意した設計を変えるときは P4 へ戻り、合意し直して snapshot を更新し、Issue に 1 行を足す。ADR-0012 のマージの時点で P4 を終えていた Issue が P4 へ戻ったときも、この手順で合意し直す
- 設計が要求の矛盾・検討漏れを露呈させた場合は P2 要求整理へ戻る（正常な反復。Intent Delta を Issue へ追記してから。書式は `common.md`）
