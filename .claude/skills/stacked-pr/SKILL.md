# Stacked PR

## いつ使うか

- P5 実装計画でスタック構成に合意した Issue の実装を進めるとき（適用条件は `implementation-plan/workflow.md` §3・`dev/routes.md`）
- スタックにしない計画（ステップが 1 つ、各ステップが独立にマージできない、P5 を通らないルート、bugfix の簡易計画）では使わない

## 環境要件

- **gh 2.90.0 以降**と `github/gh-stack` 拡張（`gh extension install github/gh-stack`）
- git 2.20 以降
- 同一リポジトリ内で完結すること（クロスフォークのスタックは非対応）
- **GitHub のパブリックプレビュー機能**であり、仕様が変わる可能性がある

**これらが満たせない環境ではスタックを使わない**（従来どおり 1 PR で進める）。生の git コマンドで代替する手順は持たない。

## 入力

- スタック構成（P5 実装計画で合意したステップ = 1 PR の境界・順序。Issue コメントの計画全体が正）

## 出力

- ステップごとの PR（base の連鎖は `gh stack` が管理する）
- 各 PR のゲート結果・検証結果・チェック依頼 → PR コメント

## 扱う Intent

- Execution Intent（実行。計画の正は Issue コメント側）

## 原則

- **機構は `gh stack` に委ねる**。ブランチの積み替え・base の付け替え・マージ順序の制御を生の git / `gh pr` コマンドで自前に行わない（両者が同じ状態を別々に管理すると壊れる）
- 各 PR の差分は自ステップ分のみを示す
- マージ順序（最下段から）は**サーバー側が強制する**。ミッドスタックの単独マージはできない
- **積み替えを行った PR は、差分が変わったかによらず「ゲート通過済み・人間チェック済み」が失効する**（ADR-0006）。失効は積み替えの直後、再ゲートは次にその PR を人間チェックへ出す直前
- コンフリクトの解消は、自明なら AI が行い、意味の選択が生じるなら人間に確認する
