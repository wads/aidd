# Stacked PR（aidd のプロセス規則）

## いつ使うか

- P5 実装計画でスタック構成に合意した Issue の実装を進めるとき（適用条件は `implementation-plan/workflow.md` §3・`dev/routes.md`）
- スタックにしない計画（ステップが 1 つ、各ステップが独立にマージできない、P5 を通らないルート、bugfix の簡易計画）では使わない

## この skill の位置づけ

**`gh stack` の操作手順はここには書かない。** GitHub が公式のエージェント向け skill を提供しており、そちらが単一の正である。

```bash
gh extension install github/gh-stack     # CLI 拡張（機能本体）
gh skill install github/gh-stack         # エージェント向け skill（操作手順の正）
```

公式 skill は、非対話実行で必要なフラグ（`submit --auto` / `view --json` / `merge <target> --yes` など bare 実行が TUI やプロンプトで止まるもの）、exit code 体系、コンフリクト復旧、`gh stack modify` が TUI 専用であることとその回避策（`unstack` してから `init` で組み直す）まで含んでいる。**コマンドの使い方は必ず公式 skill を参照する**。

この skill が持つのは、aidd のフローに固有の規則だけである。

## 環境要件

- **gh 2.90.0 以降** + `github/gh-stack` 拡張 + `github/gh-stack` skill
- git 2.20 以降
- 同一リポジトリ内で完結すること（クロスフォークのスタックは非対応）
- 対象リポジトリで stacked PR が有効になっていること。**事前の確認手段は公式にも無く、最初の `gh stack submit`（P5 の step1 PR 作成）が exit 9 で失敗して初めて分かる**（有効化手順も公式ドキュメントには無い）
- **GitHub のパブリックプレビュー機能**であり、仕様が変わる可能性がある

**要件を満たすかの判定と、満たさない場合の人間確認は `implementation-plan` が P5 で行う**（責務配置は `docs/design/0002-stacked-pr-responsibilities.md`）。この skill は要件の定義を持つ。

要件を満たせないことが確定した計画はスタックにしない（従来の 1 PR で進める）。生の git コマンドで機構を代替する手順は持たない。

## 入力

- スタック構成（P5 実装計画で合意したステップ = 1 PR の境界・順序。Issue コメントの計画全体が正）

## 出力

- ステップごとの PR（base の連鎖は `gh stack` が管理する）
- 各 PR のゲート結果・検証結果・チェック依頼 → PR コメント

## 扱う Intent

- Execution Intent（実行。計画の正は Issue コメント側）

## 原則

- **機構は `gh stack` に委ねる**。ブランチの積み替え・base の付け替え・マージ順序の制御を生の git / `gh pr` コマンドで自前に行わない（両者が同じ状態を別々に管理すると壊れる）。**例外はスタックの再構成**（途中への挿入・分割・並べ替え・削除。公式手順が生の git でコミットの並びを組み替えてからスタックを作り直す。`workflow.md` §7）
- **スタックの形は人間が所有する**。何段に割るか・各段に何を入れるかは P5 で人間と合意した構成に従い、AI が独断で変えない
- 各 PR の差分は自ステップ分のみを示す
- **積み替え、または base の付け替えが起きた PR は、差分が変わったかによらず「ゲート通過済み・人間チェック済み」が失効する**（ADR-0006）。**下位のマージに伴う自動再ターゲットも含む**。失効した PR は draft に戻す（未チェックであることの唯一の機械的な印）。再ゲートは次にその PR を人間チェックへ出す直前
- **マージ対象は明示的に指定し、最下段から 1 本ずつマージする**。引数なしや上位の指定は、その下の未マージ PR をすべて巻き込む
- コンフリクトの解消は、自明なら AI が行い、意味の選択が生じるなら人間に確認する

## 想定外のケースに出会ったとき

**手順書に無い状況**（未知のエラー、コマンドの挙動が記述と違う、扱い方の分からない操作）に出会ったら:

1. まず**公式 skill のリファレンス**を読む（`references/commands.md` は前提条件と失敗モード、`references/troubleshooting.md` はコンフリクト・squash マージ後・ローカルとリモートの乖離、`references/stack-design.md` は段の切り方）
2. それでも分からなければ**推測で回避せず、作業を止めて人間に相談する**。公式ドキュメントを確認して対応を決める
3. aidd のプロセスに関わるものだけをこの skill へ追記する（`gh stack` の使い方は公式 skill の責務なので、ここに写さない）

この Issue では GitHub の挙動を推測で記述した結果、**実測でしか分からない誤りが 3 回混入した**。網羅的に書こうとするより、出会った時点で確認する方が確実である。
