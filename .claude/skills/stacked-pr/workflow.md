# Stacked PR Workflow

機構は `gh stack`（GitHub ネイティブ機能）が持つ。この文書は **aidd のプロセス規則**と、そこで使う `gh stack` コマンドの対応だけを定める。`gh stack` 自体の詳細は[公式ドキュメント](https://docs.github.com/ja/pull-requests/get-started/about-stacked-prs)を参照する。

以下のコマンドと挙動は実機で確認済み（gh 2.100.0 / gh-stack 拡張）。

## 0. 着手前の確認

```bash
gh --version                          # 2.90.0 以降
gh extension list | grep gh-stack     # 無ければ: gh extension install github/gh-stack
```

満たせない場合、**その計画にスタックの有用性があるなら人間に確認する**（前提を満たす / 1 PR で進める）。AI が単独で 1 PR へ落とさない。満たせないことが確定したら `implementation-plan` の非スタック経路へ戻る。生の git で代替しない。

## 1. スタックの作成

P5 実装計画でスタック構成に合意したら開始する。

```bash
gh stack init feature/issue-{n}-step1-{要約}    # 非対話ではブランチ名の指定が必須
# ... step1 を実装・コミット ...
gh stack add feature/issue-{n}-step2-{要約}     # 次の層を追加（ブランチ作成と checkout を兼ねる）
# ... step2 を実装・コミット ...
gh stack submit                                 # 全ブランチを push し、正しい base で PR を作成する
```

- `gh stack submit` は**全ブランチの push と PR 作成をまとめて行う**。個別の `git push` / `gh pr create` は不要
- **PR は draft で作成される**
- `gh stack view` でスタックの現状を確認できる
- **計画全体（スタック構成を含む）は Issue コメントが正**。各 PR の説明には自ステップ分だけを書き、Issue コメントへリンクする（`implementation-plan` の責務）
- PR 説明の冒頭にスタック位置を書く（例: `PR 2/3`）。人間がマージ画面で最初に見る情報

## 2. ステップ完了と次ステップ

**ステップ完了の時点**は区分で決まる。

- TDD ステップ: そのステップの TODO リストが尽きてテストが green に到達した時点
- DIRECT ステップ: 実装計画に書いた検証手順が完了した時点

ステップ完了ごとに `gh stack add` で次を積み、`gh stack submit` で PR を作る（submit は既存 PR の更新も兼ねる）。

## 3. 先行着手と中断

- PR を人間チェックに出したら、**チェック完了を待たずに次ステップへ着手してよい**（先行して積む）。先行分は下位への指摘次第で積み替え・手戻りが起きることを許容する
- **中断する場合**: 下位 PR への指摘が設計判断（P3/P4 再入）を要するとき。判断基準と手順は `dev/SKILL.md`「P6 実装の自動進行（スタック時）」を正とする

## 4. 下位ステップへの指摘対応（積み替え）

```bash
gh stack down {段数}                 # 修正するステップへ移動
git add . && git commit -m "..."     # 指摘対応をコミット
gh stack rebase --upstack            # 自分より上をまとめて積み替える
gh stack push                        # 書き換わったブランチをまとめて push
gh stack top                         # 最上段へ戻る
```

`gh stack rebase --upstack` は中間ブランチも含めて順に載せ替える。どのブランチをどこへ載せたかを出力するので、記録に使える。

### コンフリクト

```bash
# 競合マーカーを解消してから
git add {解消したファイル}
gh stack rebase --continue           # 最初からやり直す場合は gh stack rebase --abort
```

`gh stack` は競合時に、競合したブランチ名と解消手順を出力する。`--continue` は**エディタを開かずに完了する**ため、非対話実行でも止まらない（実測）。

- **自明な解消は AI が行う**: 片側にしか変更がない、追記位置のズレなど、どちらの意図も損なわずに統合できる場合。解消内容を PR コメントに記録する
- **判断のある解消は人間に確認する**: どちらの変更を残すか・どう統合するかに意味の選択が生じる場合。作業を止め、両案を提示して指示を得る
- 迷ったら「判断あり」に倒す

### コンフリクトせずに壊れる場合

git が差分なしと判定して**無競合で通過したのに結果が壊れている**ことがある（下位と上位が同じ行に同じ値を書いた、カウンタを両方が更新した、など）。§5 の検証再実行がこれを捕まえる。落ちたときは、壊れたステップへ `gh stack down` で移動して直し、`gh stack rebase --upstack` からやり直す。

## 5. 再ゲートと失効（aidd の規則）

**積み替えを行った PR は、差分が変わったかによらず「critical-gate 通過済み」「人間チェック済み」が失効する**（ADR-0006。免除の判定は持たない）。

- **失効は積み替えの直後**。失効した PR は人間チェックに出さない・マージしない
- **再ゲートの実行は、次にその PR を人間チェックへ出す直前**でよい。積み替えのたびに全上位を即座に再ゲートする必要はない。守るべき不変条件は「人間チェックに出す差分・マージする差分は、常にその時点でゲートを通っている」こと
- **そのステップの検証は積み替えの直後にやり直す**（再ゲートを待たない。積み替えが壊れていないことを早く知るため）。TDD ステップはテストを再実行して green を確認し、DIRECT ステップは実装計画の検証手順を再実行する。**実行内容と結果は PR コメントに記録する**

## 6. 人間チェック依頼とマージ

### チェック依頼

critical-gate（その PR の差分）を通過してから依頼する。PR コメントに含めるもの:

- **今マージしてよいか**（`マージ可` / `#{下位PR番号} のマージ待ち`）。人間が最初に必要とする情報なので先頭に置く
- 対象ステップと AC、見てほしい観点
- 自ステップ分の受入れ検証（手動タグの AC はここで検証する）と、差分範囲の整合確認（ADR・設計書との突き合わせ）の依頼

### マージ

```bash
gh pr ready {PR番号}                 # draft のままではマージできない
gh stack merge {PR番号} --merge -y   # --squash / --rebase は repo の方式に合わせる
```

- **`gh pr merge` はスタック PR では使えない**（「非同期マージ REST API を使え」というエラーになる）。必ず `gh stack merge` を使う
- **指定した PR とその下の全 PR がアトミックにマージされる**（all-or-nothing。1 本でもマージできなければ全部マージされない）。ミッドスタックの単独マージは構造的に不可能で、順序違反は起こらない
- マージ前にチェックされるのは「open かつ draft でない」ことだけ。ブランチ保護・リポジトリルールはマージ実行時に GitHub が評価する
- **マージ後、未マージの上位 PR は自動的に base ブランチへ再ターゲットされ OPEN のまま残る**（手動の base 付け替えは不要）
- マージ直前に契約チェック（`review/acceptance.md` §7 相当）を通す
- ローカルを追随させるには `gh stack sync`

## 7. スタック構成の変更（計画変更時）

計画は生きたリストであり、P6 中の変更を許容する。変更時は**必ず Issue コメントの計画全体へ Delta を追記して報告**したうえで:

```bash
gh stack modify     # 対話型: x 削除 / i・I 挿入 / r 改名 / ↑↓ 並べ替え / d・u 折りたたみ
gh stack submit     # 構成変更を GitHub 側へ反映
```

- `gh stack modify` は**対話型**なので、非対話実行では使えない。AI が自動進行中に構成を変える必要が生じたら、人間に実行を依頼する
- 構成変更で積み替えが発生した PR は §5 の失効規則に従う
- 変更後は、影響する PR の説明冒頭のスタック位置とタイトルを実態に合わせて更新する
- **チェック済み PR に影響する変更（削除・順序入れ替え）は自動進行で行わず、人間に確認してから実施する**

## 注意事項

- 操作前に `git status` で作業ツリーが clean であることを確認する（`gh stack modify` はクリーンな作業ツリーを要求する）
- **生の git / `gh pr` コマンドでブランチの付け替え・削除を行わない**。`gh stack` が管理する状態と食い違い、PR が壊れる原因になる
- スタックの状態は `gh stack view`、ローカルの追随は `gh stack sync`
- この手順で解決できない状態に陥ったら、作り込まず人間へエスカレーションする
