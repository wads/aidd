# Stacked PR Workflow（aidd のフローとの対応）

`gh stack` のコマンドの使い方は**公式の `gh-stack` skill が正**（非対話フラグ・exit code・復旧手順を含む）。この文書は **aidd のどのフェーズで何を行い、何を記録し、どこで人間の判断を挟むか**だけを定める。

## 1. P5 実装計画 — スタックの開始

スタック構成に合意したら、公式 skill の手順でスタックを作り、最初の PR を出す。

事前に済ませておくもの（初回のプロンプトや push 先の曖昧さで止まらないため）:

```bash
git config rerere.enabled true         # 競合解決を記憶する。初回実行時の確認プロンプトも回避される
git config remote.pushDefault origin   # リモートが複数ある repo では必須
```

aidd 固有の規則:

- **計画全体（スタック構成を含む）は Issue コメントが正**。下位 PR が先にマージされて閉じても参照が切れないため（`implementation-plan` の責務）
- **PR は draft で作る**（公式の `submit` の既定）。draft は「まだチェックが済んでいない・失効中」の表明として使う（§5・§6）
- 各 PR の説明には**自ステップ分だけ**を書き、Issue コメントの計画へリンクする
- PR 説明の冒頭にスタック位置を書く（例: `PR 2/3`）。人間がマージ画面で最初に見る情報
- PR のタイトル・本文は `gh stack` が自動生成する（コミット件名かブランチ名から）。**タイトルは `{Issue 番号}: step{k} {要約}` に整える**（1 PR 運用の規約に合わせる）。本文とあわせて `gh pr edit` で直す
- ブランチ名は `feature/issue-{n}-step{k}-{要約}`（`gh stack` はブランチ名をそのまま使う）

> **worktree で作業する場合**: `gh stack` のローカル追跡はその worktree に紐づく。別ディレクトリからは同じスタックを操作できず、トランクが親 clone で checkout 済みだと `gh stack trunk` は失敗する（実測）。worktree を消すと追跡も消える。別ツール・別 worktree から扱う必要が出たら公式 skill の該当節（`gh stack link`）を参照する。

## 2. P6 実装 — ステップ完了と次ステップ

**ステップ完了の時点**は区分で決まる。

- TDD ステップ: そのステップの TODO リストが尽きてテストが green に到達した時点
- DIRECT ステップ: 実装計画に書いた検証手順が完了した時点

**層はそのステップに着手する時点で積む**（コミットを積む先を先に用意する）。**PR を出すのはステップ完了時**（コミットが 1 件も無いブランチに PR を作ろうとすると失敗する）。すべてを 1 ブランチに実装してから後で分割することはしない。各層に 1 つの関心事を入れる。

## 3. 先行着手と中断

- PR を人間チェックに出したら、**チェック完了を待たずに次ステップへ着手してよい**（先行して積む）。先行分は下位への指摘次第で積み替え・手戻りが起きることを許容する
- **中断する場合**: 下位 PR への指摘が設計判断（P3/P4 再入）を要するとき。判断基準と手順は `dev/SKILL.md`「P6 実装の自動進行（スタック時）」を正とする

## 4. 下位ステップへの指摘対応

修正は**その関心事を持つ層で行う**（現在の最上段に下位の修正をコミットしない）。どの層が持つか不明なら公式 skill の手順で確認する。修正 → 上位を積み替え → push、までが 1 セット。

### コンフリクトの扱い（aidd の規則）

- **自明な解消は AI が行う**: 片側にしか変更がない、追記位置のズレなど、どちらの意図も損なわずに統合できる場合。解消内容を PR コメントに記録する
- **判断のある解消は人間に確認する**: どちらの変更を残すか・どう統合するかに意味の選択が生じる場合。作業を止め、両案を提示して指示を得る
- 迷ったら「判断あり」に倒す

### コンフリクトせずに壊れる場合

git が差分なしと判定して**無競合で通過したのに結果が壊れている**ことがある（下位と上位が同じ行に同じ値を書いた、カウンタを両方が更新した、など）。§5 の検証再実行がこれを捕まえる。落ちたときは、壊れた層へ移動して直し、積み替えからやり直す。

## 5. 再ゲートと失効（aidd の中核規則）

**積み替え、または base の付け替えが起きた PR は、差分が変わったかによらず「critical-gate 通過済み」「人間チェック済み」が失効する**（ADR-0006。免除の判定は持たない）。

**base の付け替えには、下位のマージに伴ってサーバー側で自動的に行われる再ターゲットも含む**（§6）。自動なので気づきにくいが、失効の扱いは手動の場合と同じ。

失効したときにやること:

- **ready 済みなら draft に戻す**（`gh pr ready --undo {PR番号}`）。draft は「未チェック・失効中」を表す唯一の機械的な印であり、マージ前に GitHub が見るのもこの状態だけである。文章で「マージしない」と書くだけにしない
- 失効した PR は人間チェックに出さない・マージ対象に含めない
- **再ゲートの実行は、次にその PR を人間チェックへ出す直前**でよい。積み替えのたびに全上位を即座に再ゲートする必要はない。守るべき不変条件は「人間チェックに出す差分・マージする差分は、常にその時点でゲートを通っている」こと
- **そのステップの検証は積み替えの直後にやり直す**（再ゲートを待たない。積み替えが壊れていないことを早く知るため）。TDD ステップはテストを再実行して green を確認し、DIRECT ステップは実装計画の検証手順を再実行する。**実行内容と結果は PR コメントに記録する**
- 積み替えが済んでいない PR は人間チェックに出さない（公式 skill の状態表示で、リベースが必要な状態かを確認できる）

## 6. P7 検証・レビュー — チェック依頼とマージ

### チェック依頼

critical-gate（その PR の差分）を通過してから依頼する。PR コメントに含めるもの:

- **今マージしてよいか**（`マージ可` / `#{下位PR番号} のマージ待ち`）。人間が最初に必要とする情報なので先頭に置く
- 対象ステップと AC、見てほしい観点
- 自ステップ分の受入れ検証（手動タグの AC はここで検証する）と、差分範囲の整合確認（ADR・設計書との突き合わせ）の依頼

### マージ

**マージ対象は明示的に指定し、最下段の未マージ PR から 1 本ずつマージする。**

- `gh stack merge` を**引数なしで実行しない**。引数なし・スタック番号の指定は**未マージの PR をすべて**マージ対象にする。PR 番号を指定した場合も**その下の未マージ PR がすべて巻き込まれる**（all-or-nothing）。未チェック・失効中の PR を巻き込む経路になる
- ready 化は**マージする PR だけを単体で指定する**（`gh pr ready {PR番号}`）。`gh stack submit --open` は**既存の PR も含めてスタック全体を ready にする**ため使わない
- マージ前に GitHub が見るのは PR の状態（open・非 draft）だけで、ブランチ保護やリポジトリルールはマージ実行時に評価される。**aidd のゲート（critical-gate 通過・人間チェック済み）は AI と人間が守る**。上位を draft のままにしておくこと（§5）が、誤った対象指定に対する最後の防御になる
- マージ直前に契約チェック（`review/acceptance.md` §7 相当）を通す

### マージ後（必ず行う）

1. **着地確認**: マージは**非同期**で完了まで数分かかることがある。「コマンドが返った = マージ済み」ではないので、PR の状態と既定ブランチへの反映を確認してから次へ進む
2. **上位の積み替え**: 未マージの上位 PR はサーバー側で base が既定ブランチへ自動再ターゲットされるが、**それだけでは上位ブランチの中身は古い土台のままで、PR の差分に下位の変更が混ざる**（squash マージで実測）。公式 skill の同期手順（`gh stack sync`）で上位を積み替える
3. **失効の処理**: 2 の積み替えと base 再ターゲットにより、未マージの上位 PR はすべて §5 の失効規則の対象になる。draft へ戻し、そのステップの検証を再実行する

> **マージキューを使う repo では例外がある**: スタックはキューに投入され、マージ方式はキュー側が決める（指定したフラグは警告つきで無視される）。またキューの都合で**分割して着地することがある**ため、「指定した範囲がまとめて着地する」前提が成り立たない。着地確認をより丁寧に行う。

### CI とブランチ保護の前提（aidd のゲートとの関係）

- ブランチ保護・必須レビュー・状態チェック・CODEOWNERS・スキャンは、**直下の base ではなく「スタックベース」（トランク）に対して評価される**。各 PR が独立にレビュー可能という aidd の前提と整合する
- **CI はスタック内の PR ごとに 1 回走る**。段数が増えるほど CI 使用量が増える。重いジョブを絞りたい場合は `github.event.pull_request.stack`（`number` / `position` / `size` / `base.ref` / `base.sha`）で条件分岐できる（利用先 repo の CI 設定の話であり、aidd の責務ではない）
- **コミット署名が必須の repo では注意**: サーバー側のリベースは未署名コミットになる。ローカルで積み替えを実行すればローカルの署名設定に従う（出典: GitHub 公式ドキュメント「スタックプル要求のトラブルシューティング」）

### P7 各節の分担

`review/acceptance.md`「スタック時の適用単位」に従う（各 PR で受入れ検証・整合確認・契約チェック、最終 PR で snapshot・昇格判定・全 AC の横断確認）。

## 7. 計画変更（スタック構成の変更）

計画は生きたリストであり、P6 中の変更を許容する。

- 変更時は**必ず Issue コメントの計画全体へ Delta を追記して報告**する
- **スタックの形は人間が所有する**。段の追加・削除・順序入れ替え・分割は P5 の合意を変えることなので、**人間に確認してから実施する**（自動進行で行わない）
- **並べ替え・改名・削除に非対話の手段は無い**。公式の対話型 TUI（`gh stack modify`）は**エージェントが起動してはならない**とされており、人間に実行を依頼しても**メタデータが変わるだけで git の祖先関係は変わらない**。スタックを解体して組み直す（公式 skill の該当節を参照）
- **1 PR 運用からスタックへの転換**: 既存のブランチと PR を**そのまま step1 として引き継ぐ**（改名しない。GitHub のブランチ rename は PR を CLOSED にする）。後半の作業を既にコミット済みなら、後半を次の層へ移してから積む
- **作成済み PR の廃止**: PR をクローズし（理由をコメント）、スタックを組み直す。廃止対象より上の PR は §5 の失効規則の対象になる
- 変更後は、影響する PR のスタック位置とタイトルを実態に合わせて更新する

## 注意事項

- **生の git / `gh pr` コマンドでブランチの付け替え・削除を行わない**。`gh stack` が管理する状態と食い違い、PR が壊れる原因になる（`gh pr ready` / `gh pr edit` のような PR の状態・記述の操作は除く）
- この手順で解決できない状態に陥ったら、作り込まず人間へエスカレーションする
