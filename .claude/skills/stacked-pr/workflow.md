# Stacked PR Workflow

## 0. 用語と構造

スタックは「前のステップのブランチの上に次のステップを建てる」PR の連なり。

```
main ─ A            ← step1 ブランチ（PR-1: 差分 A。base = main）
        └ C        ← step2 ブランチ（PR-2: 差分 C。base = step1）
           └ D    ← step3 ブランチ（PR-3: 差分 D。base = step2）
```

- **下位 / 上位**: base に近い側が下位。マージは下位から順に行う
- **積み替え（restack）**: 下位の変更後、上位の鎖を新しい土台の上へ載せ替えること
- **機械的積み替え**: 積み替えのうち、各 PR の diff 内容が変わらないもの（§4 の判定で確認する）

## 1. ブランチ命名と PR 作成

### 命名

- ステップブランチ: `feature/issue-{n}-step{k}-{要約}`（例: `feature/issue-42-step2-restack-procedure`）
- P1 着手で作った Issue ブランチ（`feature/issue-{n}-{要約}`）は、P5 でスタック構成が確定した時点で step1 名へ改名する（PR 未作成段階の改名は無害）:

```bash
git branch -m feature/issue-{n}-{要約} feature/issue-{n}-step1-{要約}
```

### PR 作成のタイミングと手順

ステップ完了ごとに draft PR を作成する。「ステップ完了」の時点は区分で決まる:

- TDD ステップ: そのステップのテストが green に到達した時点
- DIRECT ステップ: 計画に書いた検証手順が完了した時点

```bash
# step1（base は既定ブランチ）
gh pr create --draft --base main --title "{Issue番号}: step1 {要約}" --body-file {自ステップ分の説明}
# step k >= 2（base は前ステップのブランチ）
git switch -c feature/issue-{n}-step{k}-{要約} feature/issue-{n}-step{k-1}-{要約}
# ... 実装 ...
gh pr create --draft --base feature/issue-{n}-step{k-1}-{要約} --title "{Issue番号}: step{k} {要約}" --body-file {説明}
```

### PR 説明の内容

- **冒頭にスタック位置とマージ可否を明記する**（人間がマージ画面で最初に見る情報）:

  ```md
  > **PR 2/4**・base = `feature/issue-42-step1-...`・**#109 のマージまでマージ不可**
  ```

- **自ステップ分のみ**: このステップの計画・実施内容、自ステップ分の AC⇄テスト対応表
- 最終 PR に集約するセクション（短期コンテキストの昇格判定・全体対応表）は「最終 PR で実施」と参照記載する（契約チェックはこの記載で通す）
- 計画全体（スタック構成を含む）は Issue コメントが正（`implementation-plan` の責務）。PR からは Issue コメントへリンクする

## 2. 先行着手と中断

- PR が人間チェック待ちの間も、そのブランチを土台に次ステップの実装へ先行着手してよい（先行分は下位への指摘内容次第で積み替え・手戻りが起きることを許容済み）
- **中断する場合**: 下位 PR への指摘が設計判断（P3/P4 再入）を要するとき。自動進行と先行積みを止め、人間の採用判断を得てから再開する（`dev` のルール参照）。目安: 指摘の解消に「どの案を採るか」の選択が生じる、共有 API・共有部品の設計変更に触れる

## 3. 積み替え（下位 PR に修正が入ったとき）

下位（例: step1）に指摘対応コミットが入ったら、上位の鎖を新しい step1 の上へ載せ替える。

```bash
# 0) 判定用に、積み替え前の各ブランチ位置を記録しておく
git rev-parse feature/issue-{n}-step2-{要約} feature/issue-{n}-step3-{要約}  # 旧位置を控える

# 1) 最上段ブランチで一括積み替え（途中ブランチの先頭も自動で付け替わる）
git switch feature/issue-{n}-step3-{要約}
git rebase feature/issue-{n}-step1-{要約} --update-refs

# 2) 書き換わった全ブランチを push（自分専用ブランチに限り承認不要）
git push --force-with-lease origin feature/issue-{n}-step2-{要約} feature/issue-{n}-step3-{要約}
```

- 積み替えが終わるまで、影響を受ける上位 PR は人間チェックに出さない
- 積み替え後は §4 の判定 → §5 の再ゲート・テスト再実行へ進む

### コンフリクトの扱い

- **自明な解消は AI が行う**: 片側にしか変更がない、追記位置のズレなど、どちらの意図も損なわずに機械的に統合できる場合。解消内容を PR コメントに記録する
- **判断のある解消は人間に確認する**: どちらの変更を残すか・どう統合するかに意味の選択が生じる場合（例: 双方が同じ振る舞いを別の方法で変えている）。作業を止め、両案を提示して指示を得る
- 迷ったら「判断あり」に倒す

## 4. diff 不変判定（range-diff）

積み替えの前後で各 PR の diff 内容が変わったかを、`git range-diff` で機械的に判定する。

```bash
# PR ごとに: 旧コミット列（控えた旧位置） vs 新コミット列
git range-diff {旧base}..{旧head} {新base}..{新head}
```

- 全コミットが `=`（パッチ内容同一）→ **不変**
- `!` や追加・削除がある → **内容が変わった**

判定結果（コマンド出力の要約と判定）を各 PR にコメントで記録する。

## 5. 再ゲート・失効規則

判定結果に応じて:

- **内容が変わった PR**: 「critical-gate 通過済み」「人間チェック済み」の両状態が**失効**する。critical-gate（PR 差分）を再実行 → 通過後に人間チェックを再依頼する。失効した PR はマージしない
- **不変の PR**: 再ゲート不要。ただし積み替え後のブランチで**テストを再実行し green を確認する**（下位の修正で上位が依拠するコードの意味が変わるケースをここで捕捉する）。green にならなければ「内容が変わった」扱いに切り替える

## 6. 人間チェック依頼とマージ

### チェック依頼

critical-gate（PR 差分）通過後:

1. **draft のままチェックを依頼する**（ready 化しない）。draft でもレビュー・コメントはできる。ready 化は §7 でその PR が最下段になったときだけ行う
2. PR コメントでチェックを依頼する。含めるもの:
   - **今マージしてよいか**（`マージ可` / `#{下位PR番号} のマージ待ち`）。人間が最初に必要とする情報なので先頭に置く
   - 対象ステップと AC、見てほしい観点
   - 自ステップ分の受入れ検証（手動タグの AC はここで検証する）と差分範囲の整合確認（ADR・設計書との突き合わせ）の依頼

### マージ（都度マージ）

- 人間チェック完了 = マージしてよい合図。ただし**マージできるのは最下段（base が既定ブランチ）の PR のみ**。チェック済みでも下位が未マージなら、下位のマージを待つ（上位は draft のままなので、マージボタン自体が押せない）
- マージ直前に契約チェック（`review/acceptance.md` §7 相当）を通す
- マージ後は §7 へ（**着地確認 → ブランチ削除 → base 付け替え**の順。確認前に削除しない）

> **補足（CI 設定への影響）**: 上位 PR が draft のままになるため、`types: [ready_for_review]` などで draft をスキップする CI 設定の repo では、上位ステップの CI が最下段になるまで走らない。その場合は CI を draft でも走る設定にするか、ローカルでのテスト実行（§5）で代替する。

## 7. 着地確認と base 付け替え（下位 PR がマージされたとき）

最下段（例: step1）がマージされたら、次の PR（step2）を新しい最下段にする。

### 7-1. 着地確認（必須・削除より先）

「MERGED になった」ことは「既定ブランチへ入った」ことを意味しない。base がトピックブランチのままマージされると、変更はそのトピックブランチへ入り、既定ブランチには届かない。マージのたびに確認する。

```bash
# 1) マージ先が既定ブランチだったか
gh pr view {マージしたPR番号} --json baseRefName -q .baseRefName   # → 既定ブランチ名であること

# 2) 変更が既定ブランチに実際に含まれるか（ブランチ削除前に実行する）
git fetch origin
git log --oneline origin/{既定ブランチ}..origin/{マージしたブランチ}   # → 空であること
```

いずれかが期待と違えば、付け替えへ進まず §7-3 の復旧へ。

### 7-2. ブランチ削除と付け替え

着地確認が通ってからブランチを削除する。**削除は後回しにしない**: GitHub は base ブランチの削除を契機に、それを base にしていた PR の base を自動で付け替える。残したままだと自動付け替えが働かず、上位 PR の base が消えたブランチを指し続ける。

```bash
# 1) マージ済みブランチを削除（自動付け替えの契機）
git push origin --delete feature/issue-{n}-step1-{要約}

# 2) base を既定ブランチへ付け替え（GitHub が自動で付け替えた場合は確認のみ）
gh pr edit {step2のPR番号} --base main

# 3) 既定ブランチの最新を取り込み、マージ済み差分をブランチから落とす
git switch feature/issue-{n}-step3-{要約}   # 最上段で一括
git rebase --onto origin/main {旧step1の先頭コミット} --update-refs
git push --force-with-lease origin feature/issue-{n}-step2-{要約} feature/issue-{n}-step3-{要約}

# 4) 新しく最下段になった PR を ready 化（§6 の draft ガードを解除するのはここだけ）
gh pr ready {step2のPR番号}
```

- **merge commit 運用の repo**: 通常は `git rebase origin/main --update-refs` で足りる（マージ済みコミットはパッチ同一で自動スキップされる）
- **squash マージ運用の repo**: 上記のとおり `--onto` で旧コミット列を明示的に落とす（squash はコミット ID が変わるため自動スキップが効かず、放置すると step2 の diff に step1 の差分が混ざって見える）
- 付け替え後は §4 の判定 → §5 へ（機械的付け替えなら不変になるのが通常）

### 7-3. 誤マージからの復旧（上位 PR を下位ブランチへマージしてしまったとき）

着地確認（§7-1）が期待と違った場合の定型手順。変更は失われておらず、どこかのトピックブランチに集約されている。

1. **集約先の特定**: 各ブランチについて `git log --oneline origin/{既定ブランチ}..origin/{branch}` を実行し、既定ブランチに未着地のコミットがどこにあるかを調べる（通常は最上段に集まる）
2. **統合 PR を 1 本作る**: 集約先ブランチから既定ブランチへの PR を作成する（段ごとに作り直さない）
3. **マージ前に差分検証**: 想定外のコミット・ブランチが混入していないかを確認する（マージ予定のないブランチが混ざっていないか。段数分のコミットがすべて含まれるか）
4. **テスト・lint・build を実行してからマージ**する
5. 復旧の経緯と統合 PR 番号を Issue コメントに残す（スタック構成の Delta として）

## 8. スタック構成の変更（計画変更時）

計画は生きたリストであり、P6 中の変更を許容する。変更時は必ず Issue コメントの計画全体へ Delta を追記して報告し、そのうえで:

- **ステップ追加**: 挿入位置の下位ブランチから新ブランチを切り、挿入位置より上を新ブランチの上へ積み替える（§3）
- **ステップ分割**: 対象ブランチのコミットを 2 ブランチに分け（`git rebase -i` 相当の分割）、上位を積み替える
- **ステップ削除・順序入れ替え**: 対象コミット列を除外・並べ替えて積み替える。**作成済み PR を廃止する場合**は PR をクローズし（理由をコメント）、その上位の base を廃止 PR の下位へ付け替える（§7 と同じ操作）
- **1 PR 運用からスタックへの転換**: 途中でステップ分割が決まった場合、既存ブランチを step1 名へ改名し（§1）、以降を積む
- チェック済み PR に影響する変更（削除・分割・順序入れ替え）は自動進行で行わず、人間に確認してから実施する

## 注意事項

- 操作前に `git status` で作業ツリーが clean であることを確認する（積み替えは未コミット差分と共存できない）
- 積み替え・付け替えの操作履歴（実行コマンドと結果）は該当 PR のコメントに残す。障害時の巻き戻しは記録した旧位置（§3 の rev-parse）を使う
- この手順で解決できない状態（積み替えの連鎖失敗など）に陥ったら、無理に作り込まず人間へエスカレーションする
