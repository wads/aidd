# Stacked PR Workflow

## 0. 用語と構造

スタックは「前のステップのブランチの上に次のステップを建てる」PR の連なり。

```
{既定} ─ A          ← step1 ブランチ（PR-1: 差分 A。base = 既定ブランチ）
        └ C        ← step2 ブランチ（PR-2: 差分 C。base = step1）
           └ D    ← step3 ブランチ（PR-3: 差分 D。base = step2）
```

- **下位 / 上位**: base に近い側が下位。マージは下位から順に行う
- **積み替え（restack）**: 下位の変更後、上位の鎖を新しい土台の上へ載せ替えること

## 0.5 着手前の確認（repo ごとに違う前提）

手順が repo の設定に依存するため、最初に確認する。

```bash
gh repo view --json defaultBranchRef,squashMergeAllowed,mergeCommitAllowed,rebaseMergeAllowed,deleteBranchOnMerge \
  -q '"既定ブランチ=\(.defaultBranchRef.name) squash=\(.squashMergeAllowed) merge=\(.mergeCommitAllowed) rebase=\(.rebaseMergeAllowed) 自動削除=\(.deleteBranchOnMerge)"'
```

- **既定ブランチ**: 以降の `{既定ブランチ}` はこの値（`main` とは限らない）
- **マージ方式**: 許可されている方式が §6 のマージコマンドと §7-2 の追随手順の分岐を決める
- **マージ時の自動ブランチ削除**: 有効でも問題ない（§7-2 参照）。ただし挙動が変わるので把握しておく

あわせて SKILL.md の環境要件を満たすか確認する（`git --version` が 2.38 以上か、その repo で draft PR を作れるか）。

## 1. ブランチ命名と PR 作成

### 命名

- ステップブランチ: `feature/issue-{n}-step{k}-{要約}`（例: `feature/issue-42-step2-restack-procedure`）
- P1 着手で作った Issue ブランチ（`feature/issue-{n}-{要約}`）は、P5 でスタック構成が確定した時点で step1 名へ改名する（PR 未作成段階の改名は無害）:

```bash
git branch -m feature/issue-{n}-{要約} feature/issue-{n}-step1-{要約}
```

### PR 作成のタイミングと手順

- **step1 の PR は P5 実装計画の時点で作成する**（既存の「P5 で draft PR を作る」規約のまま。コミットが無ければ空コミットで作る）
- **step2 以降はステップ完了ごとに作成する**。「ステップ完了」の時点は区分で決まる:
  - TDD ステップ: そのステップのテストが green に到達した時点
  - DIRECT ステップ: 計画に書いた検証手順が完了した時点

```bash
# step1: P5 実装計画の時点で作る（実装の前）。通常は P1 のブランチを改名して使い、
#        新規に切る場合のみ既定ブランチから
git switch -c feature/issue-{n}-step1-{要約} {既定ブランチ}
# コミットが無いと PR を作れない。無ければ空コミット:
git commit --allow-empty -m "chore: Issue #{n} 着手"
git push -u origin feature/issue-{n}-step1-{要約}     # push してから PR を作る
gh pr create --draft --head feature/issue-{n}-step1-{要約} --base {既定ブランチ} \
  --title "{Issue番号}: step1 {要約}" --body-file {説明を書いたファイルのパス}

# step k >= 2: base は前ステップのブランチ
git switch -c feature/issue-{n}-step{k}-{要約} feature/issue-{n}-step{k-1}-{要約}
# ... 実装 ...
git push -u origin feature/issue-{n}-step{k}-{要約}
gh pr create --draft --head feature/issue-{n}-step{k}-{要約} \
  --base feature/issue-{n}-step{k-1}-{要約} \
  --title "{Issue番号}: step{k} {要約}" --body-file {説明を書いたファイルのパス}
```

- **PR 作成前に必ず push する**（未 push だと `gh pr create` が対話プロンプトを出し、非対話実行では止まる）
- **`--head` を必ず明示する**。`gh pr create` は省略するとカレントブランチを head にするため、別のブランチにいるまま実行すると**既存 PR と同じ head を持つ別 PR が、警告もエラーもなく作られる**（§8 の構成変更で積み替えた直後に起きやすい。実測）
- `--body-file` に渡すのは**説明本文を書いたファイルのパス**。作業ツリー外（一時ディレクトリ）に置き、repo にはコミットしない
- タイトルの Issue 番号は `#` を付けない（例: `42: step1 一覧の取得`。`implementation-plan` の PR タイトル規約に合わせる）

### PR 説明の内容

- **冒頭にスタック位置とマージ可否を明記する**（人間がマージ画面で最初に見る情報）:

  ```md
  <!-- k は積み順の通し番号（枝番ブランチも通し番号で数える）、N は総ステップ数。
       §8 で増減したら未マージ PR のヘッダを更新する -->
  > **PR 1/4**・base = `main`・**マージ可**

  <!-- 上位 -->
  > **PR 2/4**・base = `feature/issue-42-step1-...`・**#109 のマージまでマージ不可**
  ```

- **自ステップ分のみ**: このステップの計画・実施内容、自ステップ分の AC⇄テスト対応表
- 最終 PR に集約するセクション（短期コンテキストの昇格判定・全体対応表）は「最終 PR で実施」と参照記載する（契約チェックはこの記載で通す）
- 計画全体（スタック構成を含む）は Issue コメントが正（`implementation-plan` の責務）。PR からは Issue コメントへリンクする

## 2. 先行着手と中断

- PR が人間チェック待ちの間も、そのブランチを土台に次ステップの実装へ先行着手してよい（先行分は下位への指摘内容次第で積み替え・手戻りが起きることを許容済み）
- **中断する場合**: 下位 PR への指摘が設計判断（P3/P4 再入）を要するとき。判断基準と手順は `dev/SKILL.md`「P6 実装の自動進行（スタック時）」を正とする

## 3. 積み替え（下位 PR に修正が入ったとき）

下位（例: step1）に指摘対応コミットが入ったら、上位の鎖を新しい step1 の上へ載せ替える。**手順 0 の記録は修正コミットを積む前に行う**（積んだ後では旧位置を名前で参照できない。取り忘れた場合は reflog から復元する）。

```bash
# 0) §4 の記録用に、積み替え前の全ブランチ位置を控えておく（修正コミットを積む前に）
#    上位ブランチだけでなく、修正する下位ブランチ自身の旧 tip も控える。
#    §4 の range-diff で「各 PR の旧 base」として必要になり、修正後は名前で参照できなくなるため
git rev-parse feature/issue-{n}-step1-{要約} feature/issue-{n}-step2-{要約} feature/issue-{n}-step3-{要約}

#    控え忘れた場合の復元: reflog から積み替え前の位置を得る
#    git reflog feature/issue-{n}-step1-{要約}   （例: step1@{1} が修正前の tip）

# 1) 最上段ブランチで一括積み替え（途中ブランチの先頭も自動で付け替わる）
git switch feature/issue-{n}-step3-{要約}

#    A) 下位にコミットを「積み増した」だけの場合（通常の指摘対応）
git rebase feature/issue-{n}-step1-{要約} --update-refs

#    B) 下位の履歴を「書き換えた」場合（amend / fixup / コミットの削除・並べ替え。
#       §8 のうち分割・削除・順序入れ替えが該当。ステップ追加は A を使う）
#       旧 tip を明示しないと、旧コミットの再適用による衝突や「何も起きない」が発生する
#       引数は「書き換えた段」の新旧で揃える（step1 を書き換えたなら step1 の新ブランチと旧 tip）
git rebase --onto {書き換えた段のブランチ} {同じ段の旧 tip の SHA} --update-refs

# 2) 書き換わった全ブランチを push（下位の修正コミット自体もここでまとめて push してよい。
#    自分専用ブランチに限り承認不要）
#    **修正した下位ブランチ自身も必ず含める**。含め忘れるとリモートの下位が古いまま残り、
#    GitHub 上の上位 PR の差分に下位の変更が混ざる（§4 のリモート側の確認で検知する）
git push --force-with-lease origin \
  feature/issue-{n}-step1-{要約} feature/issue-{n}-step2-{要約} feature/issue-{n}-step3-{要約}
```

- 積み替えが終わるまで、影響を受ける上位 PR は人間チェックに出さない
- 積み替え後は §4 で変化を記録し、§5 の再ゲート・再検証へ進む

### コンフリクトの扱い

- **自明な解消は AI が行う**: 片側にしか変更がない、追記位置のズレなど、どちらの意図も損なわずに機械的に統合できる場合。解消内容を PR コメントに記録する
- **判断のある解消は人間に確認する**: どちらの変更を残すか・どう統合するかに意味の選択が生じる場合（例: 双方が同じ振る舞いを別の方法で変えている）。作業を止め、両案を提示して指示を得る
- 迷ったら「判断あり」に倒す

解消後の再開:

```bash
git add {解消したファイル}
git -c core.editor=true rebase --continue   # エディタを開かせない（非対話実行で止まらないため）
```

積み替えを中止して元に戻す場合は `git rebase --abort`。**コンフリクトは例外ではなく通常経路**（下位の指摘対応が上位の変更箇所に近いと普通に起きる）なので、この手順まで含めて 1 セットで扱う。

### コンフリクトせずに壊れる場合

git が差分なしと判定して**無競合で通過したのに、結果が壊れている**ことがある（下位と上位が同じ行に同じ値を書いた、カウンタや連番を両方が更新した、など。全ステップが同じファイルを触る構成では珍しくない。実測で発生）。§5 の検証再実行がこれを捕まえる。落ちたときは:

1. どのステップの結果が壊れたかを特定する（各ブランチで検証を実行する）
2. **そのステップのブランチで直す**。積み替えの途中なら解消コミットに同梱し、積み替え後に気づいたなら該当ブランチで `git commit --amend`（またはコミットを足す）
3. 直したブランチより上を §3 の分岐 B（履歴を書き換えたケース）で積み替え直す
4. 全ステップで検証を再実行して green を確認する

## 4. 変化の記録

積み替え・base 付け替えの前後で、その PR の差分がどう変わったかを記録する。**これは判定ではなく、人間が変化を読むための記録**である（再ゲートの要否は §5 のとおり変化によらない）。

```bash
# 積み替え前後のコミット列を比較（§3-0 で控えた旧位置を使う）
git range-diff {旧base}..{旧head} {新base}..{新head}
```

あわせて、その PR の差分が**自ステップ分のみ**であることを確認する（AC-5 の不変条件）。**コミット列で見る**:

```bash
# ローカル
git log --oneline {その PR の base}..{その PR のブランチ}     # そのステップのコミットだけが並ぶこと
# リモート（GitHub 上の PR が実際に見せている差分）
git fetch origin
git log --oneline origin/{その PR の base}..origin/{その PR のブランチ}
```

あわせて、**GitHub 上の PR が正しいブランチを指しているか**を確認する（ブランチが正しくても PR の指し先が誤っていることがある。§1 の `--head` 参照）:

```bash
gh pr view {PR番号} --json headRefName,baseRefName -q '"head=\(.headRefName) base=\(.baseRefName)"'
```

**両方を確認する**。ローカルだけでは、§3-2 の push に下位ブランチを含め忘れたケース（リモートの下位が古いまま残り、GitHub 上の PR の差分に下位の変更が混ざる）を検知できない。ref は push 時点で確定するので、`gh pr diff` の反映遅延の問題は起きない。

下位のコミットが混ざっていれば積み替え・付け替え・push が不完全である。`--name-only` によるファイル名の確認では、全ステップが同じファイルを触る構成（よくある）で混入を検知できない。

（`gh pr diff` は force-push 直後に古い差分を返すことがあるため、確認はローカルで行う。注意事項を参照）

出力と、下位の差分が混ざっていないかの確認結果を PR にコメントで記録する。

## 5. 再ゲート・失効規則

**積み替え・base 付け替えを行った PR は、差分が変わったかによらず必ず再ゲートする**（ADR-0006）。

**失効は積み替えの直後、再ゲートは次にその PR を人間チェックへ出す直前**に行う。積み替えのたびに全上位を即座に再ゲートする必要はない（段数が深いと無駄が大きい）。守るべき不変条件は「**人間チェックに出す差分・マージする差分は、常にその時点でゲートを通っている**」ことであり、この運用でも保たれる。

- 積み替えの直後に「critical-gate 通過済み」「人間チェック済み」の両状態が**失効**する
- 失効した PR は人間チェックに出さない・マージしない。次にその PR をチェックへ出すとき（通常は最下段へ昇格したとき）に critical-gate（PR 差分）を再実行し、通過後にチェックを依頼する
- ready 化済み（最下段）なら **`gh pr ready --undo {PR番号}` で draft に戻す**（マージできる状態のまま「マージしない」を文章で守らせない。§6 の draft ガードと同じ理由）
- **そのステップの検証は積み替えの直後にやり直す**（再ゲートを待たない。積み替えが壊れていないことを早く知るため）。TDD ステップはテストを再実行して green を確認し、DIRECT ステップは実装計画に書いた検証手順を再実行する。**実行内容と結果は PR コメントに記録する**（green の主張に裏付けを残す）

> **免除の仕組みは持たない**: 「差分が変わっていなければ再ゲート不要」という判定を 2 度試みたが、いずれも見逃し（再ゲートを誤って省く方向の誤り）が繰り返し見つかった。判定の網羅性を保証できない以上、免除は置かない（ADR-0006 の背景）。

> **付け替え後に下位の差分が混ざっていた場合**は、まず `--onto` の引数を疑う。旧 tip でなく最古のコミットを渡すと下位の差分が混ざる。この場合の対処は積み替えのやり直しである（下位の差分を含んだまま再ゲートを通してはならない）。

## 6. 人間チェック依頼とマージ

### チェック依頼

critical-gate（PR 差分）通過後:

1. **その PR が最下段（base が既定ブランチ）かどうかで分ける**
   - 最下段（base が既定ブランチ）: **チェック依頼の時点ではまだ draft**（§7-2 の ready 化は再ゲートと再チェックの後）。依頼時に ready 化するのではなく、チェック完了後・マージ直前に `gh pr ready {PR番号}` を実行する
   - 上位: **draft のまま依頼する**。draft でもレビュー・コメントはできる。ready 化は §7 でその PR が最下段になったときに行う
2. PR コメントでチェックを依頼する。含めるもの:
   - **今マージしてよいか**（`マージ可` / `#{下位PR番号} のマージ待ち`）。人間が最初に必要とする情報なので先頭に置く
   - 対象ステップと AC、見てほしい観点
   - 自ステップ分の受入れ検証（手動タグの AC はここで検証する）と差分範囲の整合確認（ADR・設計書との突き合わせ）の依頼

### マージ（都度マージ）

- 人間チェック完了 = マージしてよい合図。ただし**マージできるのは最下段（base が既定ブランチ）の PR のみ**。チェック済みでも下位が未マージなら、下位のマージを待つ（上位は draft のままなので、マージボタン自体が押せない）
- マージ直前に契約チェック（`review/acceptance.md` §7 相当）を通す

```bash
gh pr merge {PR番号} --squash    # repo のマージ方式に合わせる（--merge / --rebase）
gh pr view {PR番号} --json state -q .state   # → MERGED（merge コマンドは無出力なので確認する）
```

> **危険なのは「付け替え前の手動削除」**。base 付け替えより先に `git push origin --delete` でブランチを消すと、そのブランチを base にしている上位 PR は **CLOSED** になり、base 変更も reopen もできなくなる（実測）。削除は必ず付け替えの後に行う（§7-2）。
>
> 一方、**マージ時の自動削除（repo 設定 «Automatically delete head branches» や `--delete-branch`）は安全**である。この経路では GitHub が上位 PR の base を既定ブランチへ自動で付け替え、PR は OPEN のまま残る（実測: 自動削除が有効な repo で 3 段スタックを完走）。
- マージ後は §7 へ（**着地確認 → base 付け替え → ブランチ削除**の順。付け替え前に削除すると上位 PR が閉じる）

> **補足（CI 設定への影響）**: 上位 PR が draft のままになるため、`types: [ready_for_review]` などで draft をスキップする CI 設定の repo では、上位ステップの CI が最下段になるまで走らない。その場合は CI を draft でも走る設定にするか、ローカルでのテスト実行（§5）で代替する。

## 7. 着地確認と base 付け替え（下位 PR がマージされたとき）

最下段（例: step1）がマージされたら、次の PR（step2）を新しい最下段にする。

### 7-1. 着地確認（必須・削除より先）

「MERGED になった」ことは「既定ブランチへ入った」ことを意味しない。base がトピックブランチのままマージされると、変更はそのトピックブランチへ入り、既定ブランチには届かない。マージのたびに確認する。

```bash
# 1) マージ先が既定ブランチだったか
gh pr view {マージしたPR番号} --json baseRefName -q .baseRefName   # → 既定ブランチ名であること

# 2) マージで生まれたコミットが既定ブランチに含まれるか
git fetch origin
sha=$(gh pr view {マージしたPR番号} --json mergeCommit -q .mergeCommit.oid)
git merge-base --is-ancestor "$sha" origin/{既定ブランチ} && echo "着地OK"
```

いずれかが期待と違えば、付け替えへ進まず §7-3 の復旧へ。

> **`git log origin/{既定}..origin/{ブランチ}` で判定しないこと**: squash マージはコミット ID が変わるため、正しく着地していてもこの範囲は空にならない。squash 運用の repo では毎回誤検知して §7-3 へ迷い込む。上記の `mergeCommit` の祖先判定は squash・merge commit のどちらでも正しく判定できる。

### 7-2. base 付け替えとブランチ削除

**必ず「付け替え → 削除」の順で行う。順序を逆にすると PR が壊れる**: base にしているブランチが先に消えると、GitHub はその PR を **CLOSED にする**。閉じた PR は base を変更できず（`Cannot change the base branch of a closed pull request`）、base ブランチが無いので reopen もできない。復旧には消したブランチを push で復元する必要がある。

マージ時の自動削除が**有効な repo**では、GitHub が上位 PR の base を既定ブランチへ自動で付け替え、ブランチも消えている。その場合は手順 1・2 を「付け替わったことの確認」に読み替え、削除はスキップする（下記コマンドの通り）。

```bash
# 0) 積み替えに使う旧 step1 の tip を控える（ローカルブランチが残っていても名前依存にしない）
git rev-parse feature/issue-{n}-step1-{要約}
#    ローカルも消えている場合: gh pr view {マージしたPR番号} --json headRefOid -q .headRefOid

# 1) 上位 PR の base を既定ブランチへ付け替え（自動で付け替わっていた場合は確認のみ）
gh pr edit {step2のPR番号} --base {既定ブランチ}

# 2) 付け替わったことを確認してから、マージ済みブランチを削除する
gh pr view {step2のPR番号} --json baseRefName,state -q '"base=\(.baseRefName) state=\(.state)"'
#    → base が既定ブランチ・state が OPEN であること
#    自動削除が有効な repo ではブランチは既に消えているので、次の削除は不要（エラーになる）
git push origin --delete feature/issue-{n}-step1-{要約}

# 3) 既定ブランチの最新を取り込み、マージ済み差分をブランチから落とす
git switch feature/issue-{n}-step3-{要約}   # 最上段で一括
git rebase --onto origin/{既定ブランチ} {旧 step1 の tip（最新コミット）の SHA} --update-refs
git push --force-with-lease origin feature/issue-{n}-step2-{要約} feature/issue-{n}-step3-{要約}

# 4) §4 の記録 → §5 の再ゲート・再検証を済ませる
#    §4 の range-diff の引数: 旧base = 手順 0 で控えた旧 step1 の tip、新base = origin/{既定ブランチ}
#    （旧head / 新head は当該 PR のブランチの積み替え前後の位置）

# 5) 再ゲート・再チェックが完了し、マージしてよいと確認できてから ready 化
gh pr ready {step2のPR番号}
```

- **ready 化は §5 の再ゲートと人間の再チェックを終えてから行う**（マージの直前）。先に ready にすると、失効した PR やチェック未了の PR がマージ可能な状態で放置される
- 付け替えた PR の説明冒頭のヘッダ（§1）を更新する（`PR 2/4・base = {既定ブランチ}・**マージ可**`）。最も参照される情報なので、昇格のたびに直す

- `--onto` に渡すのは旧 step1 の **tip（最新コミット）** であり、最古のコミットではない。最古を渡すと step1 自身のコミットが既定ブランチの上に再生され、マージ済みの変更が重複する
- GitHub の自動付け替えは、**マージ時の自動削除では発火する**が、マージ後に `git push --delete` で手動削除した場合は**発火せず PR が CLOSED になる**（どちらも実測）。手動削除を使う運用では、上記のとおり自分で付け替えてから削除する

- **コミット ID が変わる方式（squash / rebase マージ）**: 上記のとおり `--onto` で旧コミット列を明示的に落とす。ID が変わるためパッチ同一による自動スキップが効かず、放置すると step2 の diff に step1 の差分が混ざって見える
- **merge commit 運用の repo**: 通常は `git rebase origin/{既定ブランチ} --update-refs` で足りる（マージ済みコミットはパッチ同一で自動スキップされ、`--onto` は不要。実測で確認）
- 付け替え後も §5 のとおり再ゲートが必要（付け替えによる変化の有無を問わない）
- **最上段（最後の PR）をマージしたら**、着地確認（§7-1）のうえでそのブランチを削除して終了する。付け替える上位はもう無い
- 全段のマージ後、ローカルに残ったステップブランチを削除する（squash / rebase マージ運用ではコミット ID が変わり未マージ扱いになるため `git branch -D` が要る。worktree を使っている場合はその後片付けも）

### 7-3. 復旧手順

#### (a) base ブランチを先に消して PR が閉じたとき

§7-2 の順序を誤ったとき（実測で発生）。GitHub は base ブランチが消えると PR を CLOSED にする。

1. 消したブランチを復元する: `git push origin {旧tipのSHA}:refs/heads/{消したブランチ名}`
   - SHA を控えていない場合は、**削除したブランチを head に持つ PR**（＝ひとつ下の、マージ済みの PR）から取る: `gh pr view {マージ済みの下位 PR の番号} --json headRefOid -q .headRefOid`
   - **閉じた PR の番号を渡さないこと**（それはその PR 自身の head であって、消した base ブランチではない）。復元 SHA が違っていても reopen 自体は通ってしまい、PR の差分が壊れたまま気づけない
2. PR を reopen する（`gh pr reopen {PR番号}`。base ブランチが無いと失敗するため 1 が先）
3. base を既定ブランチへ付け替える（`gh pr edit {PR番号} --base {既定ブランチ}`）
4. 付け替わったことを確認してから、復元したブランチを改めて削除する

#### (b) 誤マージ（上位 PR を下位ブランチへマージしてしまったとき）

着地確認（§7-1）で「マージ先が既定ブランチでない」と判明した場合の定型手順。変更は失われておらず、どこかのトピックブランチに集約されている。

1. **集約先の特定**: 各ブランチについて `git log --oneline origin/{既定ブランチ}..origin/{branch}` を実行し、既定ブランチに未着地のコミットがどこにあるかを調べる（通常は最上段に集まる）
2. **統合 PR を 1 本作る**: 集約先ブランチから既定ブランチへの PR を作成する（段ごとに作り直さない）
3. **マージ前に差分検証**: 想定外のコミット・ブランチが混入していないかを確認する（マージ予定のないブランチが混ざっていないか。段数分のコミットがすべて含まれるか）
4. **テスト・lint・build を実行してからマージ**する
5. 復旧の経緯と統合 PR 番号を Issue コメントに残す（スタック構成の Delta として）

## 8. スタック構成の変更（計画変更時）

計画は生きたリストであり、P6 中の変更を許容する。変更時は必ず Issue コメントの計画全体へ Delta を追記して報告し、そのうえで:

- **ステップ追加**: 既存ステップの番号は振り直さず、**挿入位置に枝番を付ける**（step1 と step2 の間なら `feature/issue-{n}-step1b-{要約}`）。手順:
  1. 挿入位置の下位ブランチから新ブランチを切る
  2. 挿入位置より上を新ブランチの上へ積み替える（**§3 の分岐 A**。下位の履歴は書き換えていないため）
  3. 新ブランチを push し、**そのブランチの PR を作る**（`--head` を明示。§1 参照）
  4. **挿入位置の直上の PR の base を新ブランチへ付け替える**（`gh pr edit {PR番号} --base {新ブランチ}`）。付け替えを忘れると、その PR の差分に新ステップ分が混ざる
- **ステップ分割**: 後半に枝番を付ける（step1 を割るなら `feature/issue-{n}-step1b-{要約}`）。手順:

  ```bash
  git branch {後半ブランチ} {対象ブランチの現 tip}      # 後半 = 現状のコミット列
  git branch -f {対象ブランチ} {分割点のコミット}        # 前半 = 分割点まで戻す
  git push --force-with-lease origin {対象ブランチ}
  git push -u origin {後半ブランチ}
  ```

  1. 後半ブランチの PR を作る（`--head` 明示・base は対象ブランチ）
  2. 直上の PR の base を後半ブランチへ付け替える（元の PR は前半ブランチのまま残す）
  3. **上位ブランチは元のコミット列の上にあるので、コミットを作り直していなければ積み替えは不要**。作り直した場合のみ §3 の分岐 B を使い、`--onto` には**後半ブランチ**を渡す（前半を渡すと後半の変更が落ち、無競合のまま壊れる）
  4. 元の PR は差分が変わるため §5 の失効規則に従う（対話的な `git rebase -i` は非対話実行できないため、上記のブランチ操作で分割する）
- **ステップ削除・順序入れ替え**: 対象コミット列を除外・並べ替えて積み替える。**作成済み PR を廃止する場合**は PR をクローズし（理由をコメント）、その上位の base を廃止 PR の下位へ付け替える（§7 と同じ操作）
- **1 PR 運用からスタックへの転換**: **既存のブランチと PR をそのまま step1 として引き継ぐ**（名前は変えない）。その上に step2 以降を積む。
  - **ブランチを改名しないこと**。`git branch -m` はリモート ref を変えないため PR が旧ブランチを追い続ける。**GitHub の rename API（`gh api -X POST repos/{owner}/{repo}/branches/{b}/rename`）も PR の head を追随させず、その PR を CLOSED にする**（draft / ready・ブランチ名の形を問わず再現。実測）。命名の不揃いは害が無いので、そのまま使う
  - **既に後半の作業までコミット済みの場合**は、後半を step2 へ移す:

    ```bash
    git branch {step2ブランチ} {現在の tip}              # 後半を含む現状を step2 に確保
    git branch -f {既存ブランチ} {分割点のコミット}       # step1 を分割点まで戻す
    git push --force-with-lease origin {既存ブランチ}
    git push -u origin {step2ブランチ}
    ```

    そのうえで step2 の PR を作り（`--head` 明示・base は既存ブランチ）、既存 PR の説明にスタック位置ヘッダを追加する
- 構成変更で積み替えまたは base 付け替えが発生した PR は §5 の失効規則に従い再ゲートする
- 構成変更後は、影響する PR の説明冒頭のヘッダ（§1 の `PR k/N`・base・マージ可否）とタイトルを実態に合わせて更新する
- チェック済み PR に影響する変更（削除・分割・順序入れ替え）は自動進行で行わず、人間に確認してから実施する

## 注意事項

- 操作前に `git status` で作業ツリーが clean であることを確認する（積み替えは未コミット差分と共存できない）
- **確認はローカルの git で行う**。force-push 直後の `gh pr diff` は数秒〜十数秒、積み替え前の差分を返すことがある。GitHub 側のビューだけで判断しない
- 積み替え・付け替えの操作履歴（実行コマンドと結果）は該当 PR のコメントに残す。障害時の巻き戻しは記録した旧位置（§3 の rev-parse）を使う
- この手順で解決できない状態（積み替えの連鎖失敗など）に陥ったら、無理に作り込まず人間へエスカレーションする
