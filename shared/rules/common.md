# AIDD Common Rules

## Purpose

この playbook は、AI 駆動開発（AIDD）を安全かつ継続的に改善するための共通運用ルールを提供する。

## Default Process

開発プロセスは Issue のタイプ（GitHub ラベル `type-*`）で決まる。詳細は `docs/design/0001-dev-phase-decomposition.md` を正とする。

- Issue は `product-intent` でタイプを確定して作成する（feature / bugfix / hotfix / refactoring / chore / spike）
- 着手は `dev` から。タイプ別ルートに従い各フェーズ skill を実行する
- 成果物の深さは判断駆動: ADR・設計書は書くべき判断が生じたときだけ作る
- 短期コンテキストは PR / Issue へ、長期記録（ADR・設計書・テスト）は records_root へ。マージ前に短期コンテキストの昇格を判定する

## フェーズ間の戻りと Intent Delta

フェーズは一方向に流れるとは限らない。後段の議論・実装で前段の検討漏れや前提の崩れに気づくのは、反復を前提とした本プロセスの**正常な挙動**であり、事故ではない。気づいたらその場で辻褄を合わせず、原因のフェーズへ戻ってよい。

- **戻り（正常な反復）**: 検討漏れ・前提変化の発見。Intent Delta を残して原因フェーズへ再入する。AI が主導してよい
- **エスカレーション（停止）**: プロダクト判断・スコープ変更・想定外の問題。作り込まず停止し、人間の判断を仰ぐ（`dev/escalation.md`）
- **部分再入**: 戻った先はフルにやり直さない。変わった項目（AC-ID / QC-ID / ADR / 設計要素）を参照する下流成果物だけを差分更新する。相互参照（AC-ID）を差分実行の索引に使う

戻る前に Issue へ Intent Delta を 1 件残す（本文・既存の確定版コメントは書き換えず追記する。履歴を残し、`context-snapshot` が古い順に適用して最新の意図を復元できるようにする）。書式:

```md
## Intent Delta（{日付}）
- 発見: {何に気づいたか / どのフェーズの議論で出たか}
- 戻り先: {P2〜P5}
- 影響項目: {AC-ID / QC-ID / ADR / 設計要素}
- 変更: {確定した変更（旧 → 新）}
```

## Project Binding（記録先・Issue の単一バインディング）

長期記録（ADR・設計書・要求）と Issue の物理的な置き場所は、プロジェクトの `CLAUDE.md` で **一度だけ** 宣言する。全フェーズの skill はこの宣言だけに従う。**フェーズごとに別の規約を混在させない**（あるフェーズはプロジェクト規約、別のフェーズは aidd 規約、という運用は禁止）。

宣言する項目:

- `records_root`: 長期記録のルート。既定 `docs/`。コンテキストハブがある場合はそのパス（例 `../remosys-context/contexts`）
- `issue_repo`: Issue を集約する GitHub リポジトリ。既定は対象 repo 自身（例 `owner/remosys-context`）
- `service`: ハブ内でサービス別に分ける場合のサービス名（例 `remosys-frontend`）。単一 repo では省略可

記録の配置（records_root 起点）:

- ADR → `adr/`。`service` 指定時のサービス固有判断は `services/{service}/adr/`、複数サービス横断は `system/adr/`
- 設計書 → `design/`（同上のルールで `services/{service}/`・`system/`）
- すべての長期記録に frontmatter（`type` / `scope` / `status` / `updated`）を付与する

宣言が無いプロジェクトは standalone（`records_root: docs/`、`issue_repo`: 自 repo）として扱う。

承認ゲートは記録の置き場所・Issue トラッカーに依存しない（人間によるコンテンツ承認）。standalone でもハブでも同一に機能する。

## AI の見解（承認ゲートの出力契約）

率直さは心構えではなく**成果物**として要求する。人間の承認を求める提示（P2 要求整理の確定、P3 技術判断の採用判断、P4 設計承認、P5 実装計画 計画承認、P7 検証・レビュー 受入れ判断など）には、**AI の見解**を必ず含める。

- **推奨**: AI 自身の推奨と、その理由
- **棄却した代替案**: 検討して採らなかった案と、捨てた理由（何とのトレードオフか）
- **懸念**: 承認前に人間が知るべきリスク・弱点。「懸念なし」と書く場合は、なぜ無いと言えるかの理由を必須にする

運用ルール:

- **見解を先に出す**: 人間の意向・好みを聞く前に AI の評価を提示する。意向を聞いてから見解を合わせない
- **根拠のない同意をしない**: 「おっしゃる通りです」等の同意表現は根拠を伴う場合のみ使う。人間の案に賛成する場合も、賛成の理由と残る懸念を書く
- **軽量ルートでも省略しない**: chore / bugfix では 1〜2 行に圧縮してよいが、フィールド自体は省略しない
- **用語を定義してから提示する**: 判断の軸として持ち出す用語には、初出時に**読み手の言語での呼び名**と、**意味の一行説明**を付ける。実装（クエリ条件・データ構造・API 名）の説明は意味の説明ではない。定義されていない用語で並べた選択肢は、読み手にとって名前のない選択肢であり比較できない。説明を後から求められた場合、その用語の上に積み上げた議論は判断材料として機能していなかったと考え、説明し直したうえで判断をやり直す
- 意見が割れたまま人間が決めた場合は決定に従う。採用されなかった懸念は ADR の「検討した選択肢」や Intent Delta として記録する

## 証拠つき報告（evidence-linked claims）

実装コードには TODO リスト・Red/Green・ゲートの規律があるが、報告・記録・後片付けというメタ作業は生成のみで進み、「未実施」を突きつける機構がない。事実主張が実態に先行する事故（実行前の「確認済み」記録、未検証の状態認定にもとづく後片付け）はここから生まれる。次を規律とする:

- **「確認済み・実施済み・green・マージ済み」等の事実主張は、実行結果の転記のみ**。先に実行し、後に記述する。予定を完了形で書かない（結果が予測どおりでも、それは検証ではなく運である）
- **他者由来の状態主張（「マージした」等）は read で検証してから後続作業に入る**。特に不可逆な操作（Issue クローズ・ブランチ削除・上書き）の前提とする場合は必須
- 破壊的な検証（ミュータント注入等）は**対象の変更をコミットしてから**行う（復元操作が未コミットの修正を巻き込まないため）
- マージ前契約チェック（`review/acceptance.md` §7）で、記録中の事実主張と実行記録の対応を機械的に照合する

## 長期コンテキスト文書の承認（対話的確定）

意図が記載される長期コンテキスト文書（ADR・設計書・P2 要求整理の確定コメント）の承認は、チャットの流れに埋め込まない。承認の成立条件は「OK が返ってきたか」ではなく「**人間が決定・帰結・棄却案を把握したか**」である。承認直後に人間が決定内容と具体的帰結を自分の言葉で言えないなら、それは形式だけ通ったゲートとして扱う。

- **切り出して問う**: 決定・選択肢・帰結を、作業の流れから独立した選択式の問いとして提示する。全文の一括提示 + OK 待ちを承認とみなさない
- **具体的帰結を明示する**: 保存パス・命名規約・データ形式など、実装に現れる決定事項を提示に含める（「知らないところで決まっていた」を作らない）
- **自動進行を中断する**: 実装フェーズ（P6 実装）の自動進行中に P3 技術判断・P4 設計へ戻る場合、自動進行を中断して承認を得てから再開する。ゲート指摘の解消として作る ADR も例外にしない（進行中の作業の勢いは、承認を流し込みにする最大の圧力である）

## Principles

- 要求確認なしに大きい実装を始めない
- 人間承認ポイントを明示する。最終決定は常に人間が行う
- **軽さは人間から見た負荷（確認回数・読む量・判断の質）で測る**。AI・機械側の時間やトークンは、ハーネスで自動化されていれば重さとみなさない。実装前フェーズ（Issue 作成・要求整理・設計）の対話密度は自動化を効果的にするための投資として許容するが、chore / hotfix は入口コストを低く保つ（タイプ別ルートと `critical-gate` のタイプ別深さ）。ゲート・ビューの出力は人間が読み切れる長さに要約する（読む量が閾値を超えた時点で「読むだけで流れる」形骸化が再発する）
- **人間の関与は確認回数ではなく、人間が実際に下した判断の数で測る**。対話密度を要求整理（P2）に偏らせず、設計判断（P3〜P5、実装中に生じる判断）へ再配分する。判断項目は一括提示でなく対話的に確定し、TODO・Red/Green 単位の自動進行は維持する（確認の総量を増やすと「読むだけで流れる」形骸化が再発する）。認知負債（人間が変更内容を理解しないまま開発が進むこと）への対策はここで行う: **理解は文書を読むことではなく、判断を下すことで保たれる**
- AI は議論で率直な意見・懸念・反論を提示し、人間の意向への同調を品質より優先しない（「AI の見解」の出力契約として要求する）
- 技術判断は必要に応じて ADR に記録する
- TDD を優先する
- 変更を小さく刻む
- コメントの役割を分ける（コード＝どう動くか / テスト＝何を保証するか / コミットログ＝なぜ変えたか / コードコメント＝なぜそうしないか）。移行ステップ番号などの内部管理語彙や、変更の正当化・経緯の語りをコード・コメントに書かない（それらは Issue / PR / ADR に置く。背景参照が要る場合も ADR への参照1点に留める）。公開関数の docstring（Args/Returns/Raises 等）は言語慣習として維持してよい
- worktree やサブエージェントで作業を始める前に、対象リポジトリを origin と同期する（古い local を対象に grep・実装・棚卸しをすると誤った結論・手戻りになる）
- 途中の発見はまず安い場所（親 Issue / PR コメント、roadmap 候補、要求の「対象外」）に捕捉する。**Issue 化はコミットメント**であり着手を決めたときだけ行う（数分で直せる負債はその場で直す）。トリアージ（昇格 / その場修正 / 候補保持 / 破棄）は P7・P8 でまとめて行い、フロー中に未着手の Issue を量産しない
- **Issue 化する前に、その発見の前提を実行出力で裏取りする**。作業中に見つけた問題は推論を含んでいることが多く、Issue 本文は長期記録として固定される（誤った前提の Issue は、着手した人がそれを疑うまで正しい前提として扱われる）
- 推測をマーカーなしで埋め込まない（信頼性マーカー 🔵/🟡/🔴。ゲート通過時に 🟡・🔴 を残さない）
- **否定形の主張（「管理外」「使われていない」「存在しない」「影響がない」）には、確認した範囲を書く**。「無い」ことは、探した範囲を示さないと検証できない。ツールが複数ある環境（IaC + デプロイフレームワーク + 手動作成）では、1 つを見ただけの所有・不使用の判断は原理的に成立しない。実行出力から転記できるところまでを事実として書き、その先は「未確認」とする（🟡 を外さない）
- skill 本文は `.claude/skills/` を source of truth として扱う
- stack が同じ差分は preset、stack 自体の差分は variant で扱う
- PR 説明には必須セクション（受入れ条件⇄テスト対応表、技術判断、短期コンテキストの昇格判定、未検証項目）をそろえる。該当がなくても「なし」と明記する
