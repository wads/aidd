# [ADR-0013] P5 の承認の前に計画を机上でなぞり、P6 の計画外の停止を記録する

## ステータス

承認済み（2026-11-20。P2 の対話で条件を人間が確定し、P3 の選択式の問いで、採用と ADR-0009 との関係（部分修正）を確定）

## 背景

P6 実装は自動進行のフェーズだが、実装の途中で人間の判断が必要になって止まる回数が多い、という指摘が人間から出た（2026-11-19）。人間の期待は 2 つある。実装中は任せておきたい。判断は、文脈がそろった計画の段階でまとめて行いたい。

P6 が止まる理由のうち、選択肢のある判断、要求・設計の検討漏れ、やらないことへの踏み込みは、実装の前に洗い出せると見ている（`tdd-cycle` の停止条件からの整理で、実測ではない）。今の P5 には「リスクと検証方針」「人間確認ポイントの配置」はあるが、ステップごとに実装をたどって判断を洗い出す手順は無い。

ADR-0009 の決定 1 は、設計が承認済みなら P5 を「順序・スタック構成・検証方針の確認に絞る」としている。この ADR は、そこに机上のなぞりを足す。

## 検討した選択肢

### 案1: P5 の承認の前に、計画のステップを机上でなぞる（採用）

- 概要: AI が計画のステップを 1 つずつ、コードを書かずにたどり、4 つ（触るファイル、最初に書くテスト、決めること、未確認の前提）を書き出す。見つかった「決めること」には行き先を付け、P6 に入る前に答えを得る
- メリット: 判断が、文脈のそろった P5 にまとまる。追加の道具が要らない。P6 の停止の理由を記録するので、効いたかどうかを後から確かめられる
- デメリット: P5 が重くなる。読んでいないコードの前提は、なぞっても外れる。効果は試すまで分からない

### 案2: 先に数件で停止の回数と理由を数えてから、足すかを決める

- 概要: 手順は足さず、次の数件の Issue で P6 の停止を記録し、多ければ手順を足す
- メリット: 実測にもとづいて決められる。効かない手順を足さずに済む
- デメリット: 数えている間、止まる回数は減らない。ADR-0012（P4 の視点ごとの合意）の効果と混ざり、どちらが効いたかが分かりにくい
- 棄却の理由: 人間が「先に足したい」と判断した（2026-11-19）。記録は案1 に含める

### 案3: 計画の段階で、実際にコードを書いて試す

- 概要: 不確かな所を、使い捨ての実装で確かめてから計画を承認する
- メリット: 机上では外れる前提も確かめられる
- デメリット: 計画の段階で実装が始まり、P5 の承認の前にコードが決まってしまう。テストを先に書く規律（`tdd-cycle`）の外で書いたコードが残りやすい
- 棄却の理由: 試さないと分からない不確かさは、spike の Issue に回す（人間が選ぶ）

### 案4: 机上のなぞりを別の skill にする

- 概要: `implementation-plan` と分けて、なぞりだけを行う skill を作る
- メリット: P5 の skill が長くならない
- デメリット: P5 の中の 1 手順に、入口と exit を別に持たせることになる。読むファイルが増える
- 棄却の理由: P5 の手順として足りる。skill を増やさない（Issue の品質条件）

## 決定内容

1. **机上のなぞり**: feature と refactoring の P5 で、承認を求める前に、AI が計画のステップを 1 つずつ、コードを書かずにたどり、ステップごとに 4 つを書き出して計画に残す。触るファイル、最初に書くテスト（テストで駆動しないステップと、新しいテストを書かないステップでは、検証手順か、守りに使う既存のテスト）、決めること（選べる案が 2 つ以上あるもの）、未確認の前提。ステップが 1 つの計画でも省かず、短く行う
2. **なぞりの結果は見込み**: P6 でそこから外れること自体は、停止にしない。止まるのは今までどおり、範囲の変更・想定外の問題・新しい技術判断が出たとき。合意した設計の再掲・再検討はしない
3. **「決めること」の行き先**: 1 件ごとに、次のどれかを付ける。(a) ADR の目安に当たれば P3 へ戻す。(b) 設計に関われば P4 へ戻す。(c) 要求の検討漏れなら P2 へ戻す。(d) やらないことへの踏み込みなら、計画を止めて、範囲の変更として人間に確認する。(e) あとから変えても、ほかのステップや設計に響かない選択は、P5 の承認のときに人間が答える。答えの無いものを残して P6 に入らない
4. **未確認の前提**: コードを読んで確かめる。外れていたら計画を直し、変わったステップをなぞり直す。確かめられないものは計画のリスクに書いて人間に示す。試さないと分からないものは、AI の推奨を付けて、リスクとして進めるか、spike の Issue を先に行うかを人間が選ぶ
5. **抜けを拾う所**: P5 の軽量版ゲートの観点（なぞりが無い、行き先が付いていない）と、P6 の開始条件（なぞりが計画に無い、答えが無い）の 2 か所
6. **計画外の停止**: P6 で、計画のステップにも人間確認ポイントにも置いていないのに、AI が作業を止めて人間に判断を求めた出来事。1 つの出来事は 1 件。前のフェーズ（P2〜P5）へ戻り、戻った先で人間の承認・採用判断を経たもの、スタックで下位の PR への指摘が設計の判断を要して中断したもの、計画のリスクに書いていたものが当たって止まったものも数える。P5 で置いた人間確認ポイント、人間の側から出た追加の依頼、P6 の開始条件で P5 へ戻ったもの、P7 のゲートの差し戻しそのものは数えない
7. **記録と見せ方**: 計画外の停止は、1 件ごとに、理由と「机上のなぞりで先に出せたか」（AI の申告と明記）を PR 説明に記録する。0 件も記録する。P7 の受入れ判断の提示には、回数だけを 1 行で出す。振り返りを行うときは必ず扱い、下書きには回数と理由（事実）だけを並べ、「前のフェーズで潰せたか」は原因を掘る段で人間と突き合わせる。振り返りの項目は、人間が外すと決めるまで続ける
8. **変えないもの**: P6 の停止条件。P5 で置く人間確認ポイント。P5 の承認を一括提示と OK 待ちにしない決まり。振り返りで人間に先に問う手順

9. **適用**: この ADR の適用後に P5 の承認を求める Issue から使う。適用の前から作業中だった Issue は 1 件（`clachic/remosys-context#150`。PR `clachic/remosys-data-processor#61`）で、対象外とし、今のまま完了する（机上のなぞり、停止の記録、P7 の回数の 1 行、振り返りの項目を求めない）。ほかに無いことを確かめた（2026-11-20。aidd と利用側 5 リポジトリの開いている PR）。wads/aidd#47 自身は、決まりになる前の試行として机上のなぞりを行う。あとで出てきたら、人間が個別に判断する

ADR-0009 の決定 1 のうち、「設計が承認済みなら P5 実装計画は順序・スタック構成・検証方針の確認に絞る」に、机上のなぞりを足す（`amends`）。ADR-0009 のほかの決定は変えない。

## 設計意図

- 判断を P5 にまとめるのは、要求・設計・計画がそろっていて、人間がその場にいる時点だからである。P6 の途中の判断は、作業の勢いの中で求められ、待ちも生じる
- 停止条件を変えずに、止まる原因を前で出しきる。回数を減らすために、止まるべき所で止まらなくなることを避ける。そのため、回数に目標や上限は置かない
- P7 に出すのを回数だけにするのは、受入れ判断の提示は判断材料で、AI の評価を数字にして混ぜないためである
- 行き先を 5 つにするのは、今の決まり（戻りと Intent Delta、範囲の変更の確認）と同じ扱いにするためで、新しい経路は (e) だけである

## トレードオフ

- P5 が重くなる。小さい Issue でも省かないので、1 ステップの計画にも数行が足される
- 計画外の停止の回数そのものも AI の申告で、書き漏らしに気づける仕組みは無い（契約チェックは、PR 説明の中の記録と回数を突き合わせるだけ）。歯止めは、振り返りで人間の記憶と突き合わせることだけ
- 「机上のなぞりで先に出せたか」は AI の申告で、振り返りを省くと人間と突き合わせないまま残る。申告は PR 説明にあるので、振り返りの最初の問いより前に人間の目に入る
- 読んでいないコードの前提は外れる。計画外の停止が 0 になることは期待しない
- 効果は未確認。ADR-0012 の効果と同じ時期に現れるので、切り分けは振り返りの中で行うしかない
- bugfix の簡易計画・chore・hotfix・spike には足さない。これらのルートの停止は、今までどおり記録されない
