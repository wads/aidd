# [ADR-0011] 用語集をユビキタス言語の正本とし、追加の規則を共通ルールに置く

## ステータス

承認済み（2026-10-06 人間承認）

## 背景

ADR-0008 は、ADR の判断領域タグの語彙表 `domain-terms.md` を定め、テンプレートに任意の「用語」節を持たせて「用語集としても使える」とした。

利用側の remosys（ハブ構成）では、業務の言葉（ユビキタス言語）を `system/glossary.md` に整備した。その過程で次のことが分かった。

- **判断領域タグと業務の言葉は別物**である。判断領域タグは ADR を引くための内部の見出し（例: データモデル、時刻の扱い）で、業務の言葉は発注者・ドメインの専門家・開発者・AI が共有する言葉（例: 上部工、卓越周波数）である。読み手も変わる頻度も違う。同じファイルに置くと、業務の言葉の表に ADR を書く人だけが使うタグが混ざる。remosys は利用側の ADR（remosys-context ADR-0012）で両者を分け、語彙表に用語の定義を置かないと決めた
- **どの語を用語集に載せるか、いつ追加するかの規則が、どこにも書かれていない**。レビューのやり取りで決めた基準（ドメインに固有の語だけ・機能や環境の名前は載せない）は、PR のコメントにしか残っていない
- **「用語集に無い名前は先に用語集へ追加してから使う」という規則は、範囲を決めないと機能しない**。ほぼすべての実装が該当し、毎回作業が止まるか、規則が守られなくなる。また、用語集と実装が別のリポジトリにある構成では、同じ PR に入れられない

## 検討した選択肢

### 案1: 用語集を別ファイルにし、語彙表は判断領域だけを持つ（採用）

- 概要: 業務の言葉の正本を `{records_root}/glossary.md`（ハブは `system/glossary.md`）とする。`domain-terms.md` のテンプレートの「用語」節は、用語集へのリンク 1 行に置き換える。載せる語の基準・名前の導き方・追加の時機を共通ルール（`shared/rules/common.md`）に置く
- メリット: 業務の言葉の表に内部タグが混ざらない。索引スクリプト（`adr_index.py`）の既定パスを変えずに済む
- デメリット: records_root の直下に、名前の似た 2 ファイルが並ぶ。冒頭の役割の説明と相互リンクで区別する

### 案2: 語彙表の「用語」節を業務の言葉の正本にする

- 概要: ADR-0008 のとおり `domain-terms.md` の「用語」節に業務の言葉を置く
- メリット: 語彙のファイルが 1 つで済み、ADR-0008 を変えなくてよい
- デメリット: 発注者・ドメインの専門家も読む表に、ADR の内部タグが同居する。ファイル名と見出し（「用語と判断領域」）が、業務の言葉の置き場として見つけにくい

### 案3: 規則を共通ルールに置かず、各プロジェクトの CLAUDE.md に書く

- メリット: 各リポジトリで起動したセッションに、規則の本文が直接届く
- デメリット: 同じ規則をリポジトリの数だけ書くことになり、二重管理になる。載せる語の基準や追加の時機は、どのプロジェクトにも共通する

## 決定内容

1. **業務の言葉の正本を用語集 `glossary.md` とする**。置き場は `{records_root}/glossary.md`（ハブは `system/glossary.md`）、テンプレートは `shared/templates/glossary-template.md`。語彙表 `domain-terms.md` は ADR の判断領域タグだけを持ち、用語の定義を置かない（ADR-0008 決定 4 の「用語集としても使え」を、本決定で置き換える）
2. **用語集に載せるのはドメインに固有の語だけ**とする。一般的な語、システムの機能・処理の名前、環境の名前は載せない。列は正式名・識別子・意味の 3 つ。識別子は実際のコード名を導き出せる一般形、意味はドメインの専門家が読んで分かる言葉で書く
3. **名前の導き方**: 画面の表示・文書・保存するフィールド・外部に公開する名前に現れるドメインの語は、用語集の識別子から使う場所の命名規則で導く。関数内の局所変数は対象外。保存済みの値・外部との取り決めと、変更しない外部提供物に由来する名前は、既存の名前をそのまま使う。既存ファイルの旧表記の改名は、表記を揃える Issue に任せる
4. **追加の時機**: P2 要求整理では、受入れ条件に用語集にない概念が出たら確定コメントに追加候補を挙げる。P4 設計では、設計書で付けた名前を設計承認と同時に用語集へ追加する。P6 実装では、仮の名前で実装を続け、用語集への追加 PR を同時に出し、人間のレビューで両方をまとめて承認する（実装を止めて用語集のマージを待つことはしない）
5. **確認**: critical-gate の設計の観点と、マージ前契約チェックで、用語集に無いドメインの語・用語集と食い違う名前・仮の名前の残存を照合する
6. 規則の本文は共通ルールに置き、各プロジェクトの CLAUDE.md は用語集の場所と共通ルールへの参照だけを書く

## 設計意図

用語集の価値は、AI が人間の言葉どおりに実装・出力することにある。そのためには、用語集に載る語が絞られていること（載せすぎると照合の手がかりにならない）と、名前を付ける場面で規則が実際に働くことの両方が要る。後者は、作業を止めずに承認の場面で揃える形（決定 4）にしないと、規則のほうが守られなくなる。

## トレードオフ

- 各プロジェクトのリポジトリで直接起動したセッションには、規則の本文が届かない（参照の 1 行だけが届く）。共通ルールを読み込むワークスペースから作業する運用を前提にする
- P6 の仮の名前は、承認時に名前が変わると実装側の修正が発生する。修正は承認後・マージ前に行う

## 影響範囲

- aidd: `shared/rules/common.md`（「用語集」節の新設）、`shared/templates/glossary-template.md`（新設）、`shared/templates/domain-terms-template.md`（「用語」節の置き換え）、`requirements` / `design-docs` / `tdd-cycle` / `critical-gate` / `review` / `context-snapshot` の各 skill、ADR-0008 の frontmatter（`amended_by`）
- 利用側: 用語集が無いプロジェクトは、最初に名前を付ける機会に作る。remosys は作成済み（remosys-context PR #94）
