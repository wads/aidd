# [ADR-0012] 設計を視点ごとに snapshot で合意し、設計ドキュメントをコンポーネント単位で保守する

## ステータス

承認済み（2026-11-11。AAR 2026-11-07 の T2。P1・P2 の対話で方針を人間が選び、P3 の選択式の問いで未決の 3 点を確定したうえで採用）

## 背景

AAR 2026-11-07 で、人間から次の期待が出た。

- dev のフローでは、人間と詰める話が要件に偏っている。設計（作るクラス・モジュール、依存関係、データモデル、処理の流れ）も人間と合意したい。実装前に設計の意図も把握して、手戻りを起こしたくない
- Issue の途中で作った図は、snapshot で確かめられればよい。snapshot に要求・要件・設計・実装のポイントを足していき、それでレビューと受入れを判断する。Issue が完了したら消す
- 設計の文書は、Issue ごとに積み上げず、レイヤーやコンポーネントの粒度で常に保守する
- 意図（なぜそうなっているか・いないか）は記録したいが、判断の過程のやり取りは過剰に記録されている。残したい判断だけを ADR にする

今の決まり（ADR-0009）は、構造基準に当たる Issue で設計書を書いて承認を得る形で、何を、どの順に、どんな図で見せるかは決まっていない。設計書は Issue ごとの連番で、書き換えずに Replaces で置き換える。snapshot は記録から作る生成ビューで、途中版も消さない。

## 検討した選択肢

### 案1: 視点ごとに snapshot で合意し、残す文書はコンポーネント単位の設計ドキュメントにする（採用）

- 概要: P4 で AI が見せる視点を提案し、1 つずつ snapshot に足して合意する。合意の事実は Issue の 1 行で残す。Issue ごとの設計書は作らない。受入れのあと、関係する設計ドキュメントを更新する。snapshot は片付けで消す
- メリット: 設計の判断が、図を見ながら 1 つずつ人間を通る。残る文書は、今の構造を表す 1 つの場所になる。過程の記録が減る
- デメリット: Issue の途中の設計の元が、バージョン管理の外の snapshot になる。消したあとは、合意の経緯（棄却した案）が残らない。25 ほどのファイルにある「設計書」を前提にした決まりを付け替える必要がある

### 案2: 視点ごとに合意するが、記録の形は変えない

- 概要: 視点を 1 つずつ図つきで見せて合意し、合意した内容は今までどおり Issue ごとの設計書に書く。snapshot は生成ビューのまま
- メリット: 変更が `design-docs` の手順に収まり、新旧の方式が重なる場面ができない
- デメリット: 設計書が Issue ごとに積み上がり、今の構造がどの設計書に書いてあるかを追う必要が残る。過程の記録も減らない

### 案3: 合意した図を Issue コメントに記録し、snapshot はそこから作る

- 概要: snapshot を生成ビューのまま保ち、合意した図（mermaid）は Issue コメントに残す
- メリット: snapshot を消しても経緯が Issue に残る。生成ビューの原則を変えない
- デメリット: 過程を逐一残すことになり、背景の「必要な判断の議論だけ残す」に反する

### 案4: すべての技術判断を、受入れ時に人間が選んで ADR にする

- 概要: P3 や実装中の判断も snapshot 上で行い、ADR にするのは受入れ時に選んだものだけにする
- メリット: ADR が減る
- デメリット: 途中で止まった Issue の判断が残らない。adr の手順、実装中に止まる決まり、ゲートの観点まで変わる

## 決定内容

1. **P4 の設計は、視点ごとに合意する**: P4 の入口で、AI が見せる視点を理由つきで提案し、人間が足し引きする。視点の候補は、今の設計書テンプレートの節（構造・依存、データ、流れ、判断が要る点）。構造基準に当たる Issue では 0 件を選べず、「構造・依存」（構造図つき）と「技術的負債の方針」を必ず含める。当たらない Issue で 0 件にするときは、理由を人間に示して確定する。視点は 1 つずつ snapshot に足し、AI の見解を付け、合意してから次へ進む
2. **合意の印は Issue の 1 行**: 合意したら、Issue に 1 行（日付、合意した視点の名前、snapshot の URL）をコメントする。図ややり取りは書かない。ゲートと契約チェックは、この 1 行で合意の有無を確かめる
3. **snapshot は、Issue の途中の設計の元にする**: snapshot は Issue を通して同じ 1 枚に足していく。合意した視点は、人間の再合意なしに変えない。それ以外の節（要求、技術判断、検証）は、今までどおり記録から作る。ADR-0009 決定 3 の「判断ポイントごとに作り直す」は、記録から作る節にだけ残る
4. **Issue ごとの連番の設計書は、新しく作らない**: この変更のマージの時点で P4 を終えていない Issue すべてに新方式を使う。P4 を終えている Issue は、その設計書を設計の合意として読み、完了する。その Issue があとで P4 へ戻ったときは、新方式で合意し直す。設計ドキュメントの更新（決定 5）、ADR にする範囲（決定 7）、片付け（決定 8）、連番の設計書を新しく作らないことは、マージ後のすべての Issue に掛かる。既存の設計書は、新しい形へ移さずに残す
5. **残す文書は、レイヤー・コンポーネント単位の設計ドキュメントにする**: `{records_root}/design/` に、連番を付けずにレイヤー・コンポーネントの名前で置く（service の分け方は今と同じ）。書くのは、今の構造、その意図、守るべき振る舞い、受け入れている技術的負債とその返済条件。書き換えて保守する。Issue が書くべき内容を変えたか生んだときに、人間の受入れ判断のあと、最終 PR のマージの前に更新する。最初に作るときは、AI が切り方の案を出し、人間が決める
6. **設計ドキュメントと ADR の分担**: ADR にした判断は、設計ドキュメントで繰り返さず、ADR を参照する。ADR にしなかった意図は、設計ドキュメントに書く。同じ対象について設計ドキュメントと既存の設計書の両方があるときは、設計ドキュメントを正とし、置き換えた既存の設計書の名前を設計ドキュメントの側に書く（既存の設計書には手を付けない）
7. **ADR にする範囲**: P3 の技術判断と、実装中に出た選択肢のある判断は、今までどおりその場で ADR にする。P4 の視点の合意で出た棄却案は、受入れの昇格判定で AI が候補に挙げ、人間が選んだものだけを ADR にする
8. **snapshot は片付けで消す**: 人間の受入れ判断が済み、最後の PR の着地を確かめたあと、snapshot（公開ページとローカルの控え）と作業記録を消す。AI が削除を申し出て、人間の確認を 1 回得る

## 設計意図

人間の関与は判断の数で測る（`common.md`）。ADR-0009 は設計を判断ポイントとして固定したが、判断の単位は設計書 1 本だった。単位を視点に下げ、図を 1 つずつ見せることで、「読むだけで流れる承認」を減らす。

記録は、目的で分ける。Issue の途中に要るのは判断の材料で、これは snapshot が持つ。完了後に要るのは「今どうなっているか、なぜか」で、これは設計ドキュメントと ADR が持つ。Issue ごとの設計書は両方を兼ねていたので、積み上がるほど「今」が読みにくくなっていた。

## トレードオフ

- snapshot は、ローカルの控えがバージョン管理の外にあり、公開ページも人が消せる。失うと、合意した設計を再構成できない（P4 で再合意する）
- snapshot を消したあとは、合意の 1 行の URL が開けなくなる。残るのは、合意した事実と視点の名前だけになる
- 視点ごとの合意は、設計書 1 本の承認より往復が増える。新方式の最初の 2 件で、往復と分量を P8 振り返りで観察し、必須の視点や順を見直す
- 新旧の方式が併存する間、ゲートと後続の手順は、snapshot の合意した視点と、既存の設計書の両方を読む
- 公開ページが使えない環境（Codex など）では、ローカルの控えを 1 枚として扱う。代替の公開先は、ADR-0009 のとおり未定のままにする
