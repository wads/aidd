# [ADR-0009] 構造基準による設計協議の必須化と snapshot の常時公開

## ステータス

承認済み（2026-09-11。PR #19 の振り返り（AAR）で人間が期待違反として挙げ、選択式の問いで確定。同日のゲートで判断駆動の原則との整合・Artifact 依存・P3 の扱い・下限を追加確定）

## 背景

PR #19（ADR の索引化）の振り返りで、人間から 3 つの期待違反が出た。

- 受入れ判断のための snapshot が、途中版を含めて常に見られる状態になかった。生成は 1 回だけで、以後の判断ポイントでは数値の差し替えで流用され、図はテキストの木構造だけだった。規約は「`.snapshots/` に使い捨て・バージョン管理外」で、常時閲覧と両立していない
- 実装前に、技術選定・構造（レイヤー / クラス / シーケンス）・命名・パターン・技術的負債を増やさない方針の協議が無かった。P4 設計は「判断駆動」で、判断主体が AI のため飛ばす方向に倒れ、今回は「設計書なし」の明示すら無かった。設計書テンプレートにも図・命名・パターン・負債方針の欄が無い
- critical-gate の設計レンズは「設計書との不整合」を見る作りで、設計書が無いこと自体を指摘しない。技術的負債の増大を問う項目も無い

## 検討した選択肢

### 案1: 構造基準で P4 を必須化し、snapshot を Artifact で公開、レンズに 2 項目追加（採用）

- 概要: テスト以外のコードの新設または責務分割・依存方向の変更を伴う feature / refactoring では設計書を必須にする。この基準は規模ではなく構造の条件であり、2026-06-12 の「規模軸（Lite / Standard / Full）は廃止し深さは判断駆動」の結論は維持する。変わるのは判断の主体で、AI 単独の判断から「条件に当たれば設計判断が生じたとみなす + 作らない場合は人間が確定」に移す。設計書テンプレートに技術選定との対応・構造図（mermaid）・命名とパターン・技術的負債の方針を加える。snapshot は Artifact として 1 URL を判断ポイントごとに更新し、`.snapshots/` に連番で途中版を残す。レンズに「設計書が無い変更で構造の判断が diff に埋まっていないか」「技術的負債を増やしていないか」を足す
- メリット: 設計協議が人間の判断として入り、認知負債（理解しないまま進む）が減る。snapshot は版履歴つきで常に開ける。飛ばした設計をゲートが拾う
- デメリット: 小さな feature でも新規ファイルがあれば設計書が要る（短い設計書でよい）。Artifact（Claude Code 固有）に依存し、Codex 等では決定 3 が成立しない（代替は未定）

### 案2: P4 は判断駆動のまま、テンプレート拡充と「設計書なし」の明示だけ

- 概要: 構造基準を作らず、飛ばすときの理由提示を必須化する
- デメリット: AI が飛ばす方向に倒れる構造が残る。今回の期待違反の直接原因を解消しない

### 案3: snapshot を records_root にコミットして残す

- 概要: `docs/snapshots/` に連番でコミット
- デメリット: 「生成ビューはコミットしない」方針と衝突し、GitHub では HTML が描画されない（md なら mermaid は描画されるが、HTML の snapshot は不可）

### 案4: `.snapshots/` に連番で残すだけ

- 概要: 最小変更
- デメリット: 開くにはファイルを取りに行く必要があり、worktree の削除で消える。「常に見られる」を満たさない

## 決定内容

1. **P4 設計の必須化（構造基準）**: feature / refactoring で、テスト以外のコード（モジュール・スクリプト・コンポーネント。playbook の md やテンプレートは含まない）を新設する、または既存の責務分割・依存方向を変えるときは、設計判断が生じたとみなして設計書を必ず作る（小さな変更なら短い設計書でよい）。これは規模軸ではなく判断駆動の原則の中の条件であり、2026-06-12 の規模軸廃止の結論は維持する。それ以外は判断駆動だが、作らない場合は「設計書なし」と理由を人間に提示して確定する。設計が承認済みなら P5 実装計画は順序・スタック構成・検証方針の確認に絞る
5. **P3 の「ADR なし」の確定**: 構造基準に当たる変更では、P3 で「選択肢のある技術判断は無い」と AI が判断した場合も、その旨と理由を人間に提示して確定する（「設計書なし」と同じ問いにまとめてよい）。それ以外の変更の P3 は現状どおり判断駆動
2. **設計書の内容**: テンプレートに「技術選定との対応」「構造図（mermaid。関係する範囲のレイヤー図 / コンポーネント図は必須、クラス図・シーケンス図は設計要素があるとき）」「命名とパターン」「技術的負債の方針（意図的に受け入れる負債と返済条件、増やさないための制約。無ければ『なし』）」を加える。承認は構造図を見ながら判断項目ごとに行う
3. **snapshot の公開**: Artifact（クロード上の公開ページ。同じファイルを再公開すると同じ URL が更新され版履歴が残る）として公開し、同じ Issue では 1 つの URL を判断ポイントごとに再公開して更新する（再公開時は Issue に貼った URL を指定する。stacked PR では各 PR の受入れ判断でも更新）。URL は Issue と PR に貼る。Artifact が使えない環境（Codex 等）の代替は未定とし、必要になった時点で決める。ローカルは `.snapshots/snapshot-{Issue}-{連番}-{日付}.html` で途中版を残す。内容は日本語・簡潔で、文章の代わりに図（mermaid）で情報量を確保する。判断ポイントごとに作り直し、数値の差し替えで流用しない
4. **ゲートの設計レンズ**: 「設計書が無い変更で構造の判断が diff に埋まっていないか（構造基準に当たれば戻り先 P4）」「技術的負債を増やしていないか（記録の無い負債は戻り先 P4）」を追加する

## 設計意図

人間の関与は判断の数で測る（`common.md`）。今回は要求（AC/QC）と受入れの判断はあったが、構造の判断が一つも人間を通らなかった。設計を判断ポイントとして固定し、snapshot の図で判断材料を出し、飛ばした場合はゲートで戻す、の三点で「実装中に決まった構造」を無くす。

## トレードオフ

- 新規ファイル 1 本の小さな変更でも設計書が要る（人間が確認済みで受容）。負荷が過剰なら構造基準を見直す（振り返りで判定）。既存ファイル内の大改修は構造基準に当たらず判断駆動に落ちるが、「設計書なし」の人間確定が安全網になる
- Artifact（Claude Code 固有）への依存。ADR-0002 が残した Codex 併用の経路では決定 3 が成立せず、代替は未定。ADR-0002 とは併存する（`considered`）
- レイヤー・依存方向の違反は、プロジェクトに層の定義が無いと判定できない。定義は設計書側に持つ

## 影響範囲

- `.claude/skills/context-snapshot/`（SKILL.md・workflow.md）、`design-docs/`（SKILL.md・workflow.md・template.md）、`adr/workflow.md`（ADR なしの確定、snapshot の配線）、`dev/SKILL.md`・`routes.md`、`implementation-plan/workflow.md`、`critical-gate/lenses.md`・`workflow.md`（P5 軽量版の視点）、`review/acceptance.md` §5、`shared/rules/common.md`（判断駆動の原則に構造基準を追記）、`docs/design/0001-dev-phase-decomposition.md`（原則・ルート表・P4 節・成果物表）、`docs/design/0002-stacked-pr-responsibilities.md`（snapshot は各 PR でも更新）、`README.md`、`docs/manual.md`、`docs/assets/dev-phase-overview.svg`、`.gitignore` のコメント
- 利用側プロジェクト: 次の feature / refactoring から適用。既存の設計書は書き換えない
