# [ADR-0005] マージ順序を draft 状態で機械的に強制する

## ステータス

承認済み（2026-09-05）。ADR-0003 / ADR-0004 を置き換えるものではなく、AC-7（最下段から順に都度マージ）の実現方式を追加で定める。

## 背景

stacked PR ではマージ順序に不変条件がある。**マージできるのは最下段（base が既定ブランチ）の PR のみ**で、上位 PR を先にマージすると変更は既定ブランチではなく下位のトピックブランチへ入る。

この制約を「AI が守るルール」として手順書に書いていたが、**マージを実行するのは人間**であり、GitHub は base がトピックブランチの PR でもマージボタンを有効にする。実運用（clachic/remosys、Issue clachic/remosys-context#73 の 4 段スタック）で、4 本すべてが MERGED になったのに develop へ届いたのは最下段 1 本だけ、という事故が発生した。21 コミットが最上段のブランチに取り残され、全マージ完了後の後片付けまで誰も気づかなかった。復旧には統合 PR を別途作成している。

先行積み上げ（チェック待ちの間も次を積む）を前提にする以上、「複数の PR が同時にマージ可能に見える」状態は構造的に発生する。

## 検討した選択肢

### 案 1: 最下段以外は draft のまま保つ（採用）

- 概要: ready 化は最下段になったときだけ行う。上位 PR は draft のままチェックを依頼する
- メリット: GitHub は draft PR のマージをブロックするため、順序制約が**機械的に**守られる。レビュー・コメントは draft でも可能なので、人間チェックの運用は変わらない。draft ガード自体は利用先 repo の設定変更を必要としない（PR 単位の操作だけで完結する）
- デメリット: `types: [ready_for_review]` などで draft をスキップする CI 設定の repo では、上位ステップの CI が最下段になるまで走らない

### 案 2: 文章で順序を伝える（従来・棄却）

- 概要: PR 説明やコメントに「#109 から順にマージ」と書く
- メリット: CI への影響がない
- デメリット: 人間の記憶と注意に依存する。**実運用で実際に破られ、事故に至った**

### 案 3: branch protection で強制（棄却）

- 概要: 既定ブランチ以外を base にする PR のマージを設定で禁じる
- メリット: 最も強い強制力
- デメリット: 利用先 repo の設定変更を**必須**にする。ADR-0003 案 5a で定めた「利用先 repo の既存設定を尊重する」方針に反する。案 1 が推奨する «Automatically delete head branches» の無効化（下記）とは、守らなかった場合に運用が止まるか復旧可能かの点で性質が異なる

## 決定内容

最下段以外の PR は draft のまま保ち、ready 化は §7 でその PR が最下段になったときにだけ行う。積み替えで失効した最下段 PR は `gh pr ready --undo` で draft に戻す。あわせて、PR 説明の冒頭にスタック位置とマージ可否を明記し、チェック依頼の先頭に「今マージしてよいか」を置く。

## 設計意図

順序制約は人間が実行する操作にかかるため、AI 側の手順をいくら精密にしても守られない。人間の記憶に依存しない歯止めを、利用先 repo に追加設定を求めずに得られるのが draft 状態である。

## トレードオフ

- draft をスキップする CI 設定の repo では、上位ステップの CI が最下段になるまで走らない。その場合は CI を draft でも走る設定にするか、積み替え後のローカル検証（`stacked-pr` §5）で代替する（手順書に明記）
- ready / draft の切り替え操作が増える（最下段への昇格時と失効時）
- draft PR では CODEOWNERS による自動レビュアー要求が発火しない（GitHub の一般的な挙動。本 Issue では未検証）

なお «Automatically delete head branches» の無効化は、この draft ガードではなく**スタック運用全体（base 付け替え）の前提**であり、ADR-0003 のトレードオフに属する。有効なままでも `stacked-pr` §7-3 (a) で復旧できるため、必須の設定変更ではなく推奨である。
