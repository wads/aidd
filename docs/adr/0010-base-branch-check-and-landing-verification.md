# [ADR-0010] マージ順序の防御を base の判定に置き、着地を二点で確認する

## ステータス

承認済み（2026-09-15。wads/aidd の PR #21〜#28 のマージで発生した事故の振り返りで、選択式の問いにより A + B を採用）

## 背景

PR #23 は base が `feat/p2-confirmation-record`（PR #21 のトピックブランチ）のままマージされ、変更は main ではなくそのブランチへ着地した。PR #21 は 11 秒前に main へマージ済みだったが、**ブランチを削除していなかったため GitHub の base 付け替えが起きなかった**。#23 の表示は「Merged」であり、着地先の違いはどこにも警告として出ない。取りこぼしに気づかないまま PR #26・#27 が main へマージされ、発覚したのは PR #28 の衝突解消で `review/acceptance.md` を main と突き合わせたときだった。回復に PR #29 を要した。

同型の事故は ADR-0005 の背景にも記録されている（clachic/remosys-context#73）。当時の対策（最下段以外は draft のまま保つ）は ADR-0007 が `gh stack` のサーバー側順序強制で置き換えたため廃止された。

このリポジトリには、この事故クラスへの防御が 3 層ある。今回はすべて発火しなかった。

- **サーバー側の順序強制（ADR-0007）**: `gh stack` で作ったスタックにしか効かない。#23 は base を手で指定した通常の PR で、GitHub から見ればトピックブランチへの正当な PR である
- **draft ガード（ADR-0005、廃止済み）**: 順序強制の役割はサーバー側へ移ったとみなして廃止したが、その前提は「スタックは `gh stack` を通る」であり、**手作りのスタックには引き継ぎ先が無いまま消えた**
- **契約チェックと着地確認（`review/acceptance.md` §7、`stacked-pr/workflow.md` §7）**: どちらも発火条件が「（スタック時）」である。#21/#23 を誰もスタックと呼んでいなかったため読まれなかった

3 つとも発火条件が「これはスタックである」という**人手の分類**に依存している。一方、実際の危険条件は分類ではなく **PR の base が既定ブランチでないこと**であり、これは `gh pr view --json baseRefName` で機械的に判定できる。「スタックを組む」と宣言せずに前の作業の上へ積んだ PR は、宣言が無いぶんすべての防御の外側に落ちる。

もう一点、既存の照合はすべてマージ前にある。着地の失敗はマージ後にしか観測できない事象であり、汎用の手順に受け皿が無かった。

## 検討した選択肢

### 案 A+B: 発火条件を base の判定に置き換え、着地確認を二点で必須にする（採用）

- 概要: 契約チェック（`review/acceptance.md` §7）に条件なしの項目として「この PR の base が既定ブランチか」を加える。あわせてマージ後の着地確認を §8 として新設し、マージ直後と次の着手（P1）の二点で確認する
- メリット: 判定が PR のメタデータから機械的に決まり、人手の分類に依存しない。マージ前（A）とマージ後（B）の両方を塞ぐ。追加は skill 本文の数行で、利用先 repo の設定変更も新しい道具も要らない
- デメリット: どちらも実行されなければ効かない自己申告型のチェックである（ブロックはしない）。二点目の P1 着手時チェックは、次に何かへ着手するまで発火しない

### 案 C: draft ガードを非ネイティブのスタック向けに復活させる（棄却）

- 概要: base が既定ブランチでない PR は draft のまま保ち、GitHub のマージブロックを利用する
- メリット: マージ操作そのものをブロックできる。強制力は A+B より強い
- デメリット: ADR-0007 が draft の役割を「未チェック・失効中を表す唯一の機械的な印」に整理した直後に、順序ガードの意味を重ねることになる。印の意味が二重になると、draft を見たときに何を意味するのかが読み手に決まらない。A+B で足りなかった場合の次の手とする

### 案 D: 手作りのスタックを禁止し、積むなら `gh stack` のみとする（棄却）

- 概要: base をトピックブランチにする PR を作らない
- メリット: 発生源を断つ
- デメリット: 「前の PR の上に少し積む」だけのケースにも `gh stack` を要求することになり、chore や小さな修正の入口コストが上がる（`common.md`「軽さは人間から見た負荷で測る」）。今回のように振り返りから生まれた小さな playbook 変更が、まさにこのケースである

## 決定内容

1. **契約チェックの項目を base の値で判定する**: `review/acceptance.md` §7 に、スタックかどうかに関係なく「この PR の base が既定ブランチか」を確認する項目を置く。既定ブランチでない場合は、下位を先にマージし base が付け替わったことを確認してからマージする。付け替えは下位のブランチが削除されたときに起きることを明記する
2. **マージ後の着地確認を必須にする**: `review/acceptance.md` に §8 を新設し、`git merge-base --is-ancestor {マージコミット} origin/{既定ブランチ}` で着地を確認して記録する。着地していなければ次の作業へ進まない
3. **二点目の受け皿を P1 に置く**: マージ後の確認は人間からの伝達に依存するため、`dev/workflow.md` の開始手順にも「直前にマージした PR の着地確認」を置く。伝達が漏れても、次に何かへ着手した時点で検知する
4. **スタック時の手順は据え置く**: `stacked-pr/workflow.md` §7 の着地確認はそのまま残し、規律自体はスタックに限らないことを §8 への参照で示す

## 設計意図

防御の発火条件を人手の分類（「これはスタックである」）から、機械的に読める事実（PR の base）へ移す。分類を条件にする限り、分類しなかったケースは必ず防御の外側に落ちる。今回の事故は注意力ではなく、条件の置き方が生んでいる。

あわせて、検知の位置をマージ前だけでなくマージ後にも置く。着地の失敗はマージ後にしか観測できない事象であり、マージ前の照合をいくら厚くしても原理的に見えない。

## トレードオフ

- A も B もブロックではなく自己申告型のチェックであり、実行されなければ効かない。強制力が必要と判明した場合は案 C（draft ガードの部分復活）へ進む。判定は次にこの経路の事故が起きたときに行う
- P1 着手時の確認は「次に何かへ着手するまで」発火しない。単発の変更だけを行って開発を止めた場合、着地の失敗は検知されないまま残る
- 「直前にマージした PR」の特定は、複数の PR を並行してマージした場合に曖昧になる。その場合は当該 Issue に関係する PR をすべて確認する
