# [ADR-0003] stacked PR 運用を git 標準機能 + gh で構成する

## ステータス

承認済み（2026-09-04、Issue #18 の P3 技術判断）

## 背景

Issue #18 で aidd フローに stacked PR（積み上げ式 PR）運用を導入する。P2 で確定した AC（ステップ = 1 PR、先行積み上げ、PR 単位ゲート、diff 不変判定つき再ゲート規則、都度マージ）を実現する方式の選択が必要になった。

## 検討した選択肢

### 論点 1: スタック管理の基盤

- **案 1a: git 標準機能 + gh（採用）**: 外部依存ゼロ。どの利用先 repo でも追加セットアップ不要。積み替えの自動化はツール製より弱い
- 案 1b: Graphite（gt CLI）: restack・一括 submit が最も楽だが、外部サービスのアカウントと GitHub App 連携が必要。クライアント案件 repo に外部サービスを繋ぐ判断が別途要る
- 案 1c: spr 系（1 コミット = 1 PR）: aidd は Green / Refactor ごとに複数コミットを積む運用のため、コミット粒度と PR 粒度が一致せず不適合

### 論点 2: 積み替え（restack）の方式

- **案 2a: `git rebase --update-refs` で一括（採用）**: 1 コマンドでスタック全体を載せ替え、途中ブランチの先頭も自動で付け替わる。付け替え忘れが構造上起きない
- 案 2b: ブランチごとに `git rebase --onto`: 古い git でも動くが、段数分の手動実行と旧コミット ID の特定が毎回必要で、ミスの余地が大きく手順の再現性（QC-1）に不利
- 案 2c: merge で下位を取り込む: 各 PR の差分が自ステップ分でなくなり AC-5 に違反

### 論点 3: 再ゲート免除の「diff 不変」判定（AC-9）

> この論点の決定は [ADR-0004](0004-diff-unchanged-by-changed-lines.md) に置き換えられた（2026-09-05、QC-1 検証で range-diff の過検知が判明したため）。以下は当時の記録。

- **案 3a: `git range-diff` で積み替え前後を比較（採用）**: 標準機能で機械的に判定でき、判定結果を PR コメントへ転記できる
- 案 3b: patch-id 直接比較: 同じことをより低レベルにやるだけで、判定根拠の説明性が低い
- 案 3c: 目視確認: 再現性がない

### 論点 4: Execution Intent（実装計画）の置き場

- **案 4a: スタック時は計画全体を Issue コメントへ、各 PR 説明は自ステップ分のみ（採用）**: 計画全体はどの PR にも属さないため Issue に一元化。下位 PR が都度マージで先に閉じても参照が切れない。従来規約「計画 = draft PR 説明」のスタック時の変更になる（1 PR 運用は従来どおり）
- 案 4b: 最下段 PR に全体を書く: 都度マージで最初に閉じるため、進行中に参照先がアーカイブ化する
- 案 4c: 各 PR に全体を複製: 二重管理になり更新が腐る

### 論点 5: マージ方式（squash / merge commit）の扱い

- **案 5a: playbook では規定しない（採用）**: 利用先 repo の既存設定を尊重する。手順書に squash マージ時の積み替え手順（既定ブランチへの rebase でマージ済み差分を落とす）を含める
- 案 5b: merge commit 推奨を規定: 積み替えは最小化されるが、利用先 repo のマージ方針を playbook が拘束するのは越権。squash 運用の repo では導入障壁になる

## 決定内容

stacked PR 運用は git 標準機能（`rebase --update-refs` ほか）と gh のみで構成する。積み替えは連鎖付け替えで一括、再ゲート免除判定は range-diff（**→ ADR-0004 で変更行の比較に置き換え**）、計画全体は Issue コメント（各 PR は自ステップ分）、マージ方式は規定しない。

## 設計意図

aidd の不変条件「軽さ」を優先し、利用先 repo に追加のツール導入・サービス連携・設定変更を要求しない構成にする。判定（diff 不変）と操作（積み替え）がどちらも標準コマンドで機械的に再現できることで、手順の skill 化（QC-1: 別セッションでの再現）が成立する。

## トレードオフ

- 積み替えの自動化は Graphite 等の専用ツールに劣る。段数が深いスタックでは手数が増える（P2 で 1 ステップ = レビュー可能な粒度と定めており、実用上の段数は数段を想定）
- `git rebase --update-refs` のため git 2.38+（2022-10）が環境要件になる（QC-3 で明記）
- squash 運用の repo では下位マージのたびに積み替えが必須になる（案 5a の帰結）
- 積み替えのたびに各ブランチへ `git push --force-with-lease` が必要になる。トピックブランチ（自分専用）に限る例外として手順書に明記する
- **ブランチ削除の順序に制約がある**: base 付け替えより先に手動でブランチを消すと上位 PR が CLOSED になる。一方、マージ時の自動削除は GitHub が上位 PR を自動で付け替えるため安全（どちらも実測）。repo 設定の変更は要求しない（2026-09-05 追記: P7 ゲートの指摘と QC-1 の実測による）

## 影響範囲

- 利用先プロジェクトの環境要件（git 2.38+）
